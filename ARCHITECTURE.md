# Orchestrator Architecture

Decisions about how the Orchestrator itself is built and operated — for whoever implements the v1 Orchestrator. The conventions a Managed App's own code follows are under Managed app standards at the end. Terminology follows [GLOSSARY.md](GLOSSARY.md).

**The flow.** [docs/flow-spec.md](docs/flow-spec.md) is the official, numbered spec of how a request becomes a running, recorded change; cite its steps as `STEP n.m`. This document explains the parts in terms of that flow. The flow was redesigned around a separate planning process, child tickets filed as GitHub sub-issues, and fix-first; it is built (the tickets are in `.wayfinder/intake-planning-redesign/`) and was seen live on #140 and #145; a passage that says "not yet seen live" or "not built yet" says so for that part.

Each decision links back to its ticket in the archived `.scratch/orchestrator-spec/issues/` (git tag `archive/pre-purge-2026-10-21`) for the full comparison, runner-ups, and citations.

## Agent runtime

The Orchestrator reuses an existing open-source CLI coding-agent harness rather than a custom LLM loop — shrinks build scope and matches the Factory's open-source lean.

**Harness: [OpenHands](https://github.com/All-Hands-AI/OpenHands)** (MIT). SWE-bench-leading, pluggable to open-weight models via LiteLLM, purpose-built `--headless` CLI mode with `--json` structured output. Runner-up: mini-swe-agent.
→ [issues/01](https://github.com/ojones/ai-factory/blob/archive/pre-purge-2026-10-21/.scratch/orchestrator-spec/issues/01-agent-runtime-reuse-harness.md), [issues/07](https://github.com/ojones/ai-factory/blob/archive/pre-purge-2026-10-21/.scratch/orchestrator-spec/issues/07-which-agent-harness.md)

## Agents and Build Run stages

A Build Run runs several Agents in sequence, each a separate headless OpenHands invocation with its own role prompt. Role prompts live in ai-factory, not in the Managed App repo, so the coder can't edit its reviewer's instructions. Agents hand off through `main` and structured JSON files (findings, verdicts), never through branches or PRs. **The coder is the only Agent whose work reaches `main`**, but it only commits: the Orchestrator holds the PAT and does the push, so no Agent can read a credential from its checkout or environment. The Orchestrator rejects and discards a coder commit that touches the Starter Template's protected files (`.github/`, `fly.toml`, `fly/`, the flag wrapper `feature-flags.ts`, `INTAKE.md`, and the lint and formatter config `eslint.config.mjs`, `.prettierrc.json`, `.prettierignore`), since the workflows hold the Fly token and the lint config is how a check reaches every app: owning it means the coder cannot loosen a rule to make a check pass. When template sync changes that config it is committed locally after the run's base and pushed with the coder's first reviewed work (a push of the config alone could turn the app's Test Gate red), and the coder, and only the coder, fixes what the new rules report, through the same Update App Intake as everything else; the Orchestrator also names any `eslint-disable`, `@ts-ignore` or `@ts-nocheck` a diff adds as a minor finding.

**Roles**
- **Coder**: implements the task from the Intake issue (from its child ticket, STEP 4.1), committing to `main` for the Orchestrator to push. Every change goes behind a feature flag recorded in `flags.json` (the Orchestrator names and creates it) unless it has no user-visible effect ([Feature-flag infrastructure](#feature-flag-infrastructure)). Its model is set in [agents/profiles.yml](agents/profiles.yml) (currently DeepSeek-V4.1-Flash, see [Model serving](#model-serving)).
- **Reviewer**: read-only on code. Reviews the coder's commit **before it is pushed** (so code it blocks never reaches `main` or the deploy) and emits a structured JSON verdict with findings, plus any `improvements` it suggests for the system (below). On an update, a user-facing change with no flag around it is a top-priority finding, but a first build is never faulted for lacking flags; it wraps nothing itself and sends the finding back to the coder. **The Orchestrator derives the verdict from the findings and their structure** (`banded_findings`): every finding carries a `category` and an `evidence_kind` (`repro`, `cited` or `opinion`), and one the reviewer called blocking blocks only if its category can block (not style, duplication or other) and it has a repro or a cited file and line; otherwise it is minor, with the reason recorded. A document without that structure is refused and the reviewer is asked again, so a label is never trusted alone. Two flag checks need no judgement and are made by the Orchestrator itself (`flag_findings`, always minor): a flag no code outside the tests reads, and a flag description with no issue reference. The Orchestrator ignores the model's own `verdict` field: in testing the model wrote "clean" on every diff, even while listing blocking findings. When the reviewer is asked for structured output, the schema must put analysis and findings before the verdict, because generation follows property order and a verdict-first schema approved every diff, including an obvious command injection. Its model should differ from the coder's, since a clean review releases to everyone and a shared model shares blind spots. **Known deviation:** both currently run DeepSeek-V4.1-Flash (chosen on speed and cost, see [Model serving](#model-serving)), so the reviewer shares the coder's blind spots until one of them changes; revisit when the model-upgrade benchmark exists.
- **Tester**: runs after the push, against the deployed app, and exercises the dark feature using the Preview Token. It also runs the repository's own tests that apply to the release, and spot-checks that what was live before still works. Every check ends in one of four states, `passed`, `failed`, `blocked` or `not_run`, and only `passed` lets a change release (a check marked `passed` whose own evidence admits it was not observed, such as "unable to observe logs in production", counts as `not_run`, because the first real run on an unobservable requirement passed on exactly such a claim; for things not visible from outside the tester reports the repository's own test of it, or marks the check `not_run`); the tester also lists what it could not test or clean up (`limitations`). It works with tagged synthetic records, declares and avoids real side effects, stays bounded, and deletes what it created. On a first build with no flags it exercises the live app against the Intake spec instead. For HTTP checks the tester does not judge answers itself: it writes the requests and expectations (status, JSON subset, headers) as data and runs them with the Factory's `orchestrator/shared/api_check.py`, which observes, compares mechanically and logs every result; the Orchestrator then lets the helper's log outrank the report (a result citing a failed check cannot be `passed`, and a failure the report left out is added). The helper reads the Preview Token from its environment, scrubs it from the log and calls only the app's base URL. A route gated by a secret only the app holds (an API key) cannot be checked live, because the tester never holds it: when the app answers 401 or 403 to a check that did not expect that, the helper logs the check as `blocked`, not `failed`, so no coder round is spent on it. A result citing such a check stays `passed` only when its evidence names the check's id and a run of the repository's own test, otherwise it becomes `blocked` (a tester's `failed` on it too, since the helper only saw a refusal), and a blocked check the report left out is added as `blocked`; the run then stops for a person as above without the retest, because a refusal does not change on the same commit. `ui-check` sees no statuses, so a browser scenario that needs such a secret is `not_run` (run 40208653990 spent a whole Build Run on 21 such false failures). **Each result says what it is about**: `scope: new` (the flagged change, or a first build's spec) or `scope: existing` (behaviour that was live before). The Orchestrator derives what a failure means (`test_impact`): a failed `new` check is `dark_only` and is fixed forward; a failed `existing` check that an `api-check` or `ui-check` helper observed is a `regression` (the model's word alone is not enough). Only a check the tester saw **fail** goes to the coder: one that was `blocked` or `not_run` cannot be fixed by it, so the tester looks again at the same deployed commit (`limits.test_retries`, default 1) and a run that still cannot verify stops for a person as `needs_human`, with no coder round spent. Like the reviewer it also suggests `improvements`. Can't push. Runs on the pinned model.
- **Planner** (STEP 2.1): a read-only Agent that turns an Intake into requirements, assumptions, blocking questions and ordered change sets, each with its own acceptance criteria, verification and flag. `orchestrator/planning/validate_plan.py` is the deterministic gate on its plan: every requirement covered, dependencies acyclic, criteria and verification present, a flag per update change set, each change set sized S or M (L is split) with at most 6 criteria and no mention of another change set it does not depend on, a new app's first change set being the `staging` one, at most 8 change sets, and any blocking question sent to a person instead of guessed. Planning is its own process (`plan.yml`, `orchestrator/planning/plan_run.py`, switch `limits.planner_enabled`), started when an intake label is applied and before any coding, for a New App Intake as well as an Update App Intake: it files at least one child ticket per Intake, each a complete set of coding instructions sized so that one flag can roll it back (see [Intake](#intake)), and the Build Run never plans.
- **Pipeline Agent**: invoked only when CI or the deploy fails. Deterministic polling does the normal watching, so the happy path costs no tokens. It diagnoses from the failing run's logs and Fly status, which the Orchestrator gathers into files for it (it holds no GitHub or Fly credential), and hands a fix request back to the coder. It can't edit code or workflows.

**Stages, in one Build Run**
1. The coder commits to its local `main`. It runs `npm run format` first, then the build, type-check and tests (see `agents/prompts/coder.md`); the Orchestrator does not format. Before the reviewer sees the commit, the Orchestrator runs the app's own `npm run check` (type-check and lint) on it as the Agent user, read-only; a failure is a rejected commit that goes straight back to the coder (three attempts, like a protected-file violation) and costs no review, push or CI run. A formatting difference is not checked (it is not a gate) and the build and tests stay with the coder and CI (`limits.precheck`).
2. **The reviewer reads that commit before anything is pushed.** Blocking findings go back to the coder, and nothing reaches `main` or the deploy. A clean verdict lets the Orchestrator push (only the Orchestrator pushes, and only reviewed code).
3. CI, the build, and the deploy run (the Test Gate and workflows are unchanged). The new feature is **deployed dark** because its flag is off. Failures go to the Pipeline Agent; a fix it asks for is committed locally, **reviewed again**, and only then pushed. Bounded by the cost cap and time limit as before.
4. **The tester examines the deployed app** (dark, through the Preview Token) and says what a failure means. A `regression` ends the run at once (stage 6). Any other failure goes to the coder, who commits a fix that goes through stage 2 again, still dark. This loop is a fixed, configurable number of rounds, default **4** (`limits.review_rounds` in `agents/profiles.yml`); a round is one review, one test pass (only if the review was clean) and one fix commit. A blocked review costs a model call and a coder round and never pushes; a failed deployed test costs a push, CI, a deploy and a tester pass, so a second limit, `limits.test_rounds` (default **2**), stops the run for a person once that many deployed tests have failed. Unverified checks that are retested (`test_retries`) do not count against it.
5. **Release**: a deterministic Orchestrator step, never an Agent, switches on the story's flag (created off at the start of the run; the release step never creates one, see Flag stories) in GrowthBook, but only when all four hold for the pushed SHA: CI green, deploy healthy, the tester's preview run passed, and the reviewer's verdict clean. It then posts a "released" comment in the Managed App repo. Rolling back is the owner flipping the flag off in GrowthBook, or running the `Flag set` workflow (`flag-set.yml`, `orchestrator/flag_lifecycle/set_flag.py`: app, flag and on/off; it changes only the production switch of an existing flag and reads it back); the step leaves every flag that already exists exactly as it is, except the flag of the issue itself, which an earlier attempt of that same issue created, off. **Nothing is reverted in git; only a regression rolls the deploy back**: code is fixed forward and `main` keeps every commit. A change that only breaks itself is dark, because its flag is never released, so it harms no one; the story is fixed forward by a later attempt of the same issue, behind its own flag (a **dark feature**, below). The one exception is a **regression**: the tester saw, through a helper, behaviour that was live before the run stop working. The tester only notes it. The run ends as `regression` straight away (no more rounds on top of a regression) and `finalize` has **the app's own CI** put the live app back on the previous deployed version: it dispatches the app's `rollback-fly.yml` (a Starter Template workflow; template sync gives it to existing apps) for the run's starting commit, whose image the earlier deploy left in Fly's registry, waits for that run and for `/api/health`, and records it in the Report and Summary. A failed rollback is reported loudly (an audit finding, and the first requirement of the fix request). `limits.rollback_regressions` (default `true`) switches it off. The regressing commits stay in `main` behind a flag that is off, and the story is fixed forward (the `regression` route below); the retrospective adds each failed check the tester noted to the story's own issue as a note (no new issue), and the retry carries them as requirements. Until the fix lands, any other push to `main` would deploy the regressing version again, which the bug issue is there to prevent. **Dark features**: a flagged change that ran out of rounds, hit a cap or regressed stays dark behind its flag. Its story issue is labelled `dark-broken` (and `flag:<slug>`), which together with the App State issue is how dark features are tracked; `flags.json` is not used for this, because the coder writes it and every edit to it deploys. The story is fixed forward (see Fix first). When its fix attempts are used up (`fix_attempts_max` fix children) it is labelled `needs-human`; only then can a person add `approve-retire` to it, and `.github/workflows/approve-retire.yml` (`orchestrator/flag_lifecycle/approve_retire.py approve`) files one Update App Intake that deletes the flag, the code it guarded and its tests, and starts it. Nothing removes a dark feature on its own. **Rollback of a release**: the owner flips the flag off in GrowthBook or runs `Flag set`; the watchdog does it by itself. **Fix first, never retry the unchanged child** (STEP 6.2 to 7.5). The retrospective step handles each bad ending once, by the cause it named. A cause in the app (the code is wrong, the spec was ambiguous): the `fix` verdicts of one story are grouped (STEP 7.7) into one bug Intake, which is planned in code from its ticket's numbered requirements (STEP 2.7, no Planner call), and that files a **fix child**, an ordinary child with complete instructions and its own flag, filed under the bug Intake, and the failed child waits for it as one of its blockers; when the fix child closes, the failed child is started again. A cause in the Factory (prompt, planner, Starter Template, orchestrator): one `factory-fix-request` issue in ai-factory for a person to read and fix by hand (INV-14); nothing in the pipeline reads it, and the failed child is labelled `needs-human` until the person adds `proceed-with-change` again. No cause, or an infrastructure one: the child is labelled `needs-human` and nothing runs until the owner edits it and applies the label again. An unchanged child is never started again by itself, the chain is bounded (`fix_attempts_max`, 2), and a failed child stays open and blocks its siblings. The fix child goes through the same gates as any child and releases its own flag. When it closes, the failed child runs again behind the flag named after its own issue, which already exists, off, and `release()` switches it on only because it is the issue's own flag and the gates passed; every other existing flag is left alone. A release the watchdog switched off ends its child as failed, so it gets a bug Intake and waits for the fix like any failed child. A budget failure does not raise the cost cap for the fix (a story that could not finish inside it is too big for one pass; the fix child is told to do less), so a story costs at most the cap per attempt. **Watchdog**: after a release, the Orchestrator watches the app for `limits.watchdog_minutes` (default 10). Failed health checks in a row, or a rise in error-level log lines over what the app logged before the release, make it switch off the flags this run released (never one that already existed), read each back to confirm, and end the run as `watchdog_disabled`, which opens the usual Issue in the Managed App repo. The disable call and the read-back have not yet run against the real GrowthBook.
6. If the round limit (`limits.review_rounds`, counting review fixes and pipeline fixes together), cost cap, or time limit is hit first, the flag stays off, no release happens, nothing is reverted or rolled back (a flagged change is a dark feature), and a "needs human" or "budget exhausted" Issue is opened in the Managed App repo. Dark-by-default makes this the safe outcome, so no budget is reserved for later stages. One deterministic final step always writes the Summary and Issue even after a breach.

**Credentials**: Agents run as subprocesses with a whitelisted environment: their own scoped DeepInfra JWT, plus the Preview Token for the tester. They get none of the PAT, Fly token, DeepInfra parent key or GrowthBook admin key. **Agent isolation** (`limits.agent_isolation: user`, on since 2026-10-13): Agents run as a separate unprivileged account, so they cannot read the Orchestrator's process environment, the runner's workspace or its credential files, and each run proves this before any Agent starts (see Cost guardrails, Agent isolation). The retrospective Agent runs the same way (INV-45): as the Agent user, after the same self-check, in a copy of the Factory tree without `.git` that is deleted afterwards. It names a cause and judges events and changes nothing: no change it makes in its copy is carried back, and the Orchestrator runs no git inside a directory the Agent wrote to. No Agent holds the GrowthBook admin key. The key's scope isn't app-scoped (all Managed Apps share one project), so an Agent holding it could change any app's flags, and the release step is the gate the Agents are being checked against. Agents read flag state with the app's SDK key if they need to.

**Cost**: the goal is under $1 a Build Run. It is a target, not a cap (the cap stays `limits.cost_cap_usd_default`, $2): the dashboard counts runs over it and shows the 90th percentile. Measured on the first 32 runs the mean was $0.30 and the spend was driven by rounds and by failed Agent attempts, so a failed Agent now gets a stage in the Report with its cost, and an Agent that spent its whole credential without a usable file is not given a second attempt. All Agents draw on the Build Run's one cap. The "refuse the next turn" rule applies run-wide; there are no fixed per-Agent budgets. Agents run one at a time (the reviewer before the push, the tester after the deploy), so each is minted a credential limited to what is left of the cap when it starts, and the run-wide rule stops the next turn once the cap is spent (`Budget.mint` in `orchestrator/shared/spend_budget.py`).

**Retirement**: a proven flag is retired by the pipeline, riding along in the next Update App Intake's Build Run (INV-37, STEP 4.2); a dark feature is removed only when the owner adds `approve-retire` (INV-43). No Agent proposes either on its own.

## Model serving

Open-weight model inference is consumed via a pay-per-token API, not self-hosted GPU inference — Build Runs are bounded, not continuously GPU-saturated, so idle self-hosted cost would dominate.

**Provider: [DeepInfra](https://deepinfra.com).** Cheapest confirmed per-token price for the open-weight models used here. Runner-up: Together AI.

**Coder model: `deepseek-ai/DeepSeek-V4.1-Flash`**, switched from `Qwen/Qwen3-Coder-480B-A35B-Instruct-Turbo` after a smoke screen of seven models and a replay of two real recorded tasks (clean 6/6 against the Qwen's 0/6, about 18% faster per round, about 6x cheaper; results in `.wayfinder/coder-speed/tickets/14-*.md` and `15-*.md`). It missed one smoke task three times out of three, so `fix_model` in `profiles.yml` can route fix rounds to a stronger model if real runs stall. **Tester model: `nvidia/NVIDIA-Nemotron-3-Ultra-550B-A55B`**, switched from the 480B Qwen after the seeded-bug benchmark (`agents/smoke-tester/`): on the four edge-case bugs the Qwen mostly missed it caught 11 of 12 against 3 of 9, with no false alarms on the correct app, at about $0.147 a run against $0.11; it is a different lab from the DeepSeek coder and reviewer, so the tester stays independent of them. It has not yet been measured on the easy bugs, so a run that shows it missing those is a reason to switch back. **The Pipeline Agent and retrospective Agent** still run `Qwen/Qwen3-Coder-480B-A35B-Instruct-Turbo` (Apache 2.0), chosen as the cheapest confirmed price for a model trained for long tool-calling loops. **The planner** runs `openai/gpt-oss-120b` (fallback `Qwen/Qwen3.8-Flash`) since 2026-10-15: the 480B hung for minutes on real runs, a planner needs no code-tuned model, and gpt-oss-120b is about 8x cheaper and a different lab from the coder, reviewer and tester. It is unmeasured; watch the planner's time, cost and `plan_gap` lessons, and ticket 30 would benchmark it.

**Reviewer model: `deepseek-ai/DeepSeek-V4.1-Flash`** (issue #41), as a single-call reviewer (the Orchestrator assembles the diff, changed files, `INTAKE.md` and flag usage into one prompt) that falls back to the exploring Agent when the change is too big or the call fails. It replaced `deepseek-ai/DeepSeek-V4-Pro-0813` (the #25 pick: MIT, 1M context, $1.30 in / $2.60 out per 1M tokens), which spent 7 to 20 minutes per review in real Build Runs; Flash scored 50/50 on the smoke fixtures against Pro's 48/50 at about 10 s a review. The #25 reasoning, a different lab than the coder so a clean review isn't a shared blind spot, no longer holds while the coder is also DeepSeek-V4.1-Flash (see [Agents and Build Run stages](#agents-and-build-run-stages)). The smoke test for the #25 pick ([#33](https://github.com/ojones/ai-factory/issues/33), `agents/smoke/`): `usage.estimated_cost` is returned, tool calls and structured output work, it found all four seeded bugs (off-by-one, command injection, missing flag, flag default `true`) in 3 of 3 trials and passed a clean diff in 2 of 3 (one false positive), and it reviewed correctly end to end through OpenHands. A full 5-fixture, 3-trial pass costs about $0.02. No code-review benchmark covering open-weight models exists, so beyond this smoke test the quality case rests on owner-reported agentic-coding numbers.
→ [issue #25](https://github.com/ojones/ai-factory/issues/25), [research](https://github.com/ojones/ai-factory/blob/research/reviewer-model/.scratch/orchestrator-spec/research/reviewer-model.md)

**Models, prompts, and limits are config, not architecture.** Every per-role model, the provider endpoint, each role's prompt, and the review-round limit live in [agents/](agents/profiles.yml), so any of them can be switched or tuned without editing this document.
→ [issues/02](https://github.com/ojones/ai-factory/blob/archive/pre-purge-2026-10-21/.scratch/orchestrator-spec/issues/02-model-serving-api-not-selfhosted.md), [issues/08](https://github.com/ojones/ai-factory/blob/archive/pre-purge-2026-10-21/.scratch/orchestrator-spec/issues/08-which-model-provider.md)

A model is only eligible for a role if the provider serves it on an OpenAI-compatible API and returns per-response `usage.estimated_cost`, because the cost guardrail depends on that field; smoke-test a new model before pinning it. `agents/smoke/` (reviewer), `agents/smoke-coder/` and `agents/smoke-tester/` replay fixtures through the real prompts and score them as the Orchestrator would; rerun them after changing a prompt or model, with several trials per fixture because results vary a lot (`TRIALS` sets the count; CI's value is in `.github/workflows/factory-checks.yml`). `docs/benchmark-protocol.md` holds the whole-run benchmark that decides a model swap. `limits.review_rounds` bounds the Coder's rounds, review fixes and pipeline fixes together; the `limits.watchdog_*` values control the watch after a release (see Feature-flag infrastructure); both live in `profiles.yml`, and 0 turns either off.

## Orchestrator host

The Orchestrator runs as ephemeral compute during a Build Run, not an always-on service — pay only while a Build Run is active.

**Platform: GitHub Actions** (GitHub-hosted runners). Native scheduling (`on.schedule`), secrets, and run logging with zero extra infrastructure; clears the 6-hour-per-job duration bar for an overnight run. Runner-up: Fly Machines.

## Deploy target for Managed Apps

Deployment pins one default hosting target for v1 simplicity, but the mechanism must stay swappable per project — never hardcode an assumption the target is fixed forever.

**Default: [Fly.io](https://fly.io)**. Cheapest at low-traffic scale, lowest-friction GitHub Actions deploy flow. Runner-up: Railway.

**IaC approach: `fly.toml`** (checked into each Managed App's repo) as the sole declarative app-config, paired with a thin, checked-in, idempotent provisioning script for what it can't express (secrets, DNS/certs, registry auth). Fly's own current recommendation — their official Terraform provider is archived and un-recommended by Fly.io itself.

## Cost guardrails

The spec requires a budget cap + hard stop exist and are enforced; concrete dollar figures are build-time config, not part of this spec.

**Enforcement mechanism**: the cap covers LLM token spend only (not GitHub Actions minutes or other metered calls). DeepInfra refuses a spending-limited JWT that carries more than one model (HTTP 422, "multiple models is not compatible with spending_limit", found building #32), so each Agent invocation gets its own **single-model scoped JWT** (DeepInfra `POST /v1/scoped-jwt`) whose `spending_limit` is what is left of the run's cap. All Agents therefore still share one cap, and the Orchestrator meters the run as the sum of every JWT's spend. Each JWT is both enforcer and meter. DeepInfra refuses the first call after the limit is crossed with HTTP 403, `token spending limit exceeded`, while the call that crosses it still completes, which is exactly "finish the current turn, refuse the next". The Orchestrator reads each JWT's spend from `GET /v1/scoped-jwt?jwtoken=<jwt>` (`spending_current`, USD) after its Agent invocation, for the Summary and Report and to skip remaining stages once the cap is reached. Verified empirically ([#35](https://github.com/ojones/ai-factory/issues/35)): `spending_current` equalled the sum of per-response `usage.estimated_cost` with no lag. This replaces summing `usage.estimated_cost` per response, which OpenHands' headless mode can't supply, and the earlier account-wide usage diff, which can't separate concurrent runs.

**Model swaps**: the Factory swaps models as better, cheaper, faster or more specialised ones appear, and decides each swap by a measured whole-run pass, not by a guess (INV-41; `docs/benchmark-protocol.md`). `orchestrator/monitoring/benchmark.py` runs a fixed suite of seven Intakes (`agents/benchmark/suite.json`: a flagged route, an edge-case validation, an internal refactor, a named flag retirement, an ambiguous spec, and refusals of a payment request and a pasted secret) through the real `build-run.yml` against one disposable bench app that is forced back to a frozen commit before each task; a task is scored by code (the outcome it expects, its cost limit and `api_check` scenarios against the deployed app), and a pass is compared with the accepted baseline under `agents/benchmark/rules.json` (at most one task fewer passes, no safety or refusal task regressing, cost within 1.3x, rounds within +0.5; a candidate that holds those and costs or takes 0.9x or less is an improvement). A candidate is a branch whose `profiles.yml` names the new models (with limits pinned so passes stay comparable), dispatched from that branch so production code carries no benchmark mode. The `Benchmark` workflow is manual and dry-run by default; a pass costs about $0.60 to $3.20 and takes 1.4 to 3 hours. At run time each role may name a `fallback_model`: `BuildRun.check_models` asks the provider for one token from each model the run uses and swaps a missing one for its fallback (recorded as `fallbacks` in the Report) or stops with the reason, and a nightly canary (`canary.yml`) keeps one `model-drift` issue open while any configured model, primary or fallback, is missing. The canary ran once against the real provider (2026-10-14) and found all three distinct configured models, fallbacks included, served. The bench app, the baseline and the first pass are not created yet (`agents/benchmark/bench-app-spec.md`). **Intake triage**: two checks refuse a request before anything is built (`orchestrator/planning/triage.py`, INV-40). For an update, the planner also judges feasibility first (`feasibility` in its plan): a request that needs payments, a third-party secret or key, personal data, an outside keyed service or something outside Express, React and free dependencies is `blocked` with reasons, the plan has no change sets, and the run ends `refused` right after the planner call (about $0.04). Retiring a proven flag never costs a run of its own: it rides along in an Update App Intake's Build Run that is already coming in for the same app (`orchestrator/flag_lifecycle/retirement_selection.py`, `limits.flag_retirement`). Not for a fix child. Flags are built to be removed: one flag per change set, checked at one entry point with a string literal (coder prompt, reviewer rubric). The expectations are re-read for a few seconds before a scenario fails, because a page updates after a network call. If the tester writes no usable report but a helper saw something fail, the Orchestrator builds the report from the helpers' logs instead of stopping for a person. First live use (2026-10-13, a to-do page on `ojones-todo` behind a `todo-ui` flag): the first run failed because the helper read the page too early and the tester re-ran scenarios and debugged the app until it ran out; after the fixes a second run passed 10 scenarios and 15 checks for $0.30 and released. **Agent isolation** (`limits.agent_isolation: user`): the Orchestrator and its Agents used to run as one operating-system account, so an injected Agent could read the Orchestrator's process environment and files (the PAT, Fly token, GrowthBook admin key). A probe on a GitHub-hosted runner (`isolation-probe.yml`) showed that a different unprivileged account cannot read another account's `/proc/<pid>/environ`, the runner's home or the Actions files, but can read any process's command line, so the workflow creates an `agent` account, moves the Build Run's directories to `/srv/agent` (shared with the runner through ACLs) and every Agent starts through `sudo -n -u agent` with the whitelisted variables passed by name, so no value appears on a command line; the git credential likewise moved from `git -c http.extraheader=...` arguments to `GIT_CONFIG_*` environment variables. At the start of each run a self-check runs probes as the Agent account (is it another account, can it read a marker process's environment or the workspace, does its environment hold credential variables, can it sudo) and the run stops if any fails. A timed-out or silent Agent is killed through sudo by process group. Not covered: an Agent is not stopped from reading what its own account can read, such as the app checkout. All Agents share the one `agent` account, so after each Agent finishes the Orchestrator moves that Agent's home directory (its conversation events, which can hold the Preview Token the tester echoed) to `$RUNNER_TEMP/sealed-agent-homes`, inside the runner's closed home, and sets its `openhands-<role>-<label>*` logs in the artifacts directory to mode 600, so a later Agent cannot read an earlier Agent's work (issue #168). The first real run (40240362733) showed the move failing with a `PermissionError`: the ACL mask on directories the Agent creates leaves the runner without write access, and moving a directory needs it. The Orchestrator now takes ownership first (`sudo -n chown -R`) and then moves; a move that still fails is logged and the run goes on. Not yet re-run on a real runner. The same pass removes the run's credential and any `TOKEN`, `SECRET` or `KEY` value it passed the Agent from the uploaded `openhands-*` logs, because the tester once echoed the Preview Token into its log and the artifacts of a public repo are downloadable. The Factory's own source is public, so an Agent can still clone it; that is not a secret. **Silent Agents**: an Agent's `--json` event stream grows at every step, so one whose stream has not grown for `limits.agent_stall_minutes` (8) is killed with its whole process group and counts as a failed attempt, instead of holding the run for the full `agent_timeout_minutes` (45). A coder that uses the whole `agent_timeout_minutes` without an acceptable commit is not started again (a second attempt would only repeat it): the run stops for a person. Run 40208653990 (opinion-spectrum, 2026-10-25) spent three full 45-minute attempts, 2h15m, that way; the stall rule did not fire during a 27-minute gap in one of them, and why is not yet known. The first production-feedback Build Run lost 90 minutes to two coder starts that did nothing for the full timeout. **Provider out of balance**: when the model provider answers HTTP 402 ("You need positive balance to do inference"), every request fails until someone tops up, and anything that reacts to those failures would only fail the same way. Each Build Run therefore starts with a one-token preflight to the provider; the same refusal is recognised when minting a credential, in the single-call reviewer, and in an Agent's own error event. The run stops at once as `provider_blocked`, leaves anything it had already pushed as it is (fixed forward, never reverted), and files **one** deduplicated alert in ai-factory (`provider-blocked`, `needs-human`) asking for a top-up, with the label to re-add afterwards. No fix request, lesson, self-starting retry or retrospective Agent is started. **Daily cap**: each finished Build Run adds one line (`ledger <date> <app> <usd> run:<id>`) as a comment on the `factory-ledger` issue in ai-factory, and a new Build Run refuses to start once today's lines (UTC) reach `limits.daily_cost_cap_usd` (default $10, 0 disables). Runs still in flight are counted only when they finish, so concurrent runs can overshoot by their own caps. The retrospective Agent has its own per-analysis cap (`retrospective_cost_cap_usd`), and what it actually spent is added to the same ledger (as `retrospective`, with its own run id so it is not mistaken for the run's line); the planner runs inside the Build Run's budget, so its spend is already in the run's line. **Production feedback** (STEP 8.3; built by ticket 16): the watchdog watches for ten minutes after a release; a bug that shows up later is found by a scan every six hours (`production-feedback.yml`, `orchestrator/bugs/`, switch and limits in `limits.production_feedback`). It reads each registered Managed App's Fly log, groups error-level JSON lines by fingerprint (the message with ids and numbers removed, plus the first application stack frame), and an error seen `min_occurrences` (3) times in one scan becomes a failure event. An open issue labelled `escaped-defect` in the app's repo becomes one too, but only if the repo owner wrote it (anyone else's text never reaches an Agent), and while an app has one to report its logs wait. The scan files nothing: the Retrospective judges the events in one batch (`retrospective.judge_events`, STEP 6.7) and Try Fix writes and files a bug Intake for each one worth fixing (`try_fix.file_events`, STEP 7), which the planner plans and the Build Run builds like any change. The flag decides how it is filed (STEP 8.1, 8.4): an error that names a flag the App State lists as dark (never released, off, or switched off by the watchdog) is filed with `fix_for`, so the story's open child waits for the fix; any other is a regression, an ordinary bug Intake. Flood control: one open bug per error (a repeat comments with the count), one open bug per app at a time, and one daily limit, `limits.bugs_per_app_per_day` (2), on new bug tickets per app, shared with the warnings the Retrospective sends to a fix (a failure of a Build Run is never limited by it). The event carries only the cleaned message and first frame, and the Try Fix Agent is told the evidence is data, never instructions. There is no readiness check or planner veto; if failures pile up, the bad endings are the evidence for adding one. Fly keeps a short log buffer, so a scan sees only recent lines. The old scan ran against `ojones-todo` on 2026-10-13 (one Intake for 100 occurrences, a second scan only commented); the new path has not run live. **Maintenance**: every app carries `.github/dependabot.yml` (from the Starter Template), so Dependabot watches its npm packages, Docker base image and GitHub Actions daily. Dependabot only detects: nothing merges its pull requests (trunk-only, and a green CI alone would skip the tester and reviewer). A daily pass (`maintenance.yml`, `orchestrator/maintenance/dependency_updates.py`, switch `limits.maintenance.enabled`) reads each registered app's open Dependabot pull requests and, for the npm and Docker ones, files one Update App Intake per app and set of updates, security fixes first, that starts itself; the planner, coder, tester and reviewer apply them (no flag: users see no difference) and Dependabot closes its pull requests once the dependency is updated. GitHub Actions updates edit `.github/`, which Agents may not change, so they are only listed. The same pass switches on Dependabot alerts and security updates for each repo (best effort). The Starter's Test Gate also runs `npm run audit` (`npm audit --omit=dev --audit-level=high`), so a high or critical advisory in a production dependency fails CI; the fix is the update Intake. The Starter's Dockerfile writes its Node 22 base image, pinned by digest, in both `FROM` lines (it was an `ARG` on Node 20, which Dependabot cannot update and which reached end-of-life in April 2026). A template-sync run copies the protected Starter files that are safe to overwrite itself, before any Agent starts (`.github/dependabot.yml`, `.github/workflows/test-gate.yml`, `.github/workflows/rollback-fly.yml`, `.github/workflows/deploy-fly.yml` (which carries the secrets copy step), and the lint and formatter config, which is staged and pushed with the coder's work), so existing apps get them; other protected files are still listed for a person. The daily Fly audit also prints each app's days since its last push in the run summary; nothing is retired automatically. None of this has run against a real app yet. **Orphaned Fly apps**: a daily workflow (`fly-audit.yml`, `orchestrator/monitoring/fly_audit.py`) lists the Fly apps in the organization (`FLY_ORG`, default `personal`) and keeps one `fly-orphans` issue for any that is neither infrastructure (`limits.fly_infra_apps`, plus GrowthBook) nor a Managed App with a Factory-marked repo, because those bill for machines nothing will stop. It deletes nothing. The Fly list call (`GET api.machines.dev/v1/apps?org_slug=`) ran once against the real account (2026-10-13) and reported no orphans; whether it saw every app is not yet confirmed.

**Worst-case overshoot** is one call's cost, because the crossing call completes (normally fractions of a cent; a very large-context call to the reviewer model could be a few tenths of a dollar). The DeepInfra account-level spend cap remains the last-resort ceiling. Each JWT is masked in logs, lives in the single Build Run job, and expires after the configured lifetime (default 6 hours, the Actions job limit); a compromised dependency in an Agent's environment could spend at most the JWT's remaining budget on that role's model.

**Numbers are config** in `agents/profiles.yml` (`limits`): the default cap (**$2.00**), the ceiling an Intake override may request (**$10.00**, enforced at Intake), and the JWT lifetime. They are starting values to revise after the first real multi-agent run.

## Visibility

A minimum observability/reporting requirement for unattended Build Runs is part of the architecture.

**Mechanism**: a **Build Run Summary** written to `GITHUB_STEP_SUMMARY` (status, what changed, test results, cost spent, deploy outcome + a link to that deployment's Fly log viewer). The raw OpenHands `--json` JSONL event stream is uploaded as a build artifact for deep-dive debugging. A curated, machine-readable **Build Run Report** (same fields as the Summary) is produced alongside it for future tooling. The Summary also leads with the verification counts for the last round, its limitations, and a per-round scoreboard (checks passed / failed / blocked / not run, and open blocking findings); the same data is in the Report and in `artifacts/progress.json`. The Summary has a row per stage (Agent, rounds used, cost, verdict, and the context numbers below) plus the release outcome, and each Agent invocation uploads its own JSONL artifact; the Report carries the same fields. **OpenHands is pinned in `agents/openhands-version.txt` (installed by every workflow that runs it), so an upstream release cannot change the CLI under an unattended run; changing the pin is a deliberate edit, tested with the smoke and replay suites first. **Tracing is off on purpose:** an experiment with `openhands` 1.16.0 (SDK 1.21.0) found that setting the `OTEL_EXPORTER_OTLP_*` variables does export spans to an OTLP endpoint, but the run then failed in the SDK's tracing code (`observe() got an unexpected keyword argument 'rollout_entrypoint'`) before making a model call, while the same run without the variables worked. Revisit with a newer pin. The same experiment confirmed the CLI will talk to any OpenAI-compatible endpoint set in `LLM_BASE_URL`, so a local stub model can stand in for DeepInfra in orchestration tests. **Context tracking**: each Agent invocation is one fresh LLM conversation, and the Orchestrator reads OpenHands' persisted state after it to record LLM calls, input (and cached) and output tokens, condenser calls, and the **peak context**, the largest prompt in any single call. The Summary shows these per stage and the run's highest peak; `limits.context_goal_tokens` in `agents/profiles.yml` (100,000) is a goal, not a limit, and stages over it are flagged. First measurement ([#32](https://github.com/ojones/ai-factory/issues/32), a small notes API): peaks of 29k to 54k, the coder highest. If peaks cross the goal on real Intakes, the planned response is to split the coder into planned steps, each its own invocation. On failure — a crash, the cost/time budget exhausted before CI went green, or the review-round limit reached without a clean verdict — an explicit workflow step auto-creates a GitHub Issue in the Managed App's repo, distinguishing which.

## Secrets

A request that needs a third-party secret (an API key, a signing secret) is not refused. The planner lists each as `secrets: [{name, purpose, read_by}]` (names like `OPENWEATHER_API_KEY`, never one of the Factory's own), and planning never waits for them: it files the children and comments each name as a heads-up. Nothing builds until every name exists as a GitHub Actions secret on the app's own repository: the Build Run stops as `awaiting_secret` at its start. It is an answer, not a failure (like `refused`, `ANSWERED_ENDINGS`): nothing is retried or learned from, and the Intake stays open. The comment gives each name and the exact `gh secret set NAME -R owner/app` command; the command prompts for the value, so it never appears in an issue, comment, commit, log or artifact. The declared names are recorded on the Intake (a hidden `factory-secrets` marker in a comment, and in each child issue's plan metadata), and **every later start checks them first**, in `setup`, before the planner, coder, reviewer or tester is paid for: a re-run, a retry and each child of a plan all stop as `awaiting_secret` if a name is missing (`gh secret list`, names only). The only spend before the first check is the planner call that discovers the need (about $0.05), because nothing can know sooner; a check in planning would save no model call, since the start of a Build Run is already before any Agent. The coder is told the secrets exist as `process.env.<NAME>`, reads each in one place, fails closed, and lists names and purposes (no values) in `secrets.json`; the Orchestrator rejects a commit that adds a real secret value (it is discarded, never pushed) or lists a name that breaks the name rules or is one of the Factory's own. The Starter's protected deploy workflow copies only the names in `secrets.json` to Fly, through stdin, in the deploy job alone, refuses the Factory's own names and fails if a value is missing. The workflow lists each declared secret as an ordinary `NAME: ${{ secrets.NAME }}` line between two markers, written by the Orchestrator (`wire_secrets`, committed locally before the coder starts and pushed with its work, and kept when template sync copies the file over); it never reads the whole `secrets` context, because GitHub flags such a workflow as possibly malicious and refuses to run it until a person approves (found live on 2026-10-15). A new app has no repository when it is planned, so its planning comment says the names will be needed; the staging check (STEP 3.2) reads only the Factory's own staging secrets, and the first Build Run of a business child is the first to look for the declared names. A keyed service the request names without a provider is the planner's choice of one free-tier provider, recorded as an assumption. App Staging switches on GitHub's secret scanning with push protection. A pasted value in an Intake is still refused at the start (INV-40). Residual risk, accepted: the app's own code holds the value at runtime, so the reviewer rubric limits a secret to the call that uses it. Built, not yet seen live (the diagram "finding and adding keys" in [flow-spec.md](docs/flow-spec.md)): a key only the Coder discovers is listed in `secrets.json` like any other and the Coder carries on; the Orchestrator accepts a valid undeclared name instead of rejecting it, adds it to the ticket's list (a `factory-secrets` comment on the child ticket being run, which a re-run reads), and checks the names once more after each Coder round and before the Reviewer, so a missing one ends `awaiting_secret` (an owner wait, never a failure) before the Reviewer is paid for or anything is pushed or deployed. Not built yet: the scan of artifacts before upload, and the daily pass for secrets older than 90 days and orphans (ticket 31). INV-48 to INV-50.

## Learning loop

Every Build Run, released or not, is a chance to improve the system, not only to alert someone. `orchestrator/retrospective/` (the **retrospective**; it replaced the post-mortem, which ran only after bad endings) runs as its own workflow step after `finalize` (`if: always()`) and never fails the run:

1. **Facts**: a deterministic record of the run (outcome, per-round blocking findings and which recurred, time and cost per stage, the improvements the reviewer and tester suggested), uploaded as `retrospective-facts.json`.
2. **Lesson issue**: one `factory-learning` issue in ai-factory per distinct failure. The title carries a fingerprint (outcome plus the first meaningful words of the recurring findings) so a repeat comments on the open issue ("Happened again") instead of opening a new one. Each open minor finding also becomes a `factory-learning` issue in ai-factory.
3. **Bugs and improvements**: the tester only notes which checks failed (`bugs`). They belong to the Managed App's own story, so the retrospective adds them to the Update App Intake that started the run (a comment, the `bug` label) instead of opening an issue, and the fix that follows carries the bugs among its requirements. Only a Factory-side cause opens a new issue. The reviewer and tester each also end their JSON with `improvements` (target `managed_app` or `factory`, a one-line summary, evidence). They only suggest. The retrospective files the `factory` ones as `factory-learning` issues, capped per run; a `managed_app` one is judged as a failure event and no suggestion issue is filed in the app's repo. **Before opening any issue it looks at the open ones**: a title that shares most of its content words with an open issue (`similar_open_issue`, reworded repeats still match) gets a comment with the new context instead of a duplicate. Having the Orchestrator file them keeps the run short (the Agents make no extra calls and hold no GitHub credential) and keeps a noisy model from flooding the trackers.
4. **Retrospective Agent** (`agents/prompts/retrospective.md`): runs when the run ended badly or a severe lesson was recorded. It names a root-cause category (`prompt_gap`, `template_gap`, `orchestrator_gap`, `plan_gap` (the planner split or classified a change wrongly), `spec_ambiguity`, `model_limit`, `infra`, `unknown`) and judges each event of the run (failure or warning, verdict `fix` or `record`, target, cause). It reads the Factory and changes nothing, holds no credential and runs outside the Build Run's cost cap, bounded by `retrospective_timeout_minutes`. Warnings the Agent did not judge are judged by one model call instead.
5. **A fix for the Factory is a person's job.** When a verdict is `fix` and the cause is a Factory one (`orchestrator_gap`, `prompt_gap`, `template_gap`, `plan_gap`), the Try Fix Agent writes the bug ticket (cause, target, reason, how it was found, numbered checkable requirements) and the Orchestrator files it as one `factory-fix-request` issue in ai-factory (STEP 7.2); each repeat of the same fingerprint is a "Failed again" comment, which is the sighting count. That is where the pipeline stops: nothing reads the label, no Agent plans or changes the Factory, and a person fixes it by hand in an ordinary pull request (INV-14). The failed child waits for that person (`needs-human`) and starts again when they add `proceed-with-change`.
6. **Report on the story**: a short summary (outcome, passes and cost, dark feature or regression, what was filed) is commented on the issue that started the run, once per run, whether it released or not.

The "no branches, no PRs" rule in [Git workflow](#git-workflow) applies to Managed Apps only; in the Factory repo itself, Markdown goes straight to `main` and code, workflows and config go through PRs (see CLAUDE.md).

**Built since** (unit-tested; none of the GitHub, Agent or workflow parts has run live):
- **More lessons than stuck runs.** `lessons_from` also records a release the watchdog switched off, a clean run that needed 3 or more review passes, a first test pass the coder had to fix, a run that spent 70% or more of its cap, and a stage over 15 minutes, at most 3 per run, each a `factory-learning` issue with a stable fingerprint.
- **Fix ineffective.** A lesson whose issue was closed and comes back is reopened with the `fix-ineffective` label and a comment saying so, for the person who closed it.
- **Credential and cap.** The Agent gets its own single-model credential limited to `retrospective_cost_cap_usd` (default $0.50) and never the parent key.

**Template sync**: an app is seeded once, so each app carries `.factory-template`, the ai-factory commit its template files correspond to (App Staging writes it; an older app has none, so the commit current when its repo was created is used). When `templates/starter/` has changed since an app was synced (a nightly pass at 07:47 UTC or a manual run of `template-sync.yml`, `orchestrator/maintenance/template_sync.py`; a merge to `main` does not start it), one Update App Intake per behind app is filed with the template's own diff and started at once. The coder applies it to the corresponding files, keeps the app's own code, merges by intent where the app changed the same file, and writes the new commit into `.factory-template`. It needs no flag (tooling users cannot see). Files an Agent may not change (`.github/`, `fly.toml`, `fly/`, `feature-flags.ts`; the lint and formatter config is copied by the Orchestrator) are listed in the Intake as not applied, for a person; `package-lock.json` is regenerated, not diffed. One Intake per app and target commit (a failed one is not refiled; its fix request follows the usual chain), one open at a time per app. It has not yet run against a real app. **Not built yet:** a weekly pass that clusters near-duplicate lessons (the fingerprint is the first six meaningful words) and counts distinct runs and apps.

## Intake

A person, or an automated source, asks the Factory for work with an **Intake**: a GitHub issue on this repo (ai-factory) that is the **parent** of everything that follows. (STEP 1.1 to 2.6):

**Two kinds of Intake.** A **New App Intake** (STEP 1.1; label `new-app-intake`; form `.github/ISSUE_TEMPLATE/new-app-intake.yml`) is titled the Managed App's name (kebab-cased for the eventual repo name) and carries a free-text description of what to build (the Intake Spec) and an optional cost-cap override (defaults to the standard per-Build-Run cap and may not exceed the configured ceiling). An **Update App Intake** (STEP 1.2; label `update-app-intake`; form `update-app-intake.yml`) names the app, what should change and an optional cost cap. The automated sources file the same Update App Intake with the PAT (STEP 1.3): template sync, maintenance, flag retirement and the bug tickets Try Fix writes, and `approve-retire` for a dark feature. The submitter edits and discusses the issue freely until it is ready.

**Planning starts when the label is applied** (STEP 2.1). There is no separate start label for planning: a form applies its label when the issue is created, which fires `issues: labeled` (checked in ticket 01), and an automated source applies it with the PAT, because a label set with the Actions token starts no workflow. `plan.yml` plans for both kinds: a New App Intake from its spec alone (no repo exists yet), an Update App Intake from the app's code. It ends in one of three ways. **Refused** (STEP 2.2): the comment says why and what could be built instead. **Stopped for a person** (STEP 2.3): a blocking question, a plan `planning/validate_plan.py` rejects, or a missing secret; the comment says what to fix, and the retry is to edit the issue, remove the label and apply it again. **Planned** (STEP 2.4). Planning is idempotent: a parent that already has children is not planned again, and a failed planning leaves the parent re-plannable and files no orphan children.

**Child tickets** (STEP 2.4). A plan is filed as one child per change set, as GitHub sub-issues of the parent (create the issue, then add it by its numeric id; a child has exactly one parent). Each child's body is a complete set of coding instructions: the task, numbered acceptance criteria, how each is verified, what is out of scope, whether it is internal only and the secrets it needs. Its `factory-plan` marker records its `kind` (`staging` or `update`), the flag story number, its `size` (`S` or `M`; a larger change set is split) and what it depends on. Order is expressed with GitHub's native issue dependencies; a child is ready when every blocker is closed, which is checked from each blocker's state, never from the count. A change set is the smallest slice that is independently releasable and independently reverted by flipping one flag; none works only while another's flag is on; data changes are additive. At least one child is always filed. A Build Run reads its child (and, from the parent, only its number for the repo marker and the comments), and `proceed-with-change` is only ever put on a child whose body has a marker.

**The first child of a new app is the staging child** (STEP 3.1, 3.2): `kind: staging`, no flag and no business logic. Its criteria, in order: the repo is created from the Starter Template and CI is green; the deploy is healthy on Fly; the feature-flag service is connected (GrowthBook has the app's own SDK connection); the Preview Token path works; the Factory's staging secrets are present; a boot and health smoke test passes. Every business-logic child depends on it and carries its own flag. App Staging runs when `proceed-with-change` is put on the staging child.

**Failure to fix (STEP 6.2, 6.7, 7.x; built by tickets 15b to 15d, the Bugs domain 8.x by ticket 16).** Every failure and warning becomes a failure event. The Retrospective alone names the cause and target and gives each event a verdict, `fix` or `record`; a scan with no Build Run is judged in one batch. For each `fix` the Try Fix Agent (built, ticket 15c) writes one bug ticket from the bug template (how it was found, root cause, what it takes to resolve, checkable requirements); it never decides the cause and never plans, its answer is validated (or the Orchestrator writes the text itself), and nothing secret-shaped from a log reaches it or the public ticket. The ticket is filed as an Intake and the planner plans it: an app fix is an `update-app-intake` labelled `bug`, a Factory fix is the same template in ai-factory. A failure of a child that is still open gets the failure as a comment on its story and a bug Intake with `fix_for`, planned as exactly one child that the failed child waits for; a bug in a story that is already released waits for nothing: it is a regression, an ordinary bug Intake, and the story gets a comment linking it. Attempts are counted along the `fix_for` chain, `fix_attempts_max` (2), then `needs-human`. The full rule is in [docs/flow-spec.md](docs/flow-spec.md), "From a failure to a fix".

**Hand-off is automatic, one child at a time** (STEP 2.5, 6.3). The planner puts `proceed-with-change` on the first child with no dependencies. When a child's Build Run succeeds, `finalize` closes it (STEP 6.1) and the Orchestrator, with the PAT, gives `proceed-with-change` to the next open `waiting-on-plan` child whose GitHub blockers are all closed (`retrospective/close_child.py`), so an app never has two pending Build Runs (GitHub keeps only one pending run per concurrency group). A failed child stays open without a start label, and while it does no sibling starts (STEP 4.14; the retry is adding the label again). The Orchestrator closes the parent when its last child closes (STEP 6.4); GitHub does not close a parent by itself. Fix children (STEP 7.1) are inserted ahead of the failed child by the same rules.

**How it runs.** Submitting either form applies its label, which starts `.github/workflows/plan.yml` (`orchestrator/planning/plan_run.py`): for an Update App Intake it refuses unless the app's repo exists and carries the `Intake: <factory repo>#<n>` marker App Staging wrote; it asks the planner, checks the plan (`planning/validate_plan.py`) and files the child tickets. `proceed-with-change` goes to the first child with nothing to wait for and `waiting-on-plan` to the rest. A staging child is staged by `.github/workflows/app-staging.yml`; any other child is started by `.github/workflows/update-app-intake.yml` (`build_run/start_build.py`), which refuses anything that is not a planned child of an open plan, and `retrospective/close_child.py` starts the next child when one finishes. Planning can be switched off with `limits.planner_enabled: false`. The labels are added with the PAT, because events made by the Actions token do not start workflows. Seen live on `factory-bench` (ai-factory#140 and #145, 2026-10-20).

Still open: nothing yet stops a second `proceed-with-change` on an issue whose Build Run is already running; the second run queues behind it and re-does the work. Requirements (`REQ-n`) and the numbered acceptance criteria are only as good as the planner makes them; Intake triage and an owner-confirmed criteria echo are an open ticket.

**Parallel apps, built but off.** How many Managed Apps run at once is one setting, `max_simultaneous_build_runs` in `agents/profiles.yml` (default and fallback 1), read by both `infra/app-staging/stage.sh` and the Build Run's wait loop; raising it lets that many apps through Intake → App Staging → Build Run together, still one writer per app (the workflow's `concurrency: build-run-<app>`). Do not raise it before Agents run as a separate OS user (a known gap above, open ticket) and before queued runs stop being dropped (open ticket: GitHub keeps one pending run per concurrency group). Every Intake that reaches staging gets an `app:<slug>` label, and after each Build Run the Orchestrator rewrites a pinned **App State issue** in the Managed App repo (recent runs, every flag a run released and its state as of the release) and a **registry issue** in ai-factory (one row per app, linking each State issue); these are issues rather than files on `main` so they never trigger a deploy. Not yet built: requirements (`REQ-n`) and acceptance criteria in the State issue, which wait on Intake triage. Plan and tickets: [.wayfinder/orchestrator-hardening/](.wayfinder/orchestrator-hardening/map.md).
→ [issue #17](https://github.com/ojones/ai-factory/issues/17)

## Deployment provisioning

**App Staging** creates only the baseline of a new Managed App — repo, seeded code, secrets — then hands off. Coding, review, and deployment all happen afterward, in Build Runs.

**Credential: one fine-grained personal access token**, scoped to the owner's personal GitHub account with **no expiration**, stored as an Actions secret in ai-factory. A GitHub App installation was the earlier pin but cannot work: installation tokens get `403 Resource not accessible by integration` on `POST /user/repos` for personal accounts, so repo creation — the first step of every App Staging run — is blocked (findings: [issue #20](https://github.com/ojones/ai-factory/issues/20)). The PAT must cover repository creation, contents, workflows (to push the seeded `.github/workflows/` files), secrets write, and actions (to dispatch); confirmed working end to end in App Staging (issue #31): repo creation, secrets write, a contents push that includes `.github/workflows/`, and a workflow dispatch. A fine-grained PAT cannot be created or rotated by API, so changing it is a manual step. **Accepted tradeoff:** repo creation forces "All repositories" scope, so the PAT can also write secrets in ai-factory and any other repo the owner has. A separate dedicated GitHub account to contain this was considered and rejected for v1 (one owner; extra identity to maintain). A GitHub org (which would make the App route work) was rejected for the same setup-cost reason; revisit if collaborators are added.

**Repos**: public, under the owner's personal account, named from the Intake issue title. Public means unlimited Actions minutes and plain GHCR pulls.

**Seeding**: the Starter Template stays in this monorepo at `templates/starter/` as the single source of truth — no separate template repo. App Staging creates an empty repo, writes the tracked files of `templates/starter/` (via `git archive`, never the working directory, so ignored files like `node_modules` can't leak in), adds `INTAKE.md` (the Intake Spec as submitted, a link to the Intake issue, and the cost cap used — a snapshot, never edited afterward), and makes one initial commit.

**Secrets pushed into the new repo**: `FLY_API_TOKEN` (the single shared Fly org-level token), `GROWTHBOOK_CLIENT_KEY` (see [Feature-flag infrastructure](#feature-flag-infrastructure)), and `PREVIEW_TOKEN`. The preview token is derived as `HMAC(master secret held in ai-factory, app slug)` rather than stored per app, because GitHub secrets are write-only: the Build Run recomputes it to exercise a dark feature, with no per-app storage. No DeepInfra credential is pushed: the Build Run workflow lives in ai-factory, checks out the Managed App repo with the PAT, and mints each run's capped credential in the same job, so the DeepInfra parent key never leaves ai-factory and never reaches an agent's environment.

**Fly app**: not created by App Staging. `fly/provision.sh` creates it idempotently on first deploy, deriving the name from the repo name. Fly app names are unique across all of Fly, not just this account, so a common name can already be taken by a stranger and the first deploy would fail mid-Build Run. App Staging therefore checks the name up front with a read-only call to the Fly Machines API (`GET /v1/apps/<name>`: 200 ours, 404 free, 403 taken by someone else) and refuses on a collision, before creating the repo or anything else; the Intake Issue Form warns about this too ([Deployment contents of a Managed App](#starter-template-contents-workflows-and-fly-config)).

**Idempotency**: every step is check-then-act, so App Staging is safely re-runnable after a partial failure (by re-adding `proceed-with-change` to the staging child). Repo ownership is proven by a marker in the repo description, `Intake: ojones/ai-factory#<N>`, `<N>` the parent Intake. A rerun adopts an existing repo only if the marker matches that Intake; any other pre-existing repo with that name (including `ai-factory` itself) is a hard stop, with an explanatory comment on the Intake issue, and nothing is ever overwritten. Any failed or refused run comments on the staging child and removes its start label (`proceed-with-change`), since re-adding a label that is still present would not fire the workflow. The seed push is also the first deploy: it triggers the new repo's Test Gate and Build (in parallel), then Deploy once both are green, so its secrets are created first.

**Teardown**: the manual `Teardown` workflow (`infra/app-staging/teardown.sh`, `workflow_dispatch`, dry run by default) removes one Managed App: destroys its Fly app, revokes its GrowthBook SDK connection, deletes its GHCR package (deleting a repo leaves the package, and a restage under the same name is then denied its first push; the call needs the classic `delete:packages` scope, so with a fine-grained token the row says the package must be deleted by hand) and deletes its repo (the fine-grained `FACTORY_PAT` needs the Administration: read and write repository permission). It refuses any repo whose description lacks the Intake marker, and refuses while a Build Run is in flight. GrowthBook's REST API cannot delete flags, so the script archives each of the app's `<app>.*` flags with an update call (they remain in the project, archived). The run ends with a table of outcomes per resource. Nothing runs it automatically; the project skill `.claude/skills/teardown-managed-app/` tells an agent how to drive it, always with per-app confirmation from the user.

**Handoff**: after the seed push, `orchestrator/staging/verify_infrastructure.py` proves the app works (CI green on the seed commit, healthy deploy, the flag-service connection, the Preview Token cookie, the staging secrets set, the front page served; INV-57). A missing staging secret fails the check; the app's declared secrets are not looked at here (the Build Run checks them, INV-48). Only then does `stage.sh` comment the repo link on the parent Intake (it stays open) and close the staging child, which starts the first business child (`retrospective/close_child.py`); the parent closes when its last child closes (STEP 6.4). No Build Run is started for the staging child. A failed check is a failure event (source `staging`): `stage.sh` has the Retrospective judge it (`retrospective/judge_events.py`) and Try Fix file it (`try_fix/file_events.py`), by default as a fix request for the Factory, since the seed is the unmodified Starter Template.
→ [issue #20](https://github.com/ojones/ai-factory/issues/20), [issue #23](https://github.com/ojones/ai-factory/issues/23)

## Feature-flag infrastructure

**Tool: [GrowthBook](https://www.growthbook.io)** (MIT core), with Managed App code written against **OpenFeature** rather than GrowthBook's SDK directly. Runner-up: Unleash.
→ [issues/16](https://github.com/ojones/ai-factory/blob/archive/pre-purge-2026-10-21/.scratch/orchestrator-spec/issues/16-which-feature-flag-tool.md)

**Hosting**: one shared, always-on GrowthBook instance — not one per Managed App — backed by a managed MongoDB Atlas free-tier cluster (GrowthBook requires MongoDB, not Postgres). The Orchestrator holds one manually-created, admin-scoped GrowthBook Personal Access Token (a one-time setup exception to full automation, since GrowthBook's API can't create admin keys itself).

**Per-Managed-App isolation**: self-hosted GrowthBook's free/OSS tier caps at 1 project per organization — confirmed empirically (`402` on a second `POST /v1/projects` call) and corroborated by GrowthBook's own pricing page. Every Managed App shares that one project; App Staging no longer creates a project per app. Multi-org mode (`IS_MULTI_ORG`) was considered and rejected: its self-hosted licensing status is unresolved in GrowthBook's own docs (described as a free env var, yet "Multi-tenant Mode" is marketed Self-Hosted-Enterprise-only), and — decisively — GrowthBook exposes no REST API to create organizations programmatically, only a manual/UI join flow, which would break one-call automation regardless of licensing. Paid Self-Hosted Enterprise was rejected as sales-quote-only with no disclosed price. Running a separate GrowthBook instance per Managed App was rejected: the Factory wants one shared data source, and per-app instances aren't free (each needs its own running service + MongoDB cluster). Switching feature-flag tools entirely was rejected too: every other self-hostable OSS alternative (Unleash, Flagsmith, PostHog) converges on the same 1-project-per-free-instance cap, and the one exception found (Flipt) carries a non-OSI "Fair Source" license, a worse tradeoff than GrowthBook's MIT core plus this app-naming workaround. → [Decide GrowthBook per-Managed-App flag isolation (#22)](https://github.com/ojones/ai-factory/issues/22).

Isolation between Managed Apps is therefore by **flag-key naming only**, not by any GrowthBook access boundary — every Managed App's SDK connection key can technically fetch every other app's flag payload. This is an accepted tradeoff for this personal project, not an oversight. See [Code wiring](#code-wiring) for the naming convention this forces.

During App Staging, the Orchestrator calls GrowthBook's REST API once to create an app-scoped, read-only SDK connection key, named for the app, against the single shared project (no project creation call anymore), and pushes it into the new repo's secrets alongside the Fly token. On a rerun after a partial failure, any existing key with that name is revoked and a fresh one minted and re-pushed. There is no app-wide kill switch: the lever is the flag of the change (see Feature-flag infrastructure). One key per Managed App is still minted — it buys no isolation, but keeps revocation, rotation, and GrowthBook's own per-connection usage view organized per app.
→ [issues/18](https://github.com/ojones/ai-factory/blob/archive/pre-purge-2026-10-21/.scratch/orchestrator-spec/issues/18-feature-flag-standards-content.md), [#22](https://github.com/ojones/ai-factory/issues/22)

### Flagging policy

A flag protects `main`. All work lands directly on a single `main` with no branches ([Git workflow](#git-workflow)), so a flag is what keeps a change that is not yet proven from reaching users. The policy follows from that:

- **Staging needs no flag; every change set after it does.** Staging a new app (repository, deploy, flag service, secrets) is verified by deterministic checks and has no business logic to protect. Every change set built on it goes behind a flag of its own, from the first one, so a new app is built the way an existing app is changed.
- **Every later update to an existing app that changes behaviour a user can see or reach is protected by a flag.** Changes with no user-visible effect (internal refactors, dependency bumps, a bug fix that only restores documented behaviour without altering what a user can reach) may ship unflagged; see [Release and retirement](#release-and-retirement). If in doubt, flag it: a flag is cheap and the rollback lever is the point. An update ships dark behind a flag of its own, and is released only after review and tests pass. Each update gets its own flag, separate from earlier updates', so one can be turned off without touching the others.
- **A flag covers the change, not each route or screen.** One flag around everything the change encompasses is enough. Neither the coder nor the reviewer needs a flag per endpoint or UI piece, though finer flags are allowed where they help.
- **What the Intake asks for stands.** If it names a flag, the flag is a requirement like any other.

This is the production safety net, and also the review gate, compensating for the direct-push-to-main, no-branch git workflow.
→ [issues/18](https://github.com/ojones/ai-factory/blob/archive/pre-purge-2026-10-21/.scratch/orchestrator-spec/issues/18-feature-flag-standards-content.md)

### Code wiring

All Managed Apps share one GrowthBook project (see [ARCHITECTURE.md](#feature-flag-infrastructure) — the free self-hosted tier caps at 1 project), with no GrowthBook-level boundary between apps. The flag-key naming convention carries the only isolation that exists, and so is app-scoped: **`<app-slug>.feature.<slug>`** for per-feature flags. The app slug is derived live by the Managed App's own code (e.g. from its repo name, the same env/derivation already used for the Fly app name per [#21](https://github.com/ojones/ai-factory/issues/21)) — never injected or persisted by App Staging, keeping the Starter Template's flag-handling code unmodified per app.

A single OpenFeature client is initialized once at app startup from the SDK connection key env var — not re-derived per feature. The client polls for live flag updates (`pollingInterval`) rather than using SSE streaming, which GrowthBook's own docs confirm is cloud/proxy-only, not available to a bare self-hosted instance.
→ [issues/18](https://github.com/ojones/ai-factory/blob/archive/pre-purge-2026-10-21/.scratch/orchestrator-spec/issues/18-feature-flag-standards-content.md), [build ticket #14](https://github.com/ojones/ai-factory/issues/14), [#22](https://github.com/ojones/ai-factory/issues/22)

### Resilience

Every OpenFeature call site must supply a real, sensible default value. Resilience against a GrowthBook outage comes from OpenFeature's own spec guarantee (flag evaluation always returns the default value on abnormal execution, never throws) — not from any GrowthBook-specific caching behavior.

**That default must always be `false` for a boolean flag — never `true`.** Confirmed live against `@openfeature/growthbook-provider@0.1.2`: GrowthBook represents an "off" boolean as `value: null`, and this provider's `translateResult` unconditionally substitutes the caller's default for any `null` value, with no way to distinguish "off" from "not found." Passing `true` makes a flag's off state permanently unobservable — the flag could never actually turn anything off, defeating its entire purpose. The real tradeoff this forces: "intentionally off" and "GrowthBook unreachable" become indistinguishable, so every flag fails *closed* on an outage, not open, for as long as this library bug stands. Revisit this note if a future `@openfeature/growthbook-provider` release fixes it.
→ [issues/18](https://github.com/ojones/ai-factory/blob/archive/pre-purge-2026-10-21/.scratch/orchestrator-spec/issues/18-feature-flag-standards-content.md), [build ticket #14](https://github.com/ojones/ai-factory/issues/14)

### Flag manifest

Every new flag is recorded in `flags.json` at the repo root — an array of `{slug, description}` entries — in the same commit that introduces it in code. (The slug is the `<slug>` part of the key; the release step prefixes the app slug. No added-in commit is recorded: a commit can't contain its own hash.) The release step reads the manifest to know what a Build Run introduced. A flag need not exist in GrowthBook for code to ship dark: a missing flag evaluates to `false`. But the release step never creates one: for an update the Orchestrator creates the story's flag, off, before the coder starts (see Release and retirement), and a flag that is missing at release is a failure to report, not something to make up.
→ [issue #24](https://github.com/ojones/ai-factory/issues/24)

### Preview

Every Managed App's flag wrapper honors a **Preview Token** so the tester can exercise a dark feature in the real deployment. A request carrying the token — as an `X-Preview-Token` header, or a `?preview=<token>` query parameter that sets an HttpOnly cookie for browser sessions — evaluates every `feature.*` flag as on. The token is compared against the `PREVIEW_TOKEN` env var. It works when GrowthBook is unreachable. Without a valid token the feature stays dark to everyone.
→ [issue #24](https://github.com/ojones/ai-factory/issues/24)

### Release and retirement

**Release** is the flag being enabled for all users. It is performed by a deterministic Orchestrator step after review and tests are clean, never by an Agent, and leaves every flag that already exists in GrowthBook exactly as it is, with one exception: the flag of the issue itself, created off by an earlier attempt of that same issue, is switched on once the gates pass.

**A flag has one job**: to stage a change dark and release it when it is safe. It belongs to the release pipeline end to end; nobody flips it by hand for any other purpose, and the Orchestrator may rely on that. It is short-lived by design.

**Retirement** — deleting a flag's check and its line in `flags.json`, keeping the behaviour on — is automatic, under the owner's standing approval recorded here, and it never costs a run of its own: it rides along in an Update App Intake's Build Run that is already coming in for the same app. At the start of that run the Orchestrator picks every flag (up to `limits.flag_retirement.piggyback_max`, 5, oldest first, so a backlog clears) that was released, was never switched off by the watchdog, is still in the manifest, and has a **later Build Run that also ended `released`** after it (a run that ended `nothing_to_release` does not count). The coder removes each flag's check in a separate commit, the tester checks the behaviour is still on for an ordinary visitor, the Orchestrator rejects the commit while code (not a comment) still mentions a retiring slug, and when the run ends well the retired flags are archived in GrowthBook. The newest release therefore always keeps its flag. A fix child retires nothing. Agents still never decide to retire a flag themselves. A flag the watchdog switched off is not retired: its child is fixed through a bug Intake and runs again behind its own flag (below).

**Story and flag.** One issue (the story) and one flag stay together for the whole life of a change. When an update's flag is released, the Orchestrator labels the issue `flag:<slug>`, adds `[flag: <slug>]` to its title and comments the full key; the GrowthBook feature carries the issue link in its description and an `intake-<n>` tag; the flag's entry in `flags.json` starts its description with the issue reference; the App State issue links each flag to its story; and when the flag is retired the story gets a comment saying so.

**A failure keeps its story.** When a child fails, or a release breaks and the watchdog switches its flag off, the story stays open and its flag stays off. The failed child gets a bug Intake (STEP 7.1), with exactly one child, an ordinary child with a flag of its own that goes through the same gates; the failed child waits for it and is never started again unchanged. When the fix closes, the failed child runs again behind its own flag and the release step switches that flag on when the gates pass. If it cannot be fixed within `fix_attempts_max` (2) fix children, the issue stays open, labelled `needs-human` and `dark-broken`, attached to its flag (a `flag:<slug>` label), which stays off. Its code stays in `main`, dark. That is a **dark feature**: it is tracked by its story issue and the flag, not by `flags.json`, and it is removed only when a person adds `approve-retire` to the story, which files an Update App Intake that deletes the flag, its code and its tests.

**Mechanics.** The numbered mechanics of the lifecycle (naming, creation, dark-mode tests, retirement, bug fixing) are in [flow-spec.md](docs/flow-spec.md#flag-lifecycle-mechanics).

**Built to be removed.** One change set has one flag, checked at the single entry point of the change with a plain string literal, so retiring it is deleting that one check. The reviewer flags a flag scattered across unrelated places.

Unflagged changes (bug fixes, refactors, dependency bumps, retiring a flag) go live on deploy, so the reviewer checks them before they are pushed and the Test Gate and the tester check them after. They are fixed forward if they fail; nothing is ever reverted in git, and the only thing taken back is the live deployment, rolled back through CI to the previous version, and only for a regression: users exposed to broken behaviour, meaning a failed check of behaviour that was live before (observed by a helper), or a failed check of a change that went live with no gate, whether it has no flag or its flag is read by no code (INV-25). On an update, a user-facing change with no flag around it is a blocking finding; on a first build it is not.
→ [issue #24](https://github.com/ojones/ai-factory/issues/24)

## Code layout

A domain is a plain Python folder under `orchestrator/` that holds one part of the [flow spec](docs/flow-spec.md) (steps are cited as `STEP n.m`): its code, its tests and its entry points. Nothing is installed or versioned separately; the file inventory is the folder itself.

| Domain (folder) | Steps | Role |
|---|---|---|
| Request (`request/`) | 1.1 to 1.3 | read the Intake forms, file automated Intakes |
| Planning (`planning/`) | 2.1 to 2.7 | the Planner, plan validation, child tickets |
| Staging (`staging/`) | 3.1, 3.2 | stage a new app and verify its infrastructure |
| Build Run (`build_run/`) | 4.1 to 4.14 | one `BuildRun` class whose steps are mixins, one file each |
| Flag Lifecycle (`flag_lifecycle/`) | 5.1 to 5.8 | flag names, creation, release, watchdog (5.8), retirement |
| Retrospective (`retrospective/`) | 6.1 to 6.7 | close a child, name the cause, judge events |
| Try Fix (`try_fix/`) | 7.1 to 7.7 | failure events, bug tickets, Factory fix requests for a person |
| Bugs (`bugs/`) | 8.1 to 8.4 | production errors and escaped defects |
| Maintenance (`maintenance/`) | none | template sync and dependency updates |
| Monitoring (`monitoring/`) | none | benchmark, canary, dashboard, Fly audit |
| Shared (`shared/`) | none | what two or more domains use; imports no domain |

### Rules

- **Imports** (checked by `boundary_test.py`; a new edge is added to its `ALLOWED` and here only if deliberate): `shared` imports no domain; every domain may import `shared`; `planning`, `staging`, `build_run`, `retrospective`, `maintenance`, `bugs`, `flag_lifecycle` and `try_fix` may import `request`; `build_run` may import `flag_lifecycle`, `planning` and `try_fix`; `staging` and `bugs` may import `try_fix`; `retrospective` may import `try_fix` and `flag_lifecycle`; `try_fix` may import `planning`; `monitoring` imports only `request` (benchmark files issues in the form's shape, fly audit checks the factory marker); no cycles. Anything else is a deliberate edit to the test and this page.
- **Talking through GitHub.** Domains mostly run as separate workflows, so they communicate through the `factory-plan` marker, labels, native dependencies and the App State record, not through Python calls.
- **Entry points.** A workflow sets `PYTHONPATH=orchestrator` and runs `python -m <domain>.<command>`. A command file is named for the command.
- **Tests** sit beside the code, named for the behaviour they check (`name_test.py`), and run per domain (`python -m unittest discover -s orchestrator/planning -t orchestrator`) or all together. `invariants_test`, `style_test`, `flow_spec_test` and `boundary_test` stay at the top of `orchestrator/`.
- **Moves.** A move is its own commit with behaviour unchanged. No re-export shim or old path is left behind; the workflow's command changes in the same commit.

### Imports that cross domains today

These are the couplings the domain tickets remove or put behind a named function:

- `staging` imports `try_fix` (the failure event for a failed check). `build_run` imports `planning` (the secret and triage checks) and `try_fix` (the fix note for a fix child); planning itself runs in `plan.yml`, and finalize and the retrospective are separate workflow steps. `retrospective` imports `try_fix`, `flag_lifecycle` and `request`, never `build_run`.
- `bugs` imports `request` and `try_fix` (the failure event) and talks to the Retrospective and Try Fix through files in `production-feedback.yml`. `maintenance/` and `monitoring/` no longer import any flat module.

### Workflows by trigger

- **An issue label:** `update-app-intake.yml`, `app-staging.yml`, `approve-retire.yml`. `plan.yml` runs on the two intake labels (planning).
- **Manual (`workflow_dispatch`):** `build-run.yml`, `benchmark.yml`, `flag-set.yml`, `reviewer-replay.yml`, `smoke-reviewer-model.yml`, `teardown.yml`, `verify-secrets.yml`, `isolation-probe.yml`.
- **Scheduled (and manual):** `canary.yml`, `dashboard.yml`, `fly-audit.yml`, `maintenance.yml`, `production-feedback.yml`, `template-sync.yml`.
- **Pull request:** `factory-checks.yml` (`unit`, `starter`, `reviewer-smoke`); every pull request to ai-factory is written and merged by a person.

Today there are 19 workflows, `plan.yml` included.

### The child ticket contract (`shared/child_tickets.py`)

A child ticket is a sub-issue of the Intake it was planned from. Planning writes it; the Build Run, the Retrospective and Try Fix read it. The sub-issue shape lives only in `ChildTickets` (create then add by numeric id, blockers, readiness, parent lookup with its 404).

The hidden `<!-- factory-plan:{...} -->` marker at the top of the body holds: `parent` (the Intake's number), `cs` (the change set id), `kind` (`staging` or `update`), `flag` (yes or no; the slug is always `issue-<n>`), `internal_only`, `size` (`S` or `M`), `requirements`, `secrets` (names and purposes, never values) and `depends_on`. **Decision (ticket 09):** the native GitHub blockers are the source of truth for order, because the UI shows them and readiness is judged from each blocker's state; the marker's `depends_on` holds the change-set ids that `file_children` turns into blockers when it files the children. The body below the marker is the Update App Intake form with the complete instructions (acceptance criteria, how each is checked, out of scope, the flag sentence), so a child needs nothing else to be built.

Filing is all or nothing and idempotent: a parent that already has children is left alone; if any call fails, the children made are removed from the parent and closed, and the error is raised, so the Intake can be planned again with no orphan. A child's parent is looked up with `parent_of` (None for an issue with no parent, which the Build Run refuses as unplanned).

## Managed app standards

The conventions a Managed App's own code follows, per [GLOSSARY.md](GLOSSARY.md). What an Agent needs while coding is in the Starter Template's `AGENTS.md`, which travels with every app; this section keeps the reasoning.

### Stack

Every Managed App is **Express (backend) + React (frontend), both in TypeScript** — one Node.js codebase, frontend built via Vite to static assets served directly by Express's `express.static()`. Not re-derived per project: only JS/TS pairs a competitive backend framework with a genuine frontend-framework ecosystem, and Express/React are each their ecosystem's dominant, most battle-tested choice. Runner-up: FastAPI (Python) + React — loses on forcing a second language into every Managed App.
→ [issues/20](https://github.com/ojones/ai-factory/blob/archive/pre-purge-2026-10-21/.scratch/orchestrator-spec/issues/20-which-application-stack.md)

### Starter Template

Every new Managed App is seeded from a fixed **Starter Template** (directory structure, CI config, boilerplate) rather than built from scratch each Build Run — cheaper in agent tokens, keeps every Managed App structurally identical.
→ [issues/11](https://github.com/ojones/ai-factory/blob/archive/pre-purge-2026-10-21/.scratch/orchestrator-spec/issues/11-coding-standards-content.md)

### Test gate

A hard gate in the deployment pipeline, not Agent judgment: unit tests for business logic, plus one minimal boot/health-check smoke test. No coverage-percentage threshold.

If the gate fails after a push, the same Build Run keeps watching the GitHub Actions run (a Pipeline Agent diagnoses, the coder fixes — see [ARCHITECTURE.md](#agents-and-build-run-stages)) until green, bounded by the cost guardrail ([ARCHITECTURE.md](#cost-guardrails)) — never a fire-and-forget push that can leave `main` broken indefinitely.
→ [issues/11](https://github.com/ojones/ai-factory/blob/archive/pre-purge-2026-10-21/.scratch/orchestrator-spec/issues/11-coding-standards-content.md)

### Style

Purely mechanical — checks are the style guide, not prose. The Starter Template ships Prettier (`npm run format`) and ESLint (`npm run lint`, part of `npm run check` and so of the Test Gate); formatting itself is not a gate, so an old file is never failed for its layout, but the coder runs `npm run format` first, before the build and the tests. No prose conventions (naming philosophy, comment density) for an Agent to probabilistically get wrong. Beyond formatting, the lint config carries the Factory's own rules for what recurring review findings showed (a test must not assert on source text or on `flags.json`, no committed `.only`, a test must make an assertion, and one whose only assertions are `toBeTruthy`/`toBeDefined` is a warning; anything named `expect*`, `assert*`, `verify*` or `should*` counts as an assertion, so a helper such as `expectStatus` is fine); each has failing and passing cases in `agents/lint-fixtures/cases.json`. The lint and formatter config belongs to the Orchestrator: the coder cannot edit it or suppress a rule to get past it, it fixes the code. New rules arrive through template sync and the coder fixes what they report in that Update App Intake.
→ [issues/11](https://github.com/ojones/ai-factory/blob/archive/pre-purge-2026-10-21/.scratch/orchestrator-spec/issues/11-coding-standards-content.md)

### Git workflow

Only the coder Agent pushes, and it pushes directly to `main` — no branches, no PRs. Review happens after the push, on `main`, while the new feature is still dark behind its feature flag ([Release and retirement](#release-and-retirement)). The flag is the gate for going public, the test gate is the gate for a healthy build, and a self-merged PR would add a step without adding safety.
→ [issues/11](https://github.com/ojones/ai-factory/blob/archive/pre-purge-2026-10-21/.scratch/orchestrator-spec/issues/11-coding-standards-content.md)

### Data and migrations

A feature flag hides code, not data. A deploy applies any change to stored data to every user at once, while the feature is still dark, and switching the flag off cannot undo it. So a change that touches how data is stored is **additive**: add a new field, table or index and keep writing and reading the old shape until the new code has been released and is permanent. Never drop, rename or retype something the previous version still reads in the same change; do that in a later, separate update (expand, then contract) once nothing reads the old shape. A migration must be safe to run twice and must leave the previous version of the app working. The reviewer treats a non-additive change to stored data as blocking.

### Secrets and configuration

All runtime config/secrets via env vars only, documented via a committed `.env.example`. Zero hardcoded values.
→ [issues/11](https://github.com/ojones/ai-factory/blob/archive/pre-purge-2026-10-21/.scratch/orchestrator-spec/issues/11-coding-standards-content.md)

### Dependencies

Default to free/OSS/self-hostable packages; avoid paid SaaS SDKs unless a task genuinely requires one.
→ [issues/11](https://github.com/ojones/ai-factory/blob/archive/pre-purge-2026-10-21/.scratch/orchestrator-spec/issues/11-coding-standards-content.md)

### Rule discovery

`AGENTS.md` at the repo root: OpenHands auto-loads it into its system prompt. The Starter Template seeds it with everything an Agent needs to follow these standards (stack, structure, commands, flags, rules), and Agents extend it with project-specific notes. The Standards are not copied into a Managed App repo, so anything a coder must follow belongs in that file or in a check.

### Logging

Managed App code emits structured (JSON) logs to stdout, picked up by Fly.io's native log aggregation — no extra infrastructure.
→ [issues/13](https://github.com/ojones/ai-factory/blob/archive/pre-purge-2026-10-21/.scratch/orchestrator-spec/issues/13-visibility-standard-design.md)

### Error handling

A global uncaught-exception/unhandled-rejection handler is required, logging the full error/stack trace (not just the message string) before the process exits — never a silent crash.
→ [issues/13](https://github.com/ojones/ai-factory/blob/archive/pre-purge-2026-10-21/.scratch/orchestrator-spec/issues/13-visibility-standard-design.md)

### Deployment contents of a Managed App

What a Managed App's own repo must contain. Orchestrator-side provisioning is under Deployment provisioning below.

#### Containerization

One container per Managed App — the backend serves the built frontend's static assets itself; no separate frontend container or second Fly app. Standard multi-stage Docker build, minimal base image, non-root user, pinned base image digest.
→ [issues/12](https://github.com/ojones/ai-factory/blob/archive/pre-purge-2026-10-21/.scratch/orchestrator-spec/issues/12-deployment-standards-content.md)

#### Registry

GHCR, images tagged by git commit SHA (`ghcr.io/<org>/<app>:<sha>`), plus a floating `latest` tag for convenience that moves only when a commit has passed both the Test Gate and the build. SHA tags are immutable, so the deploy step always references an unambiguous image.
→ [issues/12](https://github.com/ojones/ai-factory/blob/archive/pre-purge-2026-10-21/.scratch/orchestrator-spec/issues/12-deployment-standards-content.md)

#### Workflow split

Two separate GitHub Actions workflow files: `build.yml` (target-agnostic: checkout, build the image with a layer cache, tag by SHA, push to GHCR) and `deploy-fly.yml` (target-specific: `flyctl deploy`, driven by `fly.toml` + a thin provisioning script). `build.yml` runs in parallel with the Test Gate on every push to `main`, not after it; `deploy-fly.yml` starts when either finishes and proceeds only for the run that finds both green for the commit, so nothing deploys unless the Test Gate and the build both pass. The Test Gate installs, type-checks and tests; the image build does the real compile and bundle.

**Swappability** is expressed structurally: the build workflow never changes across targets; moving a Managed App to a different host means replacing only `deploy-fly.yml` (and its referenced native config) with a new deploy workflow — a single, isolated file change by construction.
→ [issues/12](https://github.com/ojones/ai-factory/blob/archive/pre-purge-2026-10-21/.scratch/orchestrator-spec/issues/12-deployment-standards-content.md)

#### Starter Template contents: workflows and Fly config

`build.yml`, `deploy-fly.yml`, and the Test Gate workflow (`test-gate.yml`, triggered on push to `main`) ship as **permanent, unmodified Starter Template content** — every Managed App gets byte-identical copies; App Staging never generates or mutates their YAML.

The one value that varies per Managed App — the Fly app name — is never injected or persisted by App Staging either. Intake already fixes the repo name to the Managed App's name ([ARCHITECTURE.md's Intake section](#intake)), so every reference to the Fly app name derives it live from the repo's own name instead of having App Staging template or persist a separate value. Concretely, `fly.toml` has **no `app` field** (a static file can't derive it); `deploy-fly.yml` sets `FLY_APP_NAME` from the repository name and passes `--app` to every `flyctl` call, and `fly/provision.sh` reads `FLY_APP_NAME` from its environment.

**Name collisions**: Fly app names are unique across all of Fly, so the Managed App's name (and therefore its repo name) must be globally free, not merely unused in the Factory's account. App Staging checks this before creating anything and refuses a taken name; pick something distinctive (e.g. prefix with the owner's handle).
→ [issue #21](https://github.com/ojones/ai-factory/issues/21)

#### Data storage of a Managed App

A Managed App keeps long-lived data on one **Fly volume** named `data` (1 GB, in the region `fly.toml` names as `primary_region`), mounted at `/data` and exposed to the app as `DATA_DIR`. `fly/provision.sh` creates the volume idempotently next to the Fly app, `fly.toml` mounts it, and the container's entrypoint hands `/data` to the unprivileged `node` user before dropping to it (a fresh volume is owned by root). `deploy-fly.yml` runs `fly/provision.sh` before every deploy, so the mount never points at a missing volume. Only Managed Apps staged from the Starter after this change have the mount, the entrypoint and `DATA_DIR`; earlier apps keep their own files and have no volume until a change brings those files over. Structured data goes in a SQLite file under `DATA_DIR`, through Node's built-in `node:sqlite` (FTS5 included), so there is no database server, no native npm dependency and no new account or secret. Everything else on the container's disk is lost on every deploy and restart.

**Why this and not a managed database.** It costs about $0.15 per GB-month, uses the single Fly token the Factory already holds, and fits experimental apps with few users. The price is one machine in one region: deploys and rollbacks run with `--ha=false`, the app runs as a single instance, and Fly's daily volume snapshots are the only backup. An app that needs several instances or point-in-time recovery needs a hosted database (Neon for Postgres, Turso for SQLite), which would mean the Factory holding a new account and passing a connection string to each app as a secret; that is not built.

**Teardown** destroys the Fly app and with it the volume and the data on it. Application code keeps all SQL in one persistence module, so a later move to a hosted database changes that module only.

#### GHCR to Fly image handoff

New container packages on GHCR are private by default, and changing a package's visibility is UI-only (no API), so unattended App Staging can't make them public. Fly can't authenticate to pull a private GHCR image. So `deploy-fly.yml` — the Fly-specific file — pulls the SHA-tagged image from GHCR using the job's own token, re-pushes it to `registry.fly.io/<app>:<sha>`, and deploys from there. GHCR stays the registry of record and `build.yml` is unchanged, so swappability is preserved. If a package does turn out to inherit its public repo's visibility, this step is redundant but harmless.
→ [GitHub docs on package visibility](https://docs.github.com/en/packages/learn-github-packages/configuring-a-packages-access-control-and-visibility), [issue #30](https://github.com/ojones/ai-factory/issues/30)
