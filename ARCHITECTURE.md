# Orchestrator Architecture

Decisions about how the Orchestrator itself is built and operated — for whoever implements the v1 Orchestrator. Distinct from [STANDARDS.md](STANDARDS.md): nothing here is something a Managed App's own code needs to follow. Terminology follows [GLOSSARY.md](GLOSSARY.md).

**The flow.** [docs/flow-spec.md](docs/flow-spec.md) is the official, numbered spec of how a request becomes a running, recorded change; cite its steps as `STEP n.m`. This document explains the parts in terms of that flow. The flow was redesigned around a separate planning process, child tickets filed as GitHub sub-issues, and fix-first; a passage marked **Target** describes that design and is not built yet (the tickets that build it are in `.wayfinder/intake-planning-redesign/`), and a passage marked **Built today** describes what runs now. An unmarked passage is true of both.

Advice from outside this repo, and how much of it the Orchestrator follows, is in [docs/advice/](docs/advice/README.md). It is advisory: where it conflicts with this document, this document wins.

Each decision links back to its ticket in `.scratch/orchestrator-spec/issues/` for the full comparison, runner-ups, and citations.

## Agent runtime

The Orchestrator reuses an existing open-source CLI coding-agent harness rather than a custom LLM loop — shrinks build scope and matches the Factory's open-source lean.

**Harness: [OpenHands](https://github.com/All-Hands-AI/OpenHands)** (MIT). SWE-bench-leading, pluggable to open-weight models via LiteLLM, purpose-built `--headless` CLI mode with `--json` structured output. Runner-up: mini-swe-agent.
→ [issues/01](.scratch/orchestrator-spec/issues/01-agent-runtime-reuse-harness.md), [issues/07](.scratch/orchestrator-spec/issues/07-which-agent-harness.md)

## Agents and Build Run stages

A Build Run runs several Agents in sequence, each a separate headless OpenHands invocation with its own role prompt. Role prompts live in ai-factory, not in the Managed App repo, so the coder can't edit its reviewer's instructions. Agents hand off through `main` and structured JSON files (findings, verdicts), never through branches or PRs. **The coder is the only Agent whose work reaches `main`**, but it only commits: the Orchestrator holds the PAT and does the push, so no Agent can read a credential from its checkout or environment. The Orchestrator rejects and discards a coder commit that touches the Starter Template's protected files (`.github/`, `fly.toml`, `fly/`, the flag wrapper `feature-flags.ts`, `INTAKE.md`, and the lint and formatter config `eslint.config.mjs`, `.prettierrc.json`, `.prettierignore`), since the workflows hold the Fly token and the lint config is how a check reaches every app: owning it means the coder cannot loosen a rule to make a check pass. When template sync changes that config it is committed locally after the run's base and pushed with the coder's first reviewed work (a push of the config alone could turn the app's Test Gate red), and the coder, and only the coder, fixes what the new rules report, through the same Update App Intake as everything else; the Orchestrator also names any `eslint-disable`, `@ts-ignore` or `@ts-nocheck` a diff adds as a minor finding.

**Roles**
- **Coder**: implements the task from the Intake issue (target: from its child ticket, STEP 4.1), committing to `main` for the Orchestrator to push. An update to an existing app goes behind a feature flag recorded in `flags.json`; a first build needs none ([STANDARDS-FEATURE-FLAGS.md](STANDARDS-FEATURE-FLAGS.md)). Its model is set in [agents/profiles.yml](agents/profiles.yml) (currently DeepSeek-V4.1-Flash, see [Model serving](#model-serving)).
- **Reviewer**: read-only on code. Reviews the coder's commit **before it is pushed** (so code it blocks never reaches `main` or the deploy) and emits a structured JSON verdict with findings, plus any `improvements` it suggests for the system (below). On an update, a user-facing change with no flag around it is a top-priority finding, but a first build is never faulted for lacking flags; it wraps nothing itself and sends the finding back to the coder. **The Orchestrator derives the verdict from the findings and their structure** (`banded_findings`): every finding carries a `category` and an `evidence_kind` (`repro`, `cited` or `opinion`), and one the reviewer called blocking blocks only if its category can block (not style, duplication or other) and it has a repro or a cited file and line; otherwise it is minor, with the reason recorded. A document without that structure is refused and the reviewer is asked again, so a label is never trusted alone. Two flag checks need no judgement and are made by the Orchestrator itself (`flag_findings`, always minor): a flag no code outside the tests reads, and a flag description with no issue reference. The Orchestrator ignores the model's own `verdict` field: in testing the model wrote "clean" on every diff, even while listing blocking findings. When the reviewer is asked for structured output, the schema must put analysis and findings before the verdict, because generation follows property order and a verdict-first schema approved every diff, including an obvious command injection. Its model should differ from the coder's, since a clean review releases to everyone and a shared model shares blind spots. **Known deviation:** both currently run DeepSeek-V4.1-Flash (chosen on speed and cost, see [Model serving](#model-serving)), so the reviewer shares the coder's blind spots until one of them changes; revisit when the model-upgrade benchmark exists.
- **Tester**: runs after the push, against the deployed app, and exercises the dark feature using the Preview Token. It also runs the repository's own tests that apply to the release, and spot-checks that what was live before still works. Every check ends in one of four states, `passed`, `failed`, `blocked` or `not_run`, and only `passed` lets a change release (a check marked `passed` whose own evidence admits it was not observed, such as "unable to observe logs in production", counts as `not_run`, because the first real run on an unobservable requirement passed on exactly such a claim; for things not visible from outside the tester reports the repository's own test of it, or marks the check `not_run`); the tester also lists what it could not test or clean up (`limitations`). It works with tagged synthetic records, declares and avoids real side effects, stays bounded, and deletes what it created. On a first build with no flags it exercises the live app against the Intake spec instead. For HTTP checks the tester does not judge answers itself: it writes the requests and expectations (status, JSON subset, headers) as data and runs them with the Factory's `orchestrator/api_check.py`, which observes, compares mechanically and logs every result; the Orchestrator then lets the helper's log outrank the report (a result citing a failed check cannot be `passed`, and a failure the report left out is added). The helper reads the Preview Token from its environment, scrubs it from the log and calls only the app's base URL. **Each result says what it is about**: `scope: new` (the flagged change, or a first build's spec) or `scope: existing` (behaviour that was live before). The Orchestrator derives what a failure means (`test_impact`): a failed `new` check is `dark_only` and is fixed forward; a failed `existing` check that an `api-check` or `ui-check` helper observed is a `regression` (the model's word alone is not enough). Only a check the tester saw **fail** goes to the coder: one that was `blocked` or `not_run` cannot be fixed by it, so the tester looks again at the same deployed commit (`limits.test_retries`, default 1) and a run that still cannot verify stops for a person as `needs_human`, with no coder round spent. Like the reviewer it also suggests `improvements`. Can't push. Runs on the pinned model.
- **Planner** (STEP 2.1): a read-only Agent that turns an Intake into requirements, assumptions, blocking questions and ordered change sets, each with its own acceptance criteria, verification and flag. `orchestrator/planner.py` is the deterministic gate on its plan: every requirement covered, dependencies acyclic, criteria and verification present, a flag per update change set, at most 8 change sets, and any blocking question sent to a person instead of guessed. **Target:** planning is its own process (`plan.yml`), started when an intake label is applied and before any coding, for a New App Intake as well as an Update App Intake; its output is one child ticket per change set, each a complete set of coding instructions sized so that one flag can roll it back (see [Intake](#intake)). **Built today:** the planner runs first inside the Build Run for an Update App Intake only, files child issues for a plan of several change sets, and a new app is not planned at all.
- **Pipeline Agent**: invoked only when CI or the deploy fails. Deterministic polling does the normal watching, so the happy path costs no tokens. It diagnoses from the failing run's logs and Fly status, which the Orchestrator gathers into files for it (it holds no GitHub or Fly credential), and hands a fix request back to the coder. It can't edit code or workflows.

**Stages, in one Build Run**
1. The coder commits to its local `main`. It runs `npm run format` first, then the build, type-check and tests (see `agents/prompts/coder.md`); the Orchestrator does not format. Before the reviewer sees the commit, the Orchestrator runs the app's own `npm run check` (type-check and lint) on it as the Agent user, read-only; a failure is a rejected commit that goes straight back to the coder (three attempts, like a protected-file violation) and costs no review, push or CI run. A formatting difference is not checked (it is not a gate) and the build and tests stay with the coder and CI (`limits.precheck`).
2. **The reviewer reads that commit before anything is pushed.** Blocking findings go back to the coder, and nothing reaches `main` or the deploy. A clean verdict lets the Orchestrator push (only the Orchestrator pushes, and only reviewed code).
3. CI, the build, and the deploy run (the Test Gate and workflows are unchanged). On an update the new feature is **deployed dark** because its flag is off; a first build with no flags is live on deploy. Failures go to the Pipeline Agent; a fix it asks for is committed locally, **reviewed again**, and only then pushed. Bounded by the cost cap and time limit as before.
4. **The tester examines the deployed app** (dark, through the Preview Token) and says what a failure means. A `regression` ends the run at once (stage 6). Any other failure goes to the coder, who commits a fix that goes through stage 2 again, still dark. This loop is a fixed, configurable number of rounds, default **4** (`limits.review_rounds` in `agents/profiles.yml`); a round is one review, one test pass (only if the review was clean) and one fix commit. A blocked review costs a model call and a coder round and never pushes; a failed deployed test costs a push, CI, a deploy and a tester pass, so a second limit, `limits.test_rounds` (default **2**), stops the run for a person once that many deployed tests have failed. Unverified checks that are retested (`test_retries`) do not count against it.
5. **Release**: a deterministic Orchestrator step, never an Agent, creates and enables the new flags (if there are any) in GrowthBook, but only when all four hold for the pushed SHA: CI green, deploy healthy, the tester's preview run passed, and the reviewer's verdict clean. It then posts a "released" comment in the Managed App repo. Rolling back is the owner flipping the flag off in GrowthBook, or running the `Flag set` workflow (`flag-set.yml`, `orchestrator/flag_set.py`: app, flag and on/off; it changes only the production switch of an existing flag and reads it back); the step leaves every flag that already exists exactly as it is, except a retried story's own flag that the watchdog switched off (see Fix requests). **Nothing is reverted in git; only a regression rolls the deploy back**: code is fixed forward and `main` keeps every commit. A change that only breaks itself is dark, because its flag is never released, so it harms no one; the story is fixed forward by a later attempt behind the same flag (a **dark feature**, below). The one exception is a **regression**: the tester saw, through a helper, behaviour that was live before the run stop working. The tester only notes it. The run ends as `regression` straight away (no more rounds on top of a regression) and `finalize` has **the app's own CI** put the live app back on the previous deployed version: it dispatches the app's `rollback-fly.yml` (a Starter Template workflow; template sync gives it to existing apps) for the run's starting commit, whose image the earlier deploy left in Fly's registry, waits for that run and for `/api/health`, and records it in the Report and Summary. A failed rollback is reported loudly (an audit finding, and the first requirement of the fix request). `limits.rollback_regressions` (default `true`) switches it off. The regressing commits stay in `main` behind a flag that is off, and the story is retried forward behind the same flag (the `regression` route below); the retrospective adds each failed check the tester noted to the story's own issue as a note (no new issue), and the retry carries them as requirements. Until the fix lands, any other push to `main` would deploy the regressing version again, which the bug issue is there to prevent. **Dark features**: a flagged change that ran out of rounds, hit a cap, went `stuck` or regressed stays dark behind its flag. Its story issue is labelled `dark-broken` (and `flag:<slug>`), which together with the App State issue is how dark features are tracked; `flags.json` is not used for this, because the coder writes it and every edit to it deploys. The story is fixed forward (see Fix first). When its fix attempts are used up (today: `fix_request_max_attempts` failed retries) it is labelled `needs-human`; only then can a person add `approve-retire` to it, and `.github/workflows/approve-retire.yml` (`orchestrator/flag_retirement.py approve`) files one Update App Intake that deletes the flag, the code it guarded and its tests, and starts it. Nothing removes a dark feature on its own. **Rollback of a release**: the owner flips the flag off in GrowthBook or runs `Flag set`; the watchdog does it by itself. **Fix first, never retry the unchanged child** (STEP 6.2 to 7.5). **Target:** the retrospective step handles each bad ending once, by the cause it named. A cause in the app (the code is wrong, the spec was ambiguous): planning files a **fix child**, a ticket under the same parent and ahead of the failed one, with complete instructions and the **same flag** (the story's `issue-<n>`; a fix child inherits the original story's number), and the failed child waits for it as one of its dependencies; when the fix child closes, the failed child is started again. A cause in the Factory (prompt, planner, Starter Template, orchestrator): one `factory-fix-request` issue in ai-factory (add `ready-for-factory-run` and the Factory Run proposes a PR for a person to merge); when that learning PR merges and template sync has reached the app, the failed child is started again with the PAT. No cause, or an infrastructure one: the child is labelled `needs-human` and nothing runs until the owner edits it and applies the label again. An unchanged child is never started again by itself, the chain is bounded (the limit is decided in the fix-first ticket), and a failed child stays open and blocks its siblings. The failing story keeps its flag: the fix is made behind the same flag, goes through the same gates, and `release()` switches that same flag on again only because it is the story's own flag, off in production, with the gates passed; every other existing flag is left alone. A release the watchdog switched off is a regression of the story: the fix child finds what regressed and fixes it behind the same flag, never removing the feature. A budget failure does not raise the cost cap for the fix (a story that could not finish inside it is too big for one pass; the fix child is told to do less), so a story costs at most the cap per attempt. **Built today:** the comment on the story's own issue says that it broke and why, with the retry state hidden in it (`<!-- factory-retry:... -->`), and while attempts remain the issue gets the `retrying` label and the Orchestrator puts `proceed-with-change` back on the same issue with the PAT, so the planner, coder, tester and reviewer run again with no person reviewing it; the planner turns any blocking question into an assumption and must use exactly the failed attempt's flag; after `fix_request_max_attempts` (default 2) automatic retries the issue stays open, labelled `needs-human`, attached to its flag, and nothing starts. A failure of the same run reported twice is one attempt. **Watchdog**: after a release, the Orchestrator watches the app for `limits.watchdog_minutes` (default 10). Failed health checks in a row, or a rise in error-level log lines over what the app logged before the release, make it switch off the flags this run released (never one that already existed), read each back to confirm, and end the run as `watchdog_disabled`, which opens the usual Issue in the Managed App repo. The disable call and the read-back have not yet run against the real GrowthBook.
6. If the round limit, cost cap, or time limit is hit first, or `limits.stuck_rounds` rounds in a row leave the same checks failing and the same findings open (the run ends as `stuck`), the flag stays off, no release happens, nothing is reverted or rolled back (a flagged change is a dark feature), and a "needs human" or "budget exhausted" Issue is opened in the Managed App repo. Dark-by-default makes this the safe outcome, so no budget is reserved for later stages. One deterministic final step always writes the Summary and Issue even after a breach.

**Credentials**: Agents run as subprocesses with a whitelisted environment: their own scoped DeepInfra JWT, plus the Preview Token for the tester. They get none of the PAT, Fly token, DeepInfra parent key or GrowthBook admin key. **Agent isolation** (`limits.agent_isolation: user`, on since 2026-10-13): Agents run as a separate unprivileged account, so they cannot read the Orchestrator's process environment, the runner's workspace or its credential files, and each run proves this before any Agent starts (see Cost guardrails, Agent isolation). The retrospective Agent runs the same way (INV-45): as the Agent user, after the same self-check, in a copy of the Factory tree without `.git`; the Orchestrator compares the two plain trees, carries only changes under the allowed paths into its own checkout (never a symlink, never a file over 1 MB, never a workflow), and runs the unit tests of the result as the Agent user in a throwaway copy with no credential in the environment. It never runs git inside a directory the Agent wrote to, so a planted hook or config cannot run with the PAT. No Agent holds the GrowthBook admin key. The key's scope isn't app-scoped (all Managed Apps share one project), so an Agent holding it could change any app's flags or kill switch, and the release step is the gate the Agents are being checked against. Agents read flag state with the app's SDK key if they need to.

**Cost**: the goal is under $1 a Build Run. It is a target, not a cap (the cap stays `limits.cost_cap_usd_default`, $2): the dashboard counts runs over it and shows the 90th percentile. Measured on the first 32 runs the mean was $0.30 and the spend was driven by rounds and by failed Agent attempts, so a failed Agent now gets a stage in the Report with its cost, and an Agent that spent its whole credential without a usable file is not given a second attempt. All Agents draw on the Build Run's one cap. The "refuse the next turn" rule applies run-wide; there are no fixed per-Agent budgets. Agents run one at a time (the reviewer before the push, the tester after the deploy), so each is minted a credential limited to what is left of the cap when it starts, and the run-wide rule stops the next turn once the cap is spent (`Budget.mint` in `orchestrator/shared/spend_budget.py`).

**Retirement**: deleting a flag and its code path happens only on an explicit request from the owner, as a normal Intake. No Agent proposes or performs it unprompted.
→ [issue #24](https://github.com/ojones/ai-factory/issues/24)

## Model serving

Open-weight model inference is consumed via a pay-per-token API, not self-hosted GPU inference — Build Runs are bounded, not continuously GPU-saturated, so idle self-hosted cost would dominate.

**Provider: [DeepInfra](https://deepinfra.com).** Cheapest confirmed per-token price for the open-weight models used here. Runner-up: Together AI.

**Coder model: `deepseek-ai/DeepSeek-V4.1-Flash`**, switched from `Qwen/Qwen3-Coder-480B-A35B-Instruct-Turbo` after a smoke screen of seven models and a replay of two real recorded tasks (clean 6/6 against the Qwen's 0/6, about 18% faster per round, about 6x cheaper; results in `.wayfinder/coder-speed/tickets/14-*.md` and `15-*.md`). It missed one smoke task three times out of three, so `fix_model` in `profiles.yml` can route fix rounds to a stronger model if real runs stall. **Tester model: `nvidia/NVIDIA-Nemotron-3-Ultra-550B-A55B`**, switched from the 480B Qwen after the seeded-bug benchmark (`agents/smoke-tester/`): on the four edge-case bugs the Qwen mostly missed it caught 11 of 12 against 3 of 9, with no false alarms on the correct app, at about $0.147 a run against $0.11; it is a different lab from the DeepSeek coder and reviewer, so the tester stays independent of them. It has not yet been measured on the easy bugs, so a run that shows it missing those is a reason to switch back. **The Pipeline Agent and retrospective Agent** still run `Qwen/Qwen3-Coder-480B-A35B-Instruct-Turbo` (Apache 2.0), chosen as the cheapest confirmed price for a model trained for long tool-calling loops. **The planner** runs `openai/gpt-oss-120b` (fallback `Qwen/Qwen3.8-Flash`) since 2026-10-15: the 480B hung for minutes on real runs, a planner needs no code-tuned model, and gpt-oss-120b is about 8x cheaper and a different lab from the coder, reviewer and tester. It is unmeasured; watch the planner's time, cost and `plan_gap` lessons, and ticket 30 would benchmark it.

**Reviewer model: `deepseek-ai/DeepSeek-V4.1-Flash`** (issue #41), as a single-call reviewer (the Orchestrator assembles the diff, changed files, `INTAKE.md` and flag usage into one prompt) that falls back to the exploring Agent when the change is too big or the call fails. It replaced `deepseek-ai/DeepSeek-V4-Pro-0813` (the #25 pick: MIT, 1M context, $1.30 in / $2.60 out per 1M tokens), which spent 7 to 20 minutes per review in real Build Runs; Flash scored 50/50 on the smoke fixtures against Pro's 48/50 at about 10 s a review. The #25 reasoning, a different lab than the coder so a clean review isn't a shared blind spot, no longer holds while the coder is also DeepSeek-V4.1-Flash (see [Agents and Build Run stages](#agents-and-build-run-stages)). The smoke test for the #25 pick ([#33](https://github.com/ojones/ai-factory/issues/33), `agents/smoke/`): `usage.estimated_cost` is returned, tool calls and structured output work, it found all four seeded bugs (off-by-one, command injection, missing flag, flag default `true`) in 3 of 3 trials and passed a clean diff in 2 of 3 (one false positive), and it reviewed correctly end to end through OpenHands. A full 5-fixture, 3-trial pass costs about $0.02. No code-review benchmark covering open-weight models exists, so beyond this smoke test the quality case rests on owner-reported agentic-coding numbers.
→ [issue #25](https://github.com/ojones/ai-factory/issues/25), [research](https://github.com/ojones/ai-factory/blob/research/reviewer-model/.scratch/orchestrator-spec/research/reviewer-model.md)

**Models, prompts, and limits are config, not architecture.** Every per-role model, the provider endpoint, each role's prompt, and the review-round limit live in [agents/](agents/README.md), so any of them can be switched or tuned without editing this document.
→ [issues/02](.scratch/orchestrator-spec/issues/02-model-serving-api-not-selfhosted.md), [issues/08](.scratch/orchestrator-spec/issues/08-which-model-provider.md)

## Orchestrator host

The Orchestrator runs as ephemeral compute during a Build Run, not an always-on service — pay only while a Build Run is active.

**Platform: GitHub Actions** (GitHub-hosted runners). Native scheduling (`on.schedule`), secrets, and run logging with zero extra infrastructure; clears the 6-hour-per-job duration bar for an overnight run. Runner-up: Fly Machines.
→ [issues/03](.scratch/orchestrator-spec/issues/03-orchestrator-host-ephemeral.md), [issues/09](.scratch/orchestrator-spec/issues/09-which-compute-platform.md)

## Deploy target for Managed Apps

Deployment pins one default hosting target for v1 simplicity, but the mechanism must stay swappable per project — never hardcode an assumption the target is fixed forever.

**Default: [Fly.io](https://fly.io)**. Cheapest at low-traffic scale, lowest-friction GitHub Actions deploy flow. Runner-up: Railway.
→ [issues/04](.scratch/orchestrator-spec/issues/04-deploy-target-default-swappable.md), [issues/10](.scratch/orchestrator-spec/issues/10-which-deploy-target.md)

**IaC approach: `fly.toml`** (checked into each Managed App's repo) as the sole declarative app-config, paired with a thin, checked-in, idempotent provisioning script for what it can't express (secrets, DNS/certs, registry auth). Fly's own current recommendation — their official Terraform provider is archived and un-recommended by Fly.io itself.
→ [issues/15](.scratch/orchestrator-spec/issues/15-which-iac-approach.md)

## Cost guardrails

The spec requires a budget cap + hard stop exist and are enforced; concrete dollar figures are build-time config, not part of this spec.

**Enforcement mechanism**: the cap covers LLM token spend only (not GitHub Actions minutes or other metered calls). DeepInfra refuses a spending-limited JWT that carries more than one model (HTTP 422, "multiple models is not compatible with spending_limit", found building #32), so each Agent invocation gets its own **single-model scoped JWT** (DeepInfra `POST /v1/scoped-jwt`) whose `spending_limit` is what is left of the run's cap. All Agents therefore still share one cap, and the Orchestrator meters the run as the sum of every JWT's spend. Each JWT is both enforcer and meter. DeepInfra refuses the first call after the limit is crossed with HTTP 403, `token spending limit exceeded`, while the call that crosses it still completes, which is exactly "finish the current turn, refuse the next". The Orchestrator reads each JWT's spend from `GET /v1/scoped-jwt?jwtoken=<jwt>` (`spending_current`, USD) after its Agent invocation, for the Summary and Report and to skip remaining stages once the cap is reached. Verified empirically ([#35](https://github.com/ojones/ai-factory/issues/35)): `spending_current` equalled the sum of per-response `usage.estimated_cost` with no lag. This replaces summing `usage.estimated_cost` per response, which OpenHands' headless mode can't supply, and the earlier account-wide usage diff, which can't separate concurrent runs.

**Model swaps**: the Factory swaps models as better, cheaper, faster or more specialised ones appear, and decides each swap by a measured whole-run pass, not by a guess (INV-41; `docs/benchmark-protocol.md`). `orchestrator/benchmark.py` runs a fixed suite of seven Intakes (`agents/benchmark/suite.json`: a flagged route, an edge-case validation, an internal refactor, a named flag retirement, an ambiguous spec, and refusals of a payment request and a pasted secret) through the real `build-run.yml` against one disposable bench app that is forced back to a frozen commit before each task; a task is scored by code (the outcome it expects, its cost limit and `api_check` scenarios against the deployed app), and a pass is compared with the accepted baseline under `agents/benchmark/rules.json` (at most one task fewer passes, no safety or refusal task regressing, cost within 1.3x, rounds within +0.5; a candidate that holds those and costs or takes 0.9x or less is an improvement). A candidate is a branch whose `profiles.yml` names the new models (with limits pinned so passes stay comparable), dispatched from that branch so production code carries no benchmark mode. The `Benchmark` workflow is manual and dry-run by default; a pass costs about $0.60 to $3.20 and takes 1.4 to 3 hours. At run time each role may name a `fallback_model`: `BuildRun.check_models` asks the provider for one token from each model the run uses and swaps a missing one for its fallback (recorded as `fallbacks` in the Report) or stops with the reason, and a nightly canary (`canary.yml`) keeps one `model-drift` issue open while any configured model, primary or fallback, is missing. The canary ran once against the real provider (2026-10-14) and found all three distinct configured models, fallbacks included, served. The bench app, the baseline and the first pass are not created yet (`agents/benchmark/bench-app-spec.md`). **Intake triage**: two checks refuse a request before anything is built (`orchestrator/triage.py`, INV-40). The Build Run scans the Intake text for a real secret value (a private key block, a GitHub, AWS, Slack or `sk-` token, a JWT, a password or key assignment, ignoring placeholders) at the start of the run, and refuses at once, because Intake issues and app repositories are public: the comment names the kind of secret, never repeats it, and says to rotate it. For an update, the planner also judges feasibility first (`feasibility` in its plan): a request that needs payments, a third-party secret or key, personal data, an outside keyed service or something outside Express, React and free dependencies is `blocked` with reasons, the plan has no change sets, and the run ends `refused` right after the planner call (about $0.04). A refusal posts the reason and what could be built instead on the Intake issue, removes `proceed-with-change` so the edited request can be started again, and is not retried, filed as a failure Issue in the app repo, or learned from. The acceptance criteria the planner derives are posted on the issue as before, with no confirmation step: the run continues. `docs/golden-intakes.md` shows good and refused requests, and the Update App Intake form points to it. Today a first build has no planner, so only the secret scan applies to it; target: a New App Intake is planned like an update, so both checks apply (STEP 2.1, 2.2). Proven live on `ojones-todo` (2026-10-13): a request to take card payments was refused after the planner call for $0.078 with three reasons and a suggested alternative, and a request containing a made-up `sk-` token was refused at the start for $0; neither filed a failure Issue or fix request, and `proceed-with-change` was removed from both. **Flag retirement**: a flag has one job, staging a change dark and releasing it when it is safe, so it is short-lived and nobody uses it for anything else. Retiring a proven flag never costs a run of its own: it rides along in an Update App Intake's Build Run that is already coming in for the same app (`orchestrator/flag_retirement.py`, `limits.flag_retirement`). At setup (`BuildRun.choose_flags_to_retire`) the Orchestrator reads the app's State issue and `flags.json` and picks every flag, oldest first up to `piggyback_max` (5), that was released, is still in the manifest, was released on an earlier day and has a *later Build Run that also ended `released`* after it (never the newest release, never one the watchdog switched off, and a `nothing_to_release` run counts for nothing). Not for a first build or an automatic retry. The coder's task gets a block of `retire-flag: <slug>` lines (each its own removal, its own commit, no new flag), the spec the reviewer and tester check against gets a note that the behaviour must still be on for an ordinary visitor, the Orchestrator rejects the coder's commit while code (not a comment) still mentions a retiring slug, and when the run ends well the flags it removed from `flags.json` are archived in GrowthBook. Flags are built to be removed: one flag per change set, checked at one entry point with a string literal (coder prompt, reviewer rubric). Proven live on `ojones-todo` (2026-10-13): first as a dedicated run ($0.36), which is why it now rides along; then riding along in a real update run (Intake #97, $0.48 over two rounds), which retired `todos-count-endpoint` (check and manifest line gone, archived in GrowthBook, route still answering for an ordinary visitor) with no run of its own. **Flag stories**: a flag and the issue it belongs to refer to each other in both directions (INV-38). **Target (STEP 4.1, 5.1):** the flag's slug is always `issue-<n>`, `<n>` the story's own child ticket number (a fix child uses the failed story's number), so the name alone links the two; the Orchestrator creates the GrowthBook feature (production off) at the start of the child's Build Run, before the coder works, and writes its `flags.json` entry, release only switches it on, and the Starter's `npm run check` fails a commit whose new flag lacks a flag-off and a flag-on test. **Built today:** the planner picks the slug and the feature is created at release. On release of an update's flag the Orchestrator (`BuildRun.link_flags_to_issue`) adds a `flag:<slug>` label to the Update App Intake, appends `[flag: <slug>]` to its title (never for a first build, whose title must stay the bare app name) and comments the key; `release()` creates the GrowthBook feature with the issue URL in its description and tags `intake-<n>` and `app-<app>` (retried without them if GrowthBook answers 400); the coder is given `{{issue_ref}}` and starts the flag's `flags.json` description with it (the Orchestrator files a minor finding if not); the State issue's flag table has a Story column (`appstate.story_link`); and a retirement comments on the flag's story. Proven live on Intake #97: the issue got the `flag:version-endpoint` label, the `[flag: version-endpoint]` title tag and the comment; GrowthBook has the issue link in the description and the tags `intake-97` and `app-ojones-todo`; `flags.json` starts the description with `ojones/ai-factory#97:`. **Browser checks (`ui-check`)**: for a change that touches `frontend/` or whose spec mentions something on screen, the tester's prompt also carries instructions for `orchestrator/ui_check.py`, the browser counterpart of `api-check` (limits.ui_check). The tester writes scenarios as data (a start path, `auth` preview or none, steps such as click and fill found by role or label, and what must be visible, hidden, contain which text, or how many); the helper drives a headless Chromium through Playwright in a fresh context, opens only the app's own origin, observes, compares mechanically and logs every result, and the Orchestrator lets that log outrank the report exactly as for `api-check` (INV-36). It opens an `auth: preview` scenario with the Preview Token (the app sets its HttpOnly cookie), never prints or logs the token, and takes a screenshot only of a failing scenario. Playwright and Chromium are pinned in `agents/playwright-version.txt` and installed by the workflow into `/opt/playwright`, outside the Managed App; screenshots and the helper's JSONL log are uploaded, traces and HAR files never are (they record headers and cookies, and the repos are public). The expectations are re-read for a few seconds before a scenario fails, because a page updates after a network call. If the tester writes no usable report but a helper saw something fail, the Orchestrator builds the report from the helpers' logs instead of stopping for a person. First live use (2026-10-13, a to-do page on `ojones-todo` behind a `todo-ui` flag): the first run failed because the helper read the page too early and the tester re-ran scenarios and debugged the app until it ran out; after the fixes a second run passed 10 scenarios and 15 checks for $0.30 and released. **Agent isolation** (`limits.agent_isolation: user`): the Orchestrator and its Agents used to run as one operating-system account, so an injected Agent could read the Orchestrator's process environment and files (the PAT, Fly token, GrowthBook admin key). A probe on a GitHub-hosted runner (`isolation-probe.yml`) showed that a different unprivileged account cannot read another account's `/proc/<pid>/environ`, the runner's home or the Actions files, but can read any process's command line, so the workflow creates an `agent` account, moves the Build Run's directories to `/srv/agent` (shared with the runner through ACLs) and every Agent starts through `sudo -n -u agent` with the whitelisted variables passed by name, so no value appears on a command line; the git credential likewise moved from `git -c http.extraheader=...` arguments to `GIT_CONFIG_*` environment variables. At the start of each run a self-check runs probes as the Agent account (is it another account, can it read a marker process's environment or the workspace, does its environment hold credential variables, can it sudo) and the run stops if any fails. A timed-out or silent Agent is killed through sudo by process group. Not covered: an Agent is not stopped from reading what its own account can read, such as the app checkout. **Silent Agents**: an Agent's `--json` event stream grows at every step, so one whose stream has not grown for `limits.agent_stall_minutes` (8) is killed with its whole process group and counts as a failed attempt, instead of holding the run for the full `agent_timeout_minutes` (45). The first production-feedback Build Run lost 90 minutes to two coder starts that did nothing for the full timeout. **Provider out of balance**: when the model provider answers HTTP 402 ("You need positive balance to do inference"), every request fails until someone tops up, and anything that reacts to those failures would only fail the same way. Each Build Run therefore starts with a one-token preflight to the provider; the same refusal is recognised when minting a credential, in the single-call reviewer, and in an Agent's own error event. The run stops at once as `provider_blocked`, leaves anything it had already pushed as it is (fixed forward, never reverted), and files **one** deduplicated alert in ai-factory (`provider-blocked`, `needs-human`) asking for a top-up, with the label to re-add afterwards. No fix request, lesson, self-starting retry or retrospective Agent is started. **Daily cap**: each finished Build Run adds one line (`ledger <date> <app> <usd> run:<id>`) as a comment on the `factory-ledger` issue in ai-factory, and a new Build Run refuses to start once today's lines (UTC) reach `limits.daily_cost_cap_usd` (default $10, 0 disables). Runs still in flight are counted only when they finish, so concurrent runs can overshoot by their own caps. The retrospective and Factory Run Agents have their own per-analysis cap (`retrospective_cost_cap_usd`), and what they actually spent is added to the same ledger (as `retrospective`, with its own run id so it is not mistaken for the run's line); the planner runs inside the Build Run's budget, so its spend is already in the run's line. **Production feedback**: the watchdog watches for ten minutes after a release; a bug that shows up later is found by a scan every six hours (`production-feedback.yml`, `orchestrator/production_feedback.py`, switch and limits in `limits.production_feedback`). It reads each registered Managed App's Fly log, groups error-level JSON lines by fingerprint (the message with ids and numbers removed, plus the first application stack frame), and an error seen `min_occurrences` (3) times in one scan becomes an Update App Intake that starts itself with the PAT's `proceed-with-change`, with no review first: the planner, coder, tester and reviewer run, the change ships behind a flag, and a bad ending is fixed forward and files a fix request as usual. An open issue labelled `escaped-defect` in the app's repo becomes the same kind of Intake, but only if the repo owner wrote it (anyone else's text never reaches an Agent). Flood control: one open Intake per fingerprint (a repeat comments), one open per app at a time, `max_per_app_per_day` (2) new ones per app per day. The Intake carries only the cleaned message and first frame, in a code block marked as data. There is no readiness check or planner veto; if failures pile up, the bad endings are the evidence for adding one. Fly keeps a short log buffer, so a scan sees only recent lines. It ran against `ojones-todo` on 2026-10-13 (one Intake for 100 occurrences, a second scan only commented). **Maintenance**: every app carries `.github/dependabot.yml` (from the Starter Template), so Dependabot watches its npm packages, Docker base image and GitHub Actions daily. Dependabot only detects: nothing merges its pull requests (trunk-only, and a green CI alone would skip the tester and reviewer). A daily pass (`maintenance.yml`, `orchestrator/maintenance.py`, switch `limits.maintenance.enabled`) reads each registered app's open Dependabot pull requests and, for the npm and Docker ones, files one Update App Intake per app and set of updates, security fixes first, that starts itself; the planner, coder, tester and reviewer apply them (no flag: users see no difference) and Dependabot closes its pull requests once the dependency is updated. GitHub Actions updates edit `.github/`, which Agents may not change, so they are only listed. The same pass switches on Dependabot alerts and security updates for each repo (best effort). The Starter's Test Gate also runs `npm run audit` (`npm audit --omit=dev --audit-level=high`), so a high or critical advisory in a production dependency fails CI; the fix is the update Intake. The Starter's Dockerfile writes its Node 22 base image, pinned by digest, in both `FROM` lines (it was an `ARG` on Node 20, which Dependabot cannot update and which reached end-of-life in April 2026). A template-sync run copies the protected Starter files that are safe to overwrite itself, before any Agent starts (`.github/dependabot.yml`, `.github/workflows/test-gate.yml`, `.github/workflows/rollback-fly.yml`, `.github/workflows/deploy-fly.yml` (which carries the secrets copy step), and the lint and formatter config, which is staged and pushed with the coder's work), so existing apps get them; other protected files are still listed for a person. The daily Fly audit also prints each app's days since its last push in the run summary; nothing is retired automatically. None of this has run against a real app yet. **Orphaned Fly apps**: a daily workflow (`fly-audit.yml`, `orchestrator/fly_audit.py`) lists the Fly apps in the organization (`FLY_ORG`, default `personal`) and keeps one `fly-orphans` issue for any that is neither infrastructure (`limits.fly_infra_apps`, plus GrowthBook) nor a Managed App with a Factory-marked repo, because those bill for machines nothing will stop. It deletes nothing. The Fly list call (`GET api.machines.dev/v1/apps?org_slug=`) ran once against the real account (2026-10-13) and reported no orphans; whether it saw every app is not yet confirmed.

**Worst-case overshoot** is one call's cost, because the crossing call completes (normally fractions of a cent; a very large-context call to the reviewer model could be a few tenths of a dollar). The DeepInfra account-level spend cap remains the last-resort ceiling. Each JWT is masked in logs, lives in the single Build Run job, and expires after the configured lifetime (default 6 hours, the Actions job limit); a compromised dependency in an Agent's environment could spend at most the JWT's remaining budget on that role's model.

**Numbers are config** in `agents/profiles.yml` (`limits`): the default cap (**$2.00**), the ceiling an Intake override may request (**$10.00**, enforced at Intake), and the JWT lifetime. They are starting values to revise after the first real multi-agent run.

## Visibility

A minimum observability/reporting requirement for unattended Build Runs is part of the architecture.

**Mechanism**: a **Build Run Summary** written to `GITHUB_STEP_SUMMARY` (status, what changed, test results, cost spent, deploy outcome + a link to that deployment's Fly log viewer). The raw OpenHands `--json` JSONL event stream is uploaded as a build artifact for deep-dive debugging. A curated, machine-readable **Build Run Report** (same fields as the Summary) is produced alongside it for future tooling. The Summary also leads with the verification counts for the last round, its limitations, and a per-round scoreboard (checks passed / failed / blocked / not run, and open blocking findings); the same data is in the Report and in `artifacts/progress.json`. The Summary has a row per stage (Agent, rounds used, cost, verdict, and the context numbers below) plus the release outcome, and each Agent invocation uploads its own JSONL artifact; the Report carries the same fields. **OpenHands is pinned in `agents/openhands-version.txt` (installed by every workflow that runs it), so an upstream release cannot change the CLI under an unattended run; changing the pin is a deliberate edit, tested with the smoke and replay suites first. **Tracing is off on purpose:** an experiment with `openhands` 1.16.0 (SDK 1.21.0) found that setting the `OTEL_EXPORTER_OTLP_*` variables does export spans to an OTLP endpoint, but the run then failed in the SDK's tracing code (`observe() got an unexpected keyword argument 'rollout_entrypoint'`) before making a model call, while the same run without the variables worked. Revisit with a newer pin. The same experiment confirmed the CLI will talk to any OpenAI-compatible endpoint set in `LLM_BASE_URL`, so a local stub model can stand in for DeepInfra in orchestration tests. **Context tracking**: each Agent invocation is one fresh LLM conversation, and the Orchestrator reads OpenHands' persisted state after it to record LLM calls, input (and cached) and output tokens, condenser calls, and the **peak context**, the largest prompt in any single call. The Summary shows these per stage and the run's highest peak; `limits.context_goal_tokens` in `agents/profiles.yml` (100,000) is a goal, not a limit, and stages over it are flagged. First measurement ([#32](https://github.com/ojones/ai-factory/issues/32), a small notes API): peaks of 29k to 54k, the coder highest. If peaks cross the goal on real Intakes, the planned response is to split the coder into planned steps, each its own invocation. On failure — a crash, the cost/time budget exhausted before CI went green, or the review-round limit reached without a clean verdict — an explicit workflow step auto-creates a GitHub Issue in the Managed App's repo, distinguishing which.

## Secrets

A request that needs a third-party secret (an API key, a signing secret) is not refused. The planner lists each as `secrets: [{name, purpose, read_by}]` (names like `OPENWEATHER_API_KEY`, never one of the Factory's own), and the run stops right after the planner as `awaiting_secret` (target: planning stops, STEP 2.3, before any child is filed) until every name exists as a GitHub Actions secret on the app's own repository. It is an answer, not a failure (like `refused`, `ANSWERED_ENDINGS`): nothing is retried, filed or learned from, and the Intake stays open. The Intake comment gives each name and the exact `gh secret set NAME -R owner/app` command; the command prompts for the value, so it never appears in an issue, comment, commit, log or artifact. The declared names are recorded on the Intake (a hidden `factory-secrets` marker in a comment, and in each child issue's plan metadata), and **every later start checks them first**, in `setup`, before the planner, coder, reviewer or tester is paid for: a re-run, a retry and each child of a plan all stop as `awaiting_secret` if a name is missing (`gh secret list`, names only). The only spend before the first check is the planner call that discovers the need (about $0.05), because nothing can know sooner. The coder is told the secrets exist as `process.env.<NAME>`, reads each in one place, fails closed, and lists names and purposes (no values) in `secrets.json`; the Orchestrator rejects a commit that adds a real secret value (it is discarded, never pushed) or lists a name the plan did not declare. The Starter's protected deploy workflow copies only the names in `secrets.json` to Fly, through stdin, in the deploy job alone, refuses the Factory's own names and fails if a value is missing. The workflow lists each declared secret as an ordinary `NAME: ${{ secrets.NAME }}` line between two markers, written by the Orchestrator (`wire_secrets`, committed locally before the coder starts and pushed with its work, and kept when template sync copies the file over); it never reads the whole `secrets` context, because GitHub flags such a workflow as possibly malicious and refuses to run it until a person approves (found live on 2026-10-15). App Staging switches on GitHub's secret scanning with push protection. A pasted value in an Intake is still refused at the start (INV-40). Residual risk, accepted: the app's own code holds the value at runtime, so the reviewer rubric limits a secret to the call that uses it. Not built yet: the scan of artifacts before upload, and the daily pass for secrets older than 90 days and orphans (ticket 31). INV-48 to INV-50.

## Learning loop

Every Build Run, released or not, is a chance to improve the system, not only to alert someone. `orchestrator/retrospective.py` (the **retrospective**; it replaced the post-mortem, which ran only after bad endings) runs as its own workflow step after `finalize` (`if: always()`) and never fails the run:

1. **Facts**: a deterministic record of the run (outcome, per-round blocking findings and which recurred, time and cost per stage, the improvements the reviewer and tester suggested), uploaded as `retrospective-facts.json`.
2. **Lesson issue**: one `factory-learning` issue in ai-factory per distinct failure. The title carries a fingerprint (outcome plus the first meaningful words of the recurring findings) so a repeat comments on the open issue ("Happened again") instead of opening a new one. Each open minor finding also becomes a suggestion issue in the Managed App's own repo and a `factory-learning` issue in ai-factory.
3. **Bugs and improvements**: the tester only notes which checks failed (`bugs`). They belong to the Managed App's own story, so the retrospective adds them to the Update App Intake that started the run (a comment, the `bug` label) instead of opening an issue, and the fix that follows carries the bugs among its requirements (target: the fix child; today: the retry puts the start label back on that same issue, bounded by `fix_request_max_attempts`). Only a Factory-side cause opens a new issue. The reviewer and tester each also end their JSON with `improvements` (target `managed_app` or `factory`, a one-line summary, evidence). They only suggest. The retrospective files them, capped per run: a `managed_app` one is a suggestion in the app's own repo, a `factory` one is a `factory-learning` issue. **Before opening any issue it looks at the open ones**: a title that shares most of its content words with an open issue (`similar_open_issue`, reworded repeats still match) gets a comment with the new context instead of a duplicate. Having the Orchestrator file them keeps the run short (the Agents make no extra calls and hold no GitHub credential) and keeps a noisy model from flooding the trackers.
4. **Retrospective Agent** (`agents/prompts/retrospective.md`): runs only when there is something new to look at. It names a root-cause category (`prompt_gap`, `template_gap`, `orchestrator_gap`, `spec_ambiguity`, `model_limit`, `infra`) and makes the smallest change that would stop the problem for every future Managed App. It acts on the first occurrence; it makes no change for `infra`, `spec_ambiguity` or `model_limit`.
5. **Pull request**: the Orchestrator, not the Agent, keeps only changes under `agents/`, `templates/starter/`, `orchestrator/` and the docs (never `.github/` or the Starter Template's protected files), runs the unit tests, pushes a `learning/run-<id>` branch with the PAT and opens a PR for a human to review. The Agent holds no credential and runs outside the Build Run's cost cap, bounded by `retrospective_timeout_minutes`.
6. **Report on the story**: a short summary (outcome, passes and cost, dark feature or regression, what was filed) is commented on the issue that started the run, once per run, whether it released or not.

The "no branches, no PRs" rule in [STANDARDS-CODING.md](STANDARDS-CODING.md#git-workflow) applies to Managed Apps; changes to the Factory itself go through PRs.

**Built since** (unit-tested; none of the GitHub, Agent or workflow parts has run yet):
- **More lessons than stuck runs.** `lessons_from` also records a release the watchdog switched off, a clean run that needed 3 or more review passes, a first test pass the coder had to fix, a run that spent 70% or more of its cap, and a stage over 15 minutes, at most 3 per run, each a `factory-learning` issue with a stable fingerprint.
- **Fix ineffective.** A lesson whose issue was closed (its fix merged) and comes back is reopened with the `fix-ineffective` label and a comment saying the change did not work, so the retrospective Agent reconsiders it, and undoing that change with a new one becomes an option.
- **Recurrence.** Every `factory-learning` lesson, minor finding and factory improvement is counted: a hidden `seen` marker in the issue body holds the distinct run URLs and their apps (a retry of the same run adds nothing), and the label `recurring` is added at the threshold. The Agent's analysis and fix PR for one of these waits until `limits.promote_after_runs` (default 2) distinct runs have seen it; a severe lesson (an audit violation, a watchdog switch-off), a stuck run and a fix-ineffective reopen go at once. A one-off is still recorded and counted, so the second sighting promotes it. Set 1 to act on the first sighting.
- **Lint rules come from the retrospective Agent, not a separate role.** For a test-quality, style or flag-pattern finding a lint rule can catch, its brief is lint-first: a precise `no-restricted-syntax` entry in the Starter's `eslint.config.mjs` (additive, so it can auto-merge, INV-15) with a failing and a passing case in `agents/lint-fixtures/cases.json`, which `orchestrator/starter_lint_test.py` runs in the PR checks. The Agent never edits an app's code; each app's coder fixes what the rule reports, in the template-sync Update App Intake.
- **Fix-type ladder.** The retrospective prompt prefers a deterministic check (lint or type rule, test, Starter Template script), then a Starter Template default, then a short prompt instruction (removing or merging one before adding one), then orchestrator code. It may not make the reviewer report fewer findings.
- **Regression fixture.** The Agent adds a smoke case, replay case, test or lint rule, or says why not (`no_fixture_reason`); the PR body states which. `.github/workflows/factory-checks.yml` runs the orchestrator unit tests, the Starter Template's install, type-check and tests, and the reviewer smoke fixtures (when a prompt or fixture changed) on every PR.
- **Credential and caps.** The Agent gets its own single-model credential limited to `retrospective_cost_cap_usd` (default $0.50) and never the parent key; at most `max_open_learning_prs` (3) learning PRs are open at once.
- **Merge policy.** A learning PR merges itself only when its diff is additive (no deleted lines) and touches only lint or formatter config in the Starter Template; the checks workflow recomputes this and merges after the checks pass. Prompt, standards, orchestrator and everything else wait for a human. Making the checks block human merges as well needs "unit", "starter" and "reviewer-smoke" set as required checks in branch protection, which is a repository setting.
- **Factory Run.** Adding `ready-for-factory-run` to a `factory-learning` issue runs the same Agent and PR path for that lesson (`orchestrator/retrospective.py lesson <n>`, `.github/workflows/factory-run.yml`).

**Template sync**: an app is seeded once, so each app carries `.factory-template`, the ai-factory commit its template files correspond to (App Staging writes it; an older app has none, so the commit current when its repo was created is used). When `templates/starter/` has changed since an app was synced (a nightly pass at 07:47 UTC or a manual run of `template-sync.yml`, `orchestrator/template_sync.py`; a merge to `main` does not start it), one Update App Intake per behind app is filed with the template's own diff and started at once. The coder applies it to the corresponding files, keeps the app's own code, merges by intent where the app changed the same file, and writes the new commit into `.factory-template`. It needs no flag (tooling users cannot see). Files an Agent may not change (`.github/`, `fly.toml`, `fly/`, `feature-flags.ts`; the lint and formatter config is copied by the Orchestrator) are listed in the Intake as not applied, for a person; `package-lock.json` is regenerated, not diffed. One Intake per app and target commit (a failed one is not refiled; its fix request follows the usual chain), one open at a time per app. It has not yet run against a real app. **Not built yet:** a weekly pass that clusters near-duplicate lessons (the fingerprint is the first six meaningful words) and counts distinct runs and apps.

## Intake

A person, or an automated source, asks the Factory for work with an **Intake**: a GitHub issue on this repo (ai-factory) that is the **parent** of everything that follows. **Target** (STEP 1.1 to 2.6; not built yet, see the Built today block below for what runs):

**Two kinds of Intake.** A **New App Intake** (STEP 1.1; label `new-app-intake`; form `.github/ISSUE_TEMPLATE/new-app-intake.yml`) is titled the Managed App's name (kebab-cased for the eventual repo name) and carries a free-text description of what to build (the Intake Spec) and an optional cost-cap override (defaults to the standard per-Build-Run cap and may not exceed the configured ceiling). An **Update App Intake** (STEP 1.2; label `update-app-intake`; form `update-app-intake.yml`) names the app, what should change and an optional cost cap. The automated sources file the same Update App Intake with the PAT (STEP 1.3): template sync, maintenance, production feedback and flag retirement, and `approve-retire` for a dark feature. The submitter edits and discusses the issue freely until it is ready.

**Planning starts when the label is applied** (STEP 2.1). There is no `begin-planning` label and no `ready-for-staging`: a form applies its label when the issue is created, which fires `issues: labeled` (checked in ticket 01), and an automated source applies it with the PAT, because a label set with the Actions token starts no workflow. `plan.yml` plans for both kinds: a New App Intake from its spec alone (no repo exists yet), an Update App Intake from the app's code. It ends in one of three ways. **Refused** (STEP 2.2): the comment says why and what could be built instead. **Stopped for a person** (STEP 2.3): a blocking question, a plan `planner.py` rejects, or a missing secret; the comment says what to fix, and the retry is to edit the issue, remove the label and apply it again. **Planned** (STEP 2.4). Planning is idempotent: a parent that already has children is not planned again, and a failed planning leaves the parent re-plannable and files no orphan children.

**Child tickets** (STEP 2.4). A plan is filed as one child per change set, as GitHub sub-issues of the parent (create the issue, then add it by its numeric id; a child has exactly one parent). Each child's body is a complete set of coding instructions: the task, numbered acceptance criteria, how each is verified, what is out of scope, whether it is internal only and the secrets it needs. Its `factory-plan` marker records its `kind` (`staging` or `update`), the flag story number, its `size` (`S` or `M`; a larger change set is split) and what it depends on. Order is expressed with GitHub's native issue dependencies; a child is ready when every blocker is closed, which is checked from each blocker's state, never from the count. A change set is the smallest slice that is independently releasable and independently reverted by flipping one flag; none works only while another's flag is on; data changes are additive. At least one child is always filed. A Build Run reads its child (and, from the parent, only its number for the repo marker and the comments), and `proceed-with-change` is only ever put on a child whose body has a marker.

**The first child of a new app is the staging child** (STEP 3.1, 3.2): `kind: staging`, no flag and no business logic. Its criteria, in order: the repo is created from the Starter Template and CI is green; the deploy is healthy on Fly; the feature-flag service is connected and a flag round trip works; the Preview Token path works; the declared secrets are present; a boot and health smoke test passes. Every business-logic child depends on it and carries its own flag. App Staging runs when `proceed-with-change` is put on the staging child.

**Hand-off is automatic, one child at a time** (STEP 2.5, 6.3). The planner puts `proceed-with-change` on the first child with no dependencies. When a child's Build Run succeeds, `finalize` closes it (STEP 6.1) and the Orchestrator, with the PAT, gives `proceed-with-change` to the next open `waiting-on-plan` child whose dependencies are all closed, so an app never has two pending Build Runs (GitHub keeps only one pending run per concurrency group). A failed child stays open and its siblings keep waiting (STEP 4.14). The Orchestrator closes the parent when its last child closes (STEP 6.4); GitHub does not close a parent by itself. Fix children (STEP 7.1) are inserted ahead of the failed child by the same rules.

**Built today (none of the Update flow has run on GitHub yet).** A New App Intake is an issue made from the *New App Intake* form (label `new-app-intake`), and adding **`ready-for-staging`** fires a workflow (`issues: labeled`) that runs App Staging and dispatches one Build Run from the Intake text, with no plan; the workflow refuses (commenting why) if another `intake` issue is already past this label or a Build Run is in flight, because v1 runs one Managed App through Intake, App Staging and Build Run at a time (`max_simultaneous_build_runs`, below). On success the Intake issue is closed with a comment linking the new Managed App's repo. A change request for an app the Factory already built is a GitHub issue made from the *Update App Intake* form (label `update-app-intake`; `.github/ISSUE_TEMPLATE/update-app-intake.yml`); adding the label **`proceed-with-change`** starts it at once: `.github/workflows/update-app-intake.yml` runs `orchestrator/update_intake.py start`, which refuses (comments, removes the label) unless the app's repo exists and carries the `Intake: <factory repo>#<n>` marker App Staging wrote, then labels the issue `app:<slug>` and dispatches a Build Run, which runs the planner first. One change set becomes that run's task and spec. Several change sets are filed by the Build Run as child issues (labels `update-app-intake`, `app:<slug>`, `plan:<parent>`), `proceed-with-change` goes to the first with nothing to wait for and `waiting-on-plan` to the rest, the run ends as `planned`, and `advance` starts the next sibling when a child's run succeeds. A plan that fails `orchestrator/planner.py` or has a blocking question stops the run, comments and removes `proceed-with-change`. The planner can be switched off with `limits.planner_enabled: false`. The labels are added with the PAT, because events made by the Actions token do not start workflows.

Still open: nothing yet stops a second `proceed-with-change` on an issue whose Build Run is already running; the second run queues behind it and re-does the work. Requirements (`REQ-n`) and the numbered acceptance criteria are only as good as the planner makes them; Intake triage and an owner-confirmed criteria echo are an open ticket.

**Parallel apps, built but off.** How many Managed Apps run at once is one setting, `max_simultaneous_build_runs` in `agents/profiles.yml` (default and fallback 1), read by both `infra/app-staging/stage.sh` and the Build Run's wait loop; raising it lets that many apps through Intake → App Staging → Build Run together, still one writer per app (the workflow's `concurrency: build-run-<app>`). Do not raise it before Agents run as a separate OS user (a known gap above, open ticket) and before queued runs stop being dropped (open ticket: GitHub keeps one pending run per concurrency group). Every Intake that reaches staging gets an `app:<slug>` label, and after each Build Run the Orchestrator rewrites a pinned **App State issue** in the Managed App repo (recent runs, every flag a run released and its state as of the release) and a **registry issue** in ai-factory (one row per app, linking each State issue); these are issues rather than files on `main` so they never trigger a deploy. Not yet built: requirements (`REQ-n`) and acceptance criteria in the State issue, which wait on Intake triage. Plan and tickets: [.wayfinder/orchestrator-hardening/](.wayfinder/orchestrator-hardening/map.md).
→ [issue #17](https://github.com/ojones/ai-factory/issues/17)

## Deployment provisioning

**App Staging** creates only the baseline of a new Managed App — repo, seeded code, secrets — then hands off. Coding, review, and deployment all happen afterward, in Build Runs.

**Credential: one fine-grained personal access token**, scoped to the owner's personal GitHub account with **no expiration**, stored as an Actions secret in ai-factory. A GitHub App installation was the earlier pin but cannot work: installation tokens get `403 Resource not accessible by integration` on `POST /user/repos` for personal accounts, so repo creation — the first step of every App Staging run — is blocked (findings: [issue #20](https://github.com/ojones/ai-factory/issues/20)). The PAT must cover repository creation, contents, workflows (to push the seeded `.github/workflows/` files), secrets write, and actions (to dispatch); confirmed working end to end in App Staging (issue #31): repo creation, secrets write, a contents push that includes `.github/workflows/`, and a workflow dispatch. A fine-grained PAT cannot be created or rotated by API, so changing it is a manual step. **Accepted tradeoff:** repo creation forces "All repositories" scope, so the PAT can also write secrets in ai-factory and any other repo the owner has. A separate dedicated GitHub account to contain this was considered and rejected for v1 (one owner; extra identity to maintain). A GitHub org (which would make the App route work) was rejected for the same setup-cost reason; revisit if collaborators are added.

**Repos**: public, under the owner's personal account, named from the Intake issue title. Public means unlimited Actions minutes and plain GHCR pulls.

**Seeding**: the Starter Template stays in this monorepo at `templates/starter/` as the single source of truth — no separate template repo. App Staging creates an empty repo, writes the tracked files of `templates/starter/` (via `git archive`, never the working directory, so ignored files like `node_modules` can't leak in), adds `INTAKE.md` (the Intake Spec as submitted, a link to the Intake issue, and the cost cap used — a snapshot, never edited afterward), and makes one initial commit.

**Secrets pushed into the new repo**: `FLY_API_TOKEN` (the single shared Fly org-level token), `GROWTHBOOK_CLIENT_KEY` (see [Feature-flag infrastructure](#feature-flag-infrastructure)), and `PREVIEW_TOKEN`. The preview token is derived as `HMAC(master secret held in ai-factory, app slug)` rather than stored per app, because GitHub secrets are write-only: the Build Run recomputes it to exercise a dark feature, with no per-app storage. No DeepInfra credential is pushed: the Build Run workflow lives in ai-factory, checks out the Managed App repo with the PAT, and mints each run's capped credential in the same job, so the DeepInfra parent key never leaves ai-factory and never reaches an agent's environment.

**Fly app**: not created by App Staging. `fly/provision.sh` creates it idempotently on first deploy, deriving the name from the repo name. Fly app names are unique across all of Fly, not just this account, so a common name can already be taken by a stranger and the first deploy would fail mid-Build Run. App Staging therefore checks the name up front with a read-only call to the Fly Machines API (`GET /v1/apps/<name>`: 200 ours, 404 free, 403 taken by someone else) and refuses on a collision, before creating the repo or anything else; the Intake Issue Form warns about this too ([STANDARDS-DEPLOYMENT.md](STANDARDS-DEPLOYMENT.md#starter-template-contents-workflows-and-fly-config)).

**Idempotency**: every step is check-then-act, so App Staging is safely re-runnable after a partial failure (today by re-adding the `ready-for-staging` label; target: by re-adding `proceed-with-change` to the staging child). Repo ownership is proven by a marker in the repo description, `Intake: ojones/ai-factory#<N>`. A rerun adopts an existing repo only if the marker matches this Intake issue; any other pre-existing repo with that name (including `ai-factory` itself) is a hard stop, with an explanatory comment on the Intake issue, and nothing is ever overwritten. Any failed or refused run comments on the Intake issue and removes the start label (today `ready-for-staging`), since re-adding a label that is still present would not fire the workflow. The seed push is also the first deploy: it triggers the new repo's Test Gate and Build (in parallel), then Deploy once both are green, so its secrets and kill switch are created first.

**Teardown**: the manual `Teardown` workflow (`infra/app-staging/teardown.sh`, `workflow_dispatch`, dry run by default) removes one Managed App: destroys its Fly app, revokes its GrowthBook SDK connection and deletes its repo (the fine-grained `FACTORY_PAT` needs the Administration: read and write repository permission). It refuses any repo whose description lacks the Intake marker, and refuses while a Build Run is in flight. GrowthBook's REST API cannot delete flags, so the script archives each of the app's `<app>.*` flags with an update call (they remain in the project, archived). The run ends with a table of outcomes per resource. Nothing runs it automatically; the project skill `.claude/skills/teardown-managed-app/` tells an agent how to drive it, always with per-app confirmation from the user.

**Handoff**: App Staging's last step dispatches the Build Run workflow with only the Intake issue number and app name (target: the staging child's number and the app name). The Build Run reads the task and cost-cap override from the issue body when it starts and snapshots it, so later edits don't affect a run in flight. Today the Intake issue then closes (see [Intake](#intake)); target: the staging child is the first Build Run, `stage.sh` comments the repo link on the parent and leaves it open, and the parent closes when its last child closes (STEP 6.4).
→ [issue #20](https://github.com/ojones/ai-factory/issues/20), [issue #23](https://github.com/ojones/ai-factory/issues/23)

## Feature-flag infrastructure

**Tool: [GrowthBook](https://www.growthbook.io)** (MIT core), with Managed App code written against **OpenFeature** rather than GrowthBook's SDK directly. Runner-up: Unleash.
→ [issues/16](.scratch/orchestrator-spec/issues/16-which-feature-flag-tool.md)

**Hosting**: one shared, always-on GrowthBook instance — not one per Managed App — backed by a managed MongoDB Atlas free-tier cluster (GrowthBook requires MongoDB, not Postgres). The Orchestrator holds one manually-created, admin-scoped GrowthBook Personal Access Token (a one-time setup exception to full automation, since GrowthBook's API can't create admin keys itself).

**Per-Managed-App isolation**: self-hosted GrowthBook's free/OSS tier caps at 1 project per organization — confirmed empirically (`402` on a second `POST /v1/projects` call) and corroborated by GrowthBook's own pricing page. Every Managed App shares that one project; App Staging no longer creates a project per app. Multi-org mode (`IS_MULTI_ORG`) was considered and rejected: its self-hosted licensing status is unresolved in GrowthBook's own docs (described as a free env var, yet "Multi-tenant Mode" is marketed Self-Hosted-Enterprise-only), and — decisively — GrowthBook exposes no REST API to create organizations programmatically, only a manual/UI join flow, which would break one-call automation regardless of licensing. Paid Self-Hosted Enterprise was rejected as sales-quote-only with no disclosed price. Running a separate GrowthBook instance per Managed App was rejected: the Factory wants one shared data source, and per-app instances aren't free (each needs its own running service + MongoDB cluster). Switching feature-flag tools entirely was rejected too: every other self-hostable OSS alternative (Unleash, Flagsmith, PostHog) converges on the same 1-project-per-free-instance cap, and the one exception found (Flipt) carries a non-OSI "Fair Source" license, a worse tradeoff than GrowthBook's MIT core plus this app-naming workaround. → [Decide GrowthBook per-Managed-App flag isolation (#22)](https://github.com/ojones/ai-factory/issues/22).

Isolation between Managed Apps is therefore by **flag-key naming only**, not by any GrowthBook access boundary — every Managed App's SDK connection key can technically fetch every other app's flag payload. This is an accepted tradeoff for this personal project, not an oversight. See [STANDARDS-FEATURE-FLAGS.md](STANDARDS-FEATURE-FLAGS.md#code-wiring) for the naming convention this forces.

During App Staging, the Orchestrator calls GrowthBook's REST API once to create an app-scoped, read-only SDK connection key, named for the app, against the single shared project (no project creation call anymore), and pushes it into the new repo's secrets alongside the Fly token. On a rerun after a partial failure, any existing key with that name is revoked and a fresh one minted and re-pushed. In the same step it creates the app's `<app-slug>.global-kill-switch` flag in GrowthBook and turns it **on** if it doesn't already exist (never touching an existing one, so an owner's manual off sticks). This is required, not optional: the kill switch fails closed, so until the flag exists and is on, a new Managed App serves only its maintenance response. One key per Managed App is still minted — it buys no isolation, but keeps revocation, rotation, and GrowthBook's own per-connection usage view organized per app.
