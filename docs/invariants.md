# Design invariants

The "must" rules of the Orchestrator and Starter Template, each with an ID. Every row has a test in [orchestrator/invariants_test.py](../orchestrator/invariants_test.py), named `test_invNN_...`, and a test checks that this table and the test file list exactly the same IDs, so a rule cannot be added here without a test or dropped from the tests silently. The Step column names the closest step of [the flow spec](flow-spec.md) the rule enforces. The reasoning for each rule is in [ARCHITECTURE.md](../ARCHITECTURE.md) (Managed app standards).

Some tests exercise the code (what the rule says must happen), some read a file (the rule is a property of a workflow, a template or the docs), and some compare the docs with `agents/profiles.yml` so that the two cannot drift apart. [run_audit.py](../orchestrator/retrospective/run_audit.py) checks the same kind of rule against what a real Build Run actually did.

|---|---|---|---|
| INV-01 | An Agent runs with a whitelisted environment: its own credential and role inputs, never the PAT, the Fly token, the GrowthBook admin key or the DeepInfra parent key. | ARCHITECTURE: Credentials | 4.3 |
| INV-02 | A coder commit that touches a protected file (`.github/`, `fly.toml`, `fly/`, the flag wrapper, `INTAKE.md`, the lint and formatter config) is rejected. | ARCHITECTURE: Agents and Build Run stages | 4.3 |
| INV-03 | A release happens only when CI is green, the deploy is healthy, the tester passed and the reviewer is clean, all for the same SHA. | ARCHITECTURE: stage 5 | 4.12 |
| INV-04 | The reviewer's verdict is derived from its findings; the model's own `verdict` field is ignored. | ARCHITECTURE: Reviewer | 4.5 |
| INV-05 | A tester check passes only in the state `passed`; `failed`, `blocked` and `not_run` all keep a change from releasing. | ARCHITECTURE: Tester | 4.9 |
| INV-06 | The release step switches on only the story's own flag (named after its own issue; an earlier attempt of that issue may have created it, off); it never creates a flag, and any other flag that already exists in GrowthBook is never touched. | ARCHITECTURE: stage 5 | 4.13 |
| INV-07 | The watchdog switches off only the flags its own run released. | ARCHITECTURE: stage 5 | 4.13 |
| INV-08 | The Preview Token the Build Run computes is the one the shell script computes for App Staging. | ARCHITECTURE: Secrets pushed | 4.9 |
| INV-09 | Each Agent invocation's credential is a single-model scoped JWT limited to what is left of the run's cap. | ARCHITECTURE: Cost guardrails | 4.3 |
| INV-10 | An Intake cost-cap override above the configured ceiling, or not above zero, is refused. | ARCHITECTURE: Cost guardrails | 4.1 |
| INV-11 | The review-round limit stated in ARCHITECTURE.md is the one in `agents/profiles.yml`. | docs match config | 4.5 |
| INV-12 | The coder and reviewer models named in ARCHITECTURE.md are the ones in `agents/profiles.yml`. | docs match config | 4.3 |
| INV-13 | Every role prompt named in `agents/profiles.yml` exists in the Factory repo, which Managed App repos never contain. | ARCHITECTURE: Agents | 4.3 |
| INV-14 | The retrospective Agent can change only prompts, the Starter Template, the orchestrator, `ARCHITECTURE.md` and the glossary, never workflows, protected template files or anything under `docs/`. | ARCHITECTURE: Learning loop | 6.2 |
| INV-15 | A learning PR auto-merges only when it is an additive change to lint or formatter config (the `auto-merge` job takes only `learning/` branches; a Factory Change merges by INV-66). | ARCHITECTURE: Learning loop | 7.3 |
| INV-16 | The Starter Template's flags fail closed: no flag is read with a default of `true`, and the Starter has no app-wide kill switch (the flag of the change is the only switch). | ARCHITECTURE: Feature-flag infrastructure | 4.7 |
| INV-17 | The Summary, Report and failure Issue are written even after a crash, breach or cancel: `finalize` and the retrospective step run `if: always()`. | ARCHITECTURE: Visibility | 6.2 |
| INV-18 | Build Runs of one app never overlap, a running one is never cancelled, and none waiting is dropped: the Build Run workflow's concurrency group is per app with `cancel-in-progress: false` and `queue: max` (verified with a probe: without it GitHub cancels all but one pending run). | ARCHITECTURE: Intake | 4.1 |
| INV-19 | A run whose rounds leave the same checks failing and the same findings open stops instead of spending its remaining budget. | ARCHITECTURE: stage 6 | 4.14 |
| INV-20 | The retrospective Agent never receives the DeepInfra parent key; it gets a capped scoped credential or does not run. | ARCHITECTURE: Learning loop | 6.2 |
| INV-21 | Every workflow that installs OpenHands pins it to the version in `agents/openhands-version.txt`, so an upstream release cannot change an unattended run. | ARCHITECTURE: Visibility | 4.3 |
| INV-22 | An Update App Intake can change only a repo this Factory created (its description carries the `Intake: <factory repo>#<n>` marker); anything else is refused and nothing is dispatched. | ARCHITECTURE: Intake | 1.2 |
| INV-23 | A change set of a plan starts only when every blocker of it is closed, and only one starts at a time (none while another is in flight or stopped), so an app never has two pending Build Runs (GitHub would drop one); the last child to close closes the parent. | ARCHITECTURE: Intake | 6.3 |
| INV-24 | `update-app-intake.yml` starts a Build Run only when the label `proceed-with-change` is added to an `update-app-intake` issue (and INV-55 holds for it), and the good endings (`released`, `nothing_to_release`) are defined once, in `shared/outcomes.py`, which every module uses. | ARCHITECTURE: Intake | 2.5 |
| INV-25 | Nothing is ever reverted in git: code is fixed forward and `main` keeps every commit. The one exception to leaving the live app alone is a regression, which means users are exposed to broken behaviour: either the tester saw, through a helper, behaviour that was live before the run stop working, or a change that went live with no gate (it has no flag, or its declared flag is read by no code, INV-52) failed a check: the run ends as `regression` and the app's own CI (`rollback-fly.yml`, given to existing apps by template sync) redeploys the previous version's image. No other ending rolls anything back, a failed rollback is reported instead of hidden, and the Orchestrator has no code path that commits a revert. | ARCHITECTURE: Rollback of a regression | 4.11 |
| INV-26 | A child that ends badly, and every other failure event, is judged once by the Retrospective (cause, target, verdict) and its failure is handled once: the story gets a failure comment, an app fix is one bug Intake planned like any Intake, a Factory fix is one fix request in ai-factory (an `orchestrator_gap` stays that fix request until it has been seen `promote_after_runs` times, then moves to one Factory Change Intake, INV-63 to INV-66), no cause is `needs-human`. The same event reported twice is one. | ARCHITECTURE: Fix first | 7.1 |
| INV-27 | Fix first, never retry the unchanged child, bounded and unattended: the failed child waits on its bug Intake (blocked by it) and resumes through the normal advance when the Intake closes; attempts are counted along the `fix_for` chain and after `fix_attempts_max` (2) the child is `needs-human`. | ARCHITECTURE: Fix first | 7.5 |
| INV-28 | A tester check that is marked `passed` but whose own evidence admits it was not observed counts as `not_run`, so it cannot release a change; evidence backed by a test run, or ordinary evidence, still passes. | ARCHITECTURE: Tester | 4.9 |
| INV-29 | A model provider that refuses every request because the account has no balance (HTTP 402) stops the Build Run at once as `provider_blocked`, before any work if the one-token preflight catches it: nothing is retried, no self-starting fix request, lesson or retrospective Agent is started, and one deduplicated alert asks for a top-up. | ARCHITECTURE: Cost guardrails | 4.14 |
| INV-30 | A tester result that cites an `api-check` the helper saw fail cannot stay `passed`, one citing a check the helper never ran cannot either, and a failure the helper logged that the report left out is added as a failed check: the helper's observation outranks the model's judgement. The helper only ever calls the base URL. | ARCHITECTURE: Tester | 4.9 |
| INV-31 | Production feedback is an event source, not a filer: it cannot flood the trackers or the budget (one event per fingerprint, `min_occurrences`, `max_per_app_per_day`, owner-written `escaped-defect` only), and what it finds is judged by the Retrospective before any ticket exists. | ARCHITECTURE: Production feedback | 8.3 |
| INV-32 | An Agent whose event stream stops growing for `agent_stall_minutes` is killed (its whole process group) and counts as a failed attempt, so a silent Agent cannot hold a Build Run for the full `agent_timeout_minutes`; the overall timeout still applies to a chatty one. | ARCHITECTURE: Cost guardrails | 4.3 |
| INV-33 | Template sync touches an app only through an Update App Intake and never twice for one target: it applies only files an Agent may change (protected files and the lock file are listed as not applied), files nothing when the app is current or nothing applies, and does not refile a target already filed (open or closed) or file while one is open for the app. | ARCHITECTURE: Template sync | 1.3 |
| INV-34 | With `limits.agent_isolation: user`, Agents run as a separate unprivileged account with variables passed by name (no value on a command line), the Orchestrator's git credential travels in the environment and never in an argument, and a run whose start-of-run self-check finds the Agent can read the Orchestrator's environment, the runner's workspace or a credential variable, or can use sudo, stops before any Agent runs. | ARCHITECTURE: Isolation | 4.3 |
| INV-35 | Dependency and base-image updates reach a Managed App only through an Update App Intake that goes through the normal gate: the daily pass turns Dependabot's open npm and Docker pull requests into one self-starting Intake per app and set of updates (never merging a pull request, never refiling a set, never while one is open), reports GitHub Actions updates without applying them, and a template-sync run copies only the allow-listed protected Starter files itself. | ARCHITECTURE: Maintenance | 1.3 |
| INV-36 | The browser helper's observation outranks the tester's judgement, as the API helper's does: a result citing a `ui-check` scenario the browser saw fail cannot stay `passed`, one citing a scenario never run cannot either, and a failure the report left out is added. The helper opens only the app's own origin and logs no Preview Token, and the browser the workflow installs is pinned in `agents/playwright-version.txt`. | ARCHITECTURE: Tester | 4.9 |
| INV-37 | A feature flag is retired by the pipeline, inside an update run that is already coming in for the same app and never in a run of its own: only a flag the State issue records as released, still in `flags.json`, released on an earlier day, with a later Build Run that also ended `released` (the newest release and anything the watchdog switched off are never candidates), at most `piggyback_max` per run, oldest first, never for a fix child; the coder's commit is rejected while code still references a retiring slug; and the flags a run removed from `flags.json` are archived in GrowthBook only when the run ended well. | ARCHITECTURE: Flag retirement | 4.2 |
| INV-38 | A flag and the story it belongs to point at each other: an update's issue gets a `flag:<slug>` label, the flag in its title and a comment with the key, the GrowthBook feature is created, off, at the start of the run with the issue link in its description and an `intake-<n>` tag (and still created without them if GrowthBook refuses), the State issue links each flag to its story. | ARCHITECTURE: Flag stories | 5.2 |
| INV-39 | A bug Intake with `fix_for` plans exactly one child, an ordinary child with a flag of its own (or none), which the failed child waits for. | ARCHITECTURE: Fix first | 7.1 |
| INV-40 | A request the Factory cannot fulfil is refused before anything is built or retried: an Intake containing a real secret value is refused at the start of the run (the comment names the kind, never repeats the value), a plan the planner marks `blocked` (payments, secrets, personal data, an outside keyed service, outside the stack) ends the run as `refused` right after the planner call, and a refusal is not retried, filed as a failure Issue or learned from. | ARCHITECTURE: Intake triage | 2.2 |
| INV-41 | A model swap is decided by code from a measured whole-run pass and is survivable at run time: a candidate is accepted only if its passes are within `max_pass_drop` of the baseline, no safety or refusal task that passed before now fails, its cost is within `max_cost_ratio` and its rounds within `max_rounds_delta`; the candidate runs the real Build Run from a branch with limits that keep passes comparable; and a Build Run replaces a model the provider no longer serves with the role's `fallback_model` before any work, or stops with the reason, while a zero balance stays `provider_blocked`. | ARCHITECTURE: Model swaps | 4.3 |
| INV-42 | Only code the reviewer has passed is pushed: the coder only commits, the reviewer reads the local commit, and the Orchestrator pushes it (which deploys it, dark behind its flag) only on a clean verdict; the tester runs after the deploy, and a fix that CI needed goes through the reviewer again before it is pushed. | ARCHITECTURE: Stages | 4.6 |
| INV-43 | A dark feature (flagged code that never got through its checks) stays dark and is fixed forward; it is removed only after the automatic retries are used up (`needs-human`, `dark-broken`) and a person adds `approve-retire`, which files one Update App Intake that deletes the flag, its code and its tests. | ARCHITECTURE: Dark features | 5.6 |
| INV-44 | The tester's report says what a failure means: a failed `new` check keeps the change dark, and a failed `existing` check that an `api-check` or `ui-check` helper observed is a regression; the model's word alone is not one. The tester only notes what failed (`bugs`), and the reviewer and tester only suggest `improvements`; they file nothing. The retrospective, which runs after every run, puts the bugs on the story's own Update App Intake issue (never a new issue), and files improvements as suggestion or `factory-learning` issues, capped, and never one that matches an open issue (it comments there instead). | ARCHITECTURE: Tester, Retrospective | 4.9 |
| INV-45 | The retrospective Agent is isolated like the Build Run's Agents: it runs as the unprivileged Agent user after the same self-check (no Agent runs if isolation cannot be proven), with a scrubbed environment and a capped scoped key, in a copy of the Factory tree without `.git`. The Orchestrator compares the plain trees and carries over only changes in allowed paths (no symlink, no oversized file, never `.github/`), runs git only in its own checkout, and runs the unit tests of the proposed change as the Agent user in a throwaway copy with no credential in the environment. | ARCHITECTURE: Credentials | 6.2 |
| INV-46 | What blocks or retries is decided from structure, not labels: a reviewer finding blocks only when it is marked blocking, its category can block, and it has a repro or a cited file and line (otherwise it is minor, and a finding without the structure is asked for again); the flag checks that need no judgement are made by the Orchestrator and are always minor; and only a tester check that failed goes to the coder, while blocked or not-run checks are retested and then stop the run for a person instead of costing coder rounds. | ARCHITECTURE: Reviewer, Tester | 4.5 |
| INV-47 | The Starter's lint and formatter config is the Orchestrator's, never the coder's: a coder commit that touches it is rejected, template sync copies it in, and it is committed locally after the run's base and pushed only with the coder's first reviewed work, so a stricter rule never reaches `main` alone and only the coder fixes what it reports. A suppression (`eslint-disable`, `@ts-ignore`, `@ts-nocheck`) added in a diff is named as a minor finding, and every custom lint rule has failing and passing cases that the checks run. | ARCHITECTURE: Agents and Build Run stages, Learning loop | 4.4 |
| INV-48 | A request that needs a third-party secret builds nothing until every declared name exists as a GitHub Actions secret on the app's repository: planning ends `awaiting_secret` (before any child is filed) and every later Build Run checks again at its start, before any Agent, from the names recorded on the Intake; either way it ends `awaiting_secret` (an answer, not a failure: no retry, fix request, failure issue or lesson, and the Intake stays open), the comment gives the exact `gh secret set` command with the name filled in and never a value, and only names are ever read (`gh secret list`). | ARCHITECTURE: Secrets | 2.3 |
| INV-49 | A coder commit that adds a real secret value is discarded and never pushed, and a name in `secrets.json` that the plan did not declare, or that is one of the Factory's own, is rejected; the deploy step copies only the declared names, refuses the reserved ones and fails if a value is missing. | ARCHITECTURE: Secrets | 4.3 |
| INV-50 | No secret value is in an issue, comment, commit, log or artifact: the owner sets it with `gh secret set` (a prompt), only the deploy job sees it, it reaches Fly through stdin, and an Agent's environment never holds it (INV-01). | ARCHITECTURE: Secrets | 4.1 |
| INV-51 | A flag's name is `issue-<n>` of its story and it exists, off, before the coder starts: a plan only says a change set is flagged, the Orchestrator fills in the slug, creates the GrowthBook feature (never touching one that exists) and records it in `flags.json`, and an issue that runs again keeps the flag it had. | ARCHITECTURE: Flag stories | 4.1 |
| INV-52 | A flag that does not exist at release is reported, not made up. If the code reads it the run ends `flag_missing`: a failure, nothing rolled back, with the note that a flag which can be turned on has to be added; if no code reads it the change is live with no gate, so clean tests leave it alone with a note and a failing test ends the run as a `regression` (INV-25), which rolls the deploy back. The notes (`flag_notes`) reach the retrospective. | ARCHITECTURE: Flag stories | 4.13 |
| INV-53 | Every flag in `flags.json` is tested both ways before review: `npm run check` (so the pre-review check) fails a commit whose flag lacks a `withFlag(slug, false, ...)` test or a `withFlag(slug, true, ...)` test, or is checked in more than one place, and a retirement is rejected while the slug is still in source, tests or `flags.json` (comments aside). The check script is the Orchestrator's, not the coder's. | ARCHITECTURE: Feature-flag infrastructure, Target lifecycle | 4.4 |
| INV-54 | A plan is rejected unless every change set can be released and reverted as one: size S or M, at most 6 criteria, naming no change set it does not depend on, and a new app's first change set is the only `staging` one; its children are filed as sub-issues with their dependencies as blockers, once (a parent that has children is not planned again), and a failure part-way removes and closes what was made and raises, so no orphan is left and the Intake can be planned again. | ARCHITECTURE: Code layout | 2.1, 2.4 |
| INV-55 | A Build Run starts and runs only for a planned child: a sub-issue (found through the sub-issues API, not a label or title) of an open plan, whose body has a `factory-plan` marker naming that plan; anything else is refused as not planned yet. The run reads the parent's number and state, never its body. A `kind: staging` child is a first build. | ARCHITECTURE: Code layout | 2.5, 4.1 |
| INV-56 | Planning is its own process: `plan.yml` starts on the intake labels `update-app-intake`, `new-app-intake` and `factory-change` (never on a child ticket, which carries the marker), one run per issue at a time; it files at least one child, plans an Intake that already has children never, and ends `planned`, `refused`, `awaiting_secret` or `needs_human`, each but the first leaving the Intake as it was so that removing and re-adding its label plans it again. | orchestrator-map: Planning | 2.1, 2.4 |
| INV-57 | A planned `kind: staging` child is staged by `app-staging.yml`, never started as a Build Run, and the first business child starts only after deterministic checks pass on the seeded app: CI green on the seed commit, healthy deploy, the app's flag-service connection, the Preview Token cookie, the secrets present and the front page served; a failed check comments the whole picture and leaves the child re-startable. One app is staged at a time. | orchestrator-map: Staging | 3.1, 3.2 |
| INV-58 | Every failure event, failure or warning, gets a verdict from the Retrospective; a failure is never downgraded to `record`; a warning is fixed only when the verdict says `fix` with a reason, and at most `fix_events_per_app_per_day` warnings per app per day. | flow-spec: From a failure to a fix | 6.2 |
| INV-59 | The Try Fix Agent only writes the ticket text from the bug template: it never decides the cause or target and never plans; its answer is validated (checkable requirements, at most `planner_max_criteria`, no secret value) or replaced by the Orchestrator's own text, and a secret-shaped string in the evidence never reaches the model or the public ticket. | flow-spec: From a failure to a fix | 7.6 |
| INV-60 | Whether a bug makes a child wait is decided by the flag's state in the App State, never by a guess: a flag released and still on is released (a regression: an ordinary bug Intake, nothing waits), and one never released, off, or switched off by the watchdog is dark (the bug Intake carries `fix_for` and the story's open child waits). | flow-spec: From a failure to a fix | 8.1 |
| INV-61 | A child with `proceed-with-change` is routed by the `kind` in its marker: a staging child to App Staging, every other child of an app to a Build Run, never both, a `benchmark` child to neither workflow (the benchmark dispatches its own), and a Factory Change child to `factory-change.yml` (it has its own label and never reaches a Build Run). | flow-spec: Route the child | 2.6 |
| INV-62 | A pipeline failure is read by the Pipeline Agent once per failure, a run GitHub never started is not paid for, and the re-runs (`pipeline_retries`) and coder fixes (`pipeline_fix_attempts`) are bounded before a person decides. | ARCHITECTURE: Agents and Build Run stages | 4.8 |
| INV-63 | A Factory Change is refused, not trimmed, when its diff touches a path no Agent may change (`.github/`, the checks, secrets), mixes control-path files with files that merge on green, passes the file or line limit in `agents/profiles.yml`, deletes a test without adding one, raises a model or a spending cap, or adds emphasis to a prompt. | ARCHITECTURE: Learning loop | 9.4 |
| INV-64 | Every Factory Change ends with a reproduction that fails on `main` and passes on the branch, or it does not merge. A ticket that names one has it run on `main` before any Agent starts and no Agent runs if it does not fail there; a ticket that says `none` has the Factory Coder write the test first and the Orchestrator proves that name the same way. A name that is not a test (an option, a path) is never run. | ARCHITECTURE: Learning loop | 9.7 |
| INV-65 | The Factory Change process stops while an open issue carries `factory-change-paused`: nothing is filed, and a person clears it. After a merge, the finding coming back (a failed Build Run is not read; the returning finding stands in for it), a `model-drift` alert, or two `fix-ineffective` changes in a row pause it; the merged change is not reverted, it is fixed forward (INV-68). | ARCHITECTURE: Learning loop | 9.12 |
| INV-66 | A Factory Change reaches `main` only as a pull request on `factory-change/<child>`; the Orchestrator has no code path that pushes it to `main`. It merges itself only when every file it changes is outside the control path, recomputed from the diff by the merge job (the label and the tier in the body are not trusted), and only after `unit`, `starter`, `reviewer-smoke` and `factory-change-gate` pass; a change that touches the control path waits for a person. | ARCHITECTURE: Learning loop | 9.9 |
| INV-67 | No Agent in the pipeline edits `docs/invariants.md` or `docs/flow-spec.md`: the retrospective Agent cannot carry either over, a Factory Change cannot merge either, and a Factory Coder that edits either has the whole change discarded and its ticket ends `needs_human` for a person to edit and restart. Only a person changes the rules and the flow. | ARCHITECTURE: Learning loop | 9.4 |
| INV-68 | No Agent, on the Factory side or the Managed App side, and no Orchestrator code path reverts a commit or a pull request (`git revert`, GitHub's revert, a reset of `main`): a failure is noted, becomes an Intake and is fixed by a new commit and pull request. The only thing taken back is a live deployment, through the app's own CI (INV-25). | ARCHITECTURE: Fix first | 7.1 |
