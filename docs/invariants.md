# Design invariants

The "must" rules of the Orchestrator and Starter Template, each with an ID. Every row has a test in [orchestrator/test_invariants.py](../orchestrator/test_invariants.py), named `test_invNN_...`, and a test checks that this table and the test file list exactly the same IDs, so a rule cannot be added here without a test or dropped from the tests silently. The reasoning for each rule is in [ARCHITECTURE.md](../ARCHITECTURE.md) and the [Standards](../STANDARDS.md).

Some tests exercise the code (what the rule says must happen), some read a file (the rule is a property of a workflow, a template or the docs), and some compare the docs with `agents/profiles.yml` so that the two cannot drift apart. [audit.py](../orchestrator/audit.py) checks the same kind of rule against what a real Build Run actually did.

| ID | Rule | Source |
|---|---|---|
| INV-01 | An Agent runs with a whitelisted environment: its own credential and role inputs, never the PAT, the Fly token, the GrowthBook admin key or the DeepInfra parent key. | ARCHITECTURE: Credentials |
| INV-02 | A coder commit that touches a protected file (`.github/`, `fly.toml`, `fly/`, the flag wrapper, `INTAKE.md`) is rejected. | ARCHITECTURE: Agents and Build Run stages |
| INV-03 | A release happens only when CI is green, the deploy is healthy, the tester passed and the reviewer is clean, all for the same SHA. | ARCHITECTURE: stage 4 |
| INV-04 | The reviewer's verdict is derived from its findings; the model's own `verdict` field is ignored. | ARCHITECTURE: Reviewer |
| INV-05 | A tester check passes only in the state `passed`; `failed`, `blocked` and `not_run` all keep a change from releasing. | ARCHITECTURE: Tester |
| INV-06 | The release step never re-enables or alters a flag that already exists in GrowthBook. | ARCHITECTURE: stage 4 |
| INV-07 | The watchdog switches off only the flags its own run released. | ARCHITECTURE: stage 4 |
| INV-08 | The Preview Token the Build Run computes is the one the shell script computes for App Staging. | ARCHITECTURE: Secrets pushed |
| INV-09 | Each Agent invocation's credential is a single-model scoped JWT limited to what is left of the run's cap. | ARCHITECTURE: Cost guardrails |
| INV-10 | An Intake cost-cap override above the configured ceiling, or not above zero, is refused. | ARCHITECTURE: Cost guardrails |
| INV-11 | The review-round limit stated in ARCHITECTURE.md is the one in `agents/profiles.yml`. | docs match config |
| INV-12 | The coder and reviewer models named in ARCHITECTURE.md are the ones in `agents/profiles.yml`. | docs match config |
| INV-13 | Every role prompt named in `agents/profiles.yml` exists in the Factory repo, which Managed App repos never contain. | ARCHITECTURE: Agents |
| INV-14 | The post-mortem Agent can change only prompts, the Starter Template, the orchestrator and the docs, never workflows or protected template files. | ARCHITECTURE: Learning loop |
| INV-15 | A learning PR auto-merges only when it is an additive change to lint or formatter config. | ARCHITECTURE: Learning loop |
| INV-16 | The Starter Template's flags fail closed: no flag is read with a default of `true`, and the kill switch sits after the health route and before the static files and every other route. | STANDARDS-VISIBILITY, STANDARDS-FEATURE-FLAGS |
| INV-17 | The Summary, Report and failure Issue are written even after a crash, breach or cancel: `finalize` and the post-mortem step run `if: always()`. | ARCHITECTURE: Visibility |
| INV-18 | Build Runs of one app never overlap, a running one is never cancelled, and none waiting is dropped: the Build Run workflow's concurrency group is per app with `cancel-in-progress: false` and `queue: max` (verified with a probe: without it GitHub cancels all but one pending run). | ARCHITECTURE: Intake |
| INV-19 | A run whose rounds leave the same checks failing and the same findings open stops instead of spending its remaining budget. | ARCHITECTURE: stage 5 |
| INV-20 | The post-mortem Agent never receives the DeepInfra parent key; it gets a capped scoped credential or does not run. | ARCHITECTURE: Learning loop |
| INV-21 | Every workflow that installs OpenHands pins it to the version in `agents/openhands-version.txt`, so an upstream release cannot change an unattended run. | ARCHITECTURE: Visibility |
| INV-22 | An Update Intake can change only a repo this Factory created (its description carries the `Intake: <factory repo>#<n>` marker); anything else is refused and nothing is dispatched. | ARCHITECTURE: Intake |
| INV-23 | A change set of a plan starts only when every change set it depends on is closed, and only one starts at a time, so an app never has two pending Build Runs (GitHub would drop one). | ARCHITECTURE: Intake |
| INV-24 | `update-intake.yml` starts a Build Run only when the label `proceed-with-change` is added to an `update-intake` issue, and every module agrees on which outcomes are good endings. | ARCHITECTURE: Intake |
| INV-25 | A Build Run that ends badly and pushed commits leaves `main` as it found it: one new commit restores the starting tree and history is kept. It never reverts over someone else's commit, never reverts a good ending or a release the watchdog contained, and reports a failed revert instead of hiding it. | ARCHITECTURE: Revert on failure |
| INV-26 | A Build Run that ends badly gets its failure handled once: when the cause is the request (or a release the watchdog switched off) the story's own issue gets a comment saying it broke and why, with the retry state hidden in it, and never a second issue; a Factory cause files one Factory fix request per Intake; no cause files an information issue. The same failure reported twice is one attempt. | ARCHITECTURE: Fix requests |
| INV-27 | Self-correction is bounded and unattended and stays on one story: the same issue is restarted (the start label is added with the PAT) with no person reviewing it, a retry never stops to ask a question, a retry keeps the story's flag, and after `fix_request_max_attempts` automatic retries the issue stays open, labelled `needs-human`, attached to its flag, and nothing starts. A Factory-side fix request never starts itself. | ARCHITECTURE: Fix requests |
| INV-28 | A tester check that is marked `passed` but whose own evidence admits it was not observed counts as `not_run`, so it cannot release a change; evidence backed by a test run, or ordinary evidence, still passes. | ARCHITECTURE: Tester |
| INV-29 | A model provider that refuses every request because the account has no balance (HTTP 402) stops the Build Run at once as `provider_blocked`, before any work if the one-token preflight catches it: nothing is retried, no self-starting fix request, lesson or post-mortem Agent is started, and one deduplicated alert asks for a top-up. | ARCHITECTURE: Cost guardrails |
| INV-30 | A tester result that cites an `api-check` the helper saw fail cannot stay `passed`, one citing a check the helper never ran cannot either, and a failure the helper logged that the report left out is added as a failed check: the helper's observation outranks the model's judgement. The helper only ever calls the base URL. | ARCHITECTURE: Tester |
| INV-31 | Production feedback cannot flood the trackers or the budget: one open production-feedback Intake per error fingerprint, at most one open per app, at most `max_per_app_per_day` new ones per app per day, nothing below `min_occurrences`, and an `escaped-defect` issue counts only when the repo owner wrote it. | ARCHITECTURE: Production feedback |
| INV-32 | An Agent whose event stream stops growing for `agent_stall_minutes` is killed (its whole process group) and counts as a failed attempt, so a silent Agent cannot hold a Build Run for the full `agent_timeout_minutes`; the overall timeout still applies to a chatty one. | ARCHITECTURE: Cost guardrails |
| INV-33 | Template sync touches an app only through an Update Intake and never twice for one target: it applies only files an Agent may change (protected files and the lock file are listed as not applied), files nothing when the app is current or nothing applies, and does not refile a target already filed (open or closed) or file while one is open for the app. | ARCHITECTURE: Template sync |
| INV-34 | With `limits.agent_isolation: user`, Agents run as a separate unprivileged account with variables passed by name (no value on a command line), the Orchestrator's git credential travels in the environment and never in an argument, and a run whose start-of-run self-check finds the Agent can read the Orchestrator's environment, the runner's workspace or a credential variable, or can use sudo, stops before any Agent runs. | ARCHITECTURE: Isolation |
| INV-35 | Dependency and base-image updates reach a Managed App only through an Update Intake that goes through the normal gate: the daily pass turns Dependabot's open npm and Docker pull requests into one self-starting Intake per app and set of updates (never merging a pull request, never refiling a set, never while one is open), reports GitHub Actions updates without applying them, and a template-sync run copies only the allow-listed protected Starter files itself. | ARCHITECTURE: Maintenance |
| INV-36 | The browser helper's observation outranks the tester's judgement, as the API helper's does: a result citing a `ui-check` scenario the browser saw fail cannot stay `passed`, one citing a scenario never run cannot either, and a failure the report left out is added. The helper opens only the app's own origin and logs no Preview Token, and the browser the workflow installs is pinned in `agents/playwright-version.txt`. | ARCHITECTURE: Tester |
| INV-37 | A feature flag is retired by the pipeline, inside an update run that is already coming in for the same app and never in a run of its own: only a flag the State issue records as released, still in `flags.json`, released on an earlier day, with a later Build Run that also ended `released` (the newest release and anything the watchdog switched off are never candidates), at most `piggyback_max` per run, oldest first, never in a first build or an automatic retry; the coder's commit is rejected while code still references a retiring slug; and the flags a run removed from `flags.json` are archived in GrowthBook only when the run ended well. | ARCHITECTURE: Flag retirement |
| INV-38 | A flag and the story it belongs to point at each other: an update's issue gets a `flag:<slug>` label, the flag in its title and a comment with the key, the GrowthBook feature is created with the issue link in its description and an `intake-<n>` tag (and still created without them if GrowthBook refuses), the State issue links each flag to its story, and a first build's issue title stays the bare app name. | ARCHITECTURE: Flag stories |
| INV-39 | A story and its flag live and die together: a retry plans and codes behind exactly the flag the failed attempt had (the planner rejects another), tests it like a new flag, and releases it again only when it is the story's own flag, off in production, and the gates passed; every other existing flag is never touched by the release step. | ARCHITECTURE: Fix requests |
| INV-40 | A request the Factory cannot fulfil is refused before anything is built or retried: an Intake containing a real secret value is refused at the start of the run (the comment names the kind, never repeats the value), a plan the planner marks `blocked` (payments, secrets, personal data, an outside keyed service, outside the stack) ends the run as `refused` right after the planner call, and a refusal is not reverted, retried, filed as a failure Issue or learned from. | ARCHITECTURE: Intake triage |
| INV-41 | A model swap is decided by code from a measured whole-run pass and is survivable at run time: a candidate is accepted only if its passes are within `max_pass_drop` of the baseline, no safety or refusal task that passed before now fails, its cost is within `max_cost_ratio` and its rounds within `max_rounds_delta`; the candidate runs the real Build Run from a branch with limits that keep passes comparable; and a Build Run replaces a model the provider no longer serves with the role's `fallback_model` before any work, or stops with the reason, while a zero balance stays `provider_blocked`. | ARCHITECTURE: Model swaps |
