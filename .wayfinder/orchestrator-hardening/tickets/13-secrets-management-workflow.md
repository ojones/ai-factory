## Question

A secret (a third-party API key, an OAuth client secret, a database password, a webhook signing key) is a different kind of task from a code change: no Agent may hold or see its value, the owner has to provide it out of band, and the app needs it at runtime but the repositories and Intake issues are public. Today the Factory simply refuses any request that needs one (Intake triage, ticket 06: the planner's `secrets` category, and a scan that refuses a value pasted into an Intake). That is safe but means nothing that talks to a keyed service can ever be built. What is the secrets workflow, so a request that needs a secret can proceed without the value ever reaching an Agent, a log, an artifact or a public issue?

Decide:

(a) **How a request declares a secret it needs.** The planner already detects the need. Does it produce a structured `secrets` list (name, purpose, where it is read: backend env var, CI) that becomes its own change set or a gate on the plan, and how are names kept consistent (for example `<APP>_<SERVICE>_API_KEY`)?

(b) **How the owner provides the value, and where it lives.** Candidates: `fly secrets set` by the owner, a GitHub Actions secret on the app repo for CI, an owner-run workflow that takes the value through a masked `workflow_dispatch` input, or a secrets manager. It must never pass through an issue body, a comment, a commit, a log or an uploaded artifact (all public). Which path is the default, and what does the Factory do to make it a one-step job for the owner (for example posting the exact command with the name filled in)?

(c) **How the build proceeds without the value.** The coder writes code that reads the secret from the environment and fails closed when it is missing; the tester has no real value, so it needs a documented way to verify the feature against a stand-in (a stub service, a recorded response) and to report the live integration as `not_run`. When is the secret-dependent feature released: only after the owner confirms the secret is set and a post-release check passes?

(d) **Injection and scope.** How the value reaches the running app (Fly secrets, set before deploy so the first boot has it), which Build Run steps and Agents may never see it (the whitelisted Agent environment, INV-01, and Agent isolation, INV-34, already keep the Factory's own credentials away), and least privilege: one secret per service, per app.

(e) **Lifecycle.** Rotation (a scheduled reminder or a Dependabot-style check), what happens when a secret expires or is revoked (the watchdog sees errors; the story is retried on its own issue, which cannot fix a missing secret, so it should become a secrets task), and removal when the feature is retired or the app torn down (`teardown-managed-app` must remove the secrets it created).

(f) **Detection and accident handling.** The pre-spend scan refuses a pasted secret and tells the owner to rotate it. What else: a scan of every Agent commit and artifact for secret shapes before it is pushed or uploaded, and an alert path if one slips through.

## Added context

- Today: Intake triage (`orchestrator/triage.py`, INV-40) refuses a secret value in an Intake and refuses a request whose plan is `blocked` with category `secrets`; the golden Intakes document shows both. The Agent environment is a whitelist with no provider or Fly token (INV-01), and Agents run as a separate account (INV-34).
- The Orchestrator holds `FACTORY_PAT`, `FLY_API_TOKEN`, `GROWTHBOOK_ADMIN_PAT`, `DEEPINFRA_API_KEY`, `PREVIEW_MASTER_SECRET` as Actions secrets on ai-factory (a public repo); app repos get `FLY_API_TOKEN`, `GROWTHBOOK_CLIENT_KEY` and `PREVIEW_TOKEN` from App Staging (`infra/app-staging/stage.sh` `push_secret`). That is the existing pattern for the Factory's own secrets, not for an app's third-party ones.
- The owner prefers unattended operation (no human in the loop by default). A secret is the clearest case where a human step is unavoidable, so the workflow should make that single step as small as possible and let everything else continue automatically.
- Relates to ticket 06 (triage), ticket 03 (security gates: secret scanning in the Test Gate), and `STANDARDS-FEATURE-FLAGS.md` (a secret-dependent feature still ships dark behind a flag and is released only when its gates pass).

## Resolution (2026-10-14)

Decided and documented; **not built** (the owner chose "decide and document only"). Items marked *default* were not put to the owner and can be changed.

**Findings that shaped it.** (1) A `workflow_dispatch` input is not masked and shows on the run page of a public repo, so "a workflow that takes the secret as an input" is unsafe and is ruled out. (2) A GitHub Actions secret is write-only (the API lists names and update times, never values), free, encrypted, and masked in logs, so it meets the owner's rule of keeping things in GitHub unless a common free service is clearly worth it. (3) The app runs on Fly, so the value must also reach Fly's runtime; the protected `deploy-fly.yml` already copies named GitHub secrets there with `flyctl secrets set --stage` (`GROWTHBOOK_CLIENT_KEY`, `PREVIEW_TOKEN`).

(a) **Declaring a secret.** The planner already marks `secrets` today; it will instead return a structured `secrets` list `[{name, purpose, read_by}]` in the plan, one entry per service, named `<SERVICE>_<KIND>` in capitals (for example `OPENWEATHER_API_KEY`), never one of the Factory's own names (`FLY_API_TOKEN`, `GROWTHBOOK_CLIENT_KEY`, `PREVIEW_TOKEN`, anything `GITHUB_*`). *default* The coder records the names and purposes, never values, in a public `secrets.json` at the repo root in the same commit that uses them, as `flags.json` does for flags.

(b) **Where the value lives and how the owner provides it.** In a **GitHub Actions repository secret on that app's own repo** (never an organisation secret). The owner runs `gh secret set NAME -R owner/app` (it prompts for the value, so it never appears in an issue, comment, commit, log or artifact); the Factory posts that exact command with the name filled in. The protected deploy workflow, and only the deploy job, copies the names listed in `secrets.json` to Fly before deploying, so the first boot has them. The Test Gate and Build workflows never receive them. The Orchestrator confirms a secret is set with `gh secret list -R owner/app` (names and times only) using the PAT it already has.

(c) **How the build proceeds: ask first, build after** (owner's choice). When the plan declares secrets, the run stops right after the planner, before the coder spends anything, and ends `awaiting_secret`: not a failure, not retried, not reverted, not learned from (like `refused`, the Intake issue stays open with `proceed-with-change` removed). The comment on the Intake lists each name and purpose, the exact `gh secret set` command, and says "add `proceed-with-change` again when they are set". The declared names are kept in a hidden comment, as plan metadata is. On the next start the Orchestrator checks every declared name with `gh secret list`: all present, the build proceeds; any missing, it comments which and stops again. No new label is needed. Because the real value exists in Fly by the time the build runs, the tester can exercise the live integration through the app (it never sees the value, only the app's responses); in the repository's own tests the service is stubbed, since the Test Gate has no secret. The tester keeps to its rules about real side effects and marks anything that would cost money or change the outside service `not_run`. The feature ships dark behind its flag and is released by the normal gates.

(d) **Injection and scope.** GitHub secret, then the deploy job, then a Fly secret staged before deploy. No Agent and not the Orchestrator ever holds a value (INV-01 whitelist, INV-34 and INV-45 isolation); the coder cannot edit workflows (protected files). One secret per service per app. **Residual risk, accepted:** the coder's own code runs in production with the value in its environment, so a prompt-injected coder could log or send it elsewhere. Mitigations: a reviewer rubric item (a secret is read in one place, the call to the service, and is never logged, returned in a response or sent anywhere else), the diff scan in (f), and the owner using a restricted key with a spending limit at the provider. *default*

(e) **Lifecycle.** *default* Rotation: the owner re-runs `gh secret set`; the next deploy copies it. A daily model-free pass lists each app's secrets older than 90 days (`gh secret list` update times) and comments on one open issue per app (the duplicate check applies). Expiry or revocation: the watchdog sees the errors and switches the flag off; a retry on the story cannot fix a missing or revoked secret, so a retry whose errors point at authentication is not started and the story comment asks the owner to rotate. Removal: the same pass lists secrets that no longer appear in `secrets.json` (and are not the Factory's three) as orphans for the owner to `gh secret delete`. Teardown needs nothing new, because deleting the repo deletes its secrets and destroying the Fly app deletes its runtime secrets; the teardown skill should say so.

(f) **Detection and accidents.** Already: the scan of Intake text before any spend (INV-40). Add: the Orchestrator scans every coder commit's diff for the same secret shapes before the push (a hit discards the commit, tells the coder, and nothing is pushed; the pre-push review gate is where it sits), and scans the Report, event streams and artifacts before they are uploaded, redacting a hit. Turn on GitHub's own free secret scanning with push protection when App Staging creates a repo (the `security_and_analysis` setting), so GitHub blocks known token patterns on push as well. If one slips through, the Orchestrator files a `secret-leak` issue naming the kind and the location, never the value, and tells the owner to rotate at once. *default*

**To build later (not started):** `triage.py` and `planner.py` (structured `secrets`, `awaiting_secret` replacing the `secrets` refusal; the outcome must be treated like `refused` by `finalize`, not as an OK ending, since INV-24 makes OK endings close the Intake); the start-of-run `gh secret list` check in `build_run.py`; `secrets.json` and the deploy workflow's copy step in the Starter Template (then template sync); the reviewer rubric item and the diff and artifact scan; the secret-scanning setting in `stage.sh`; the daily age and orphan pass; the golden Intake for a keyed request in `docs/golden-intakes.md`; an invariant for each of: no value reaches an Agent or an artifact, a secret-needing request builds nothing until its names exist, a coder diff with a secret shape is never pushed. One live check is worth doing before relying on it: that the deploy workflow's copy step really masks and delivers a value (use a throwaway name).
