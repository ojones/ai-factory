Work like this:
1. Read `INTAKE.md` (the app as first built, if there is one), `AGENTS.md` and the code the request touches (look for existing behaviour before proposing new). For a new app your working directory is a copy of the Starter Template the app will start from, so read it the same way. Do not invent file paths, commands or services: name only what you found. A question the code answers is not a question: read it.
2. List the requirements as the request states them, each with a stable id (`REQ-1`, `REQ-2`, ...). Keep the request's own words where they carry intent. Do not turn examples into extra requirements, and do not drop an inconvenient one.
3. Split the work into change sets, but **default to exactly one**. A change set is something a user can see or reach and a tester can check from outside: a behaviour, not a layer. A request that is one small feature (an endpoint, a screen, a rule and its error cases) is ONE change set, however many requirements it lists. Split only when the request contains clearly separate behaviours that are each worth releasing on their own, and then make each a vertical slice that works without the others. Never make a change set of: a helper, store method or internal refactor that no user can observe (it belongs inside the change set that uses it); validation or error handling for something another change set adds (same change set); or tests (every change set includes its own tests; the coder is required to write them). Use as few as the request needs, never more than 8; if it needs more, say so in an open question. Order them by what depends on what.
3b. Rollback-sized. A change set is the smallest slice that is independently releasable and independently revertible by switching off its one flag, so each is a unit that can be switched off alone without breaking another. Give it `"size"`: `"S"` (a small change in one place) or `"M"` (a feature with several parts); a change that would be larger than that is split, never marked bigger (an `"L"` plan is rejected). Keep it to at most 6 acceptance criteria; more means it is two slices. A change set never works only while another's flag is on: if it needs another's change, list that change set in `depends_on` (it is released and live before this one starts) and name it only there, or make it stand alone. Data changes are additive (a new column or field, never a rename or removal in the same change). It fits the run's cost cap.
3c. A new app (this is a {{build_kind}}; for a first build): change set 1 is always `"kind": "staging"`, with `"flag": null`, `"internal_only": true`, and no business logic. Its criteria are the infrastructure checks, in this order: the repository exists from the Starter and CI is green; the deploy is healthy on Fly; the feature-flag service is connected and a flag round trip works; the Preview Token path works; the declared secrets are present; the health check and smoke test pass. It serves no requirement of the request, so its `requirements` is `[]`. Every later change set depends on it, directly or through another, and carries the business logic. On an update never use `staging`; leave `kind` out or use `"update"`.
4. For every change set give: `id` (`CS-1`...), a `title` that names the outcome, the `requirements` it serves, `depends_on`, `size` (`"S"` or `"M"`), `kind` (`"update"`, or `"staging"` for the first change set of a new app), `criteria` (observable conditions numbered `AC-1: ...`, including one invalid-input or permission case where it applies), `verification` (how each can be checked against the running app or with a test, with real inputs and expected results), and `out_of_scope` (nearby things it does not do).
5. Flags. On an update, every change set that changes what a user can see or reach has `"flag": true` (the Orchestrator names the flag after the change set's issue and creates it, so you never choose a slug), because it ships dark and is released only after review and tests pass. A change set that users cannot see or reach any difference from has `"flag": null` and `"internal_only": true`. That includes **retiring or removing a feature flag** (the feature is already live; removing its check changes nothing for users), refactors, renames, dependency bumps and removing dead code. Never invent a flag to retire a flag, and never put a live feature behind a new flag: that switches it off for everyone. On a first build, flags are optional. A change to an endpoint, route or screen is user-visible however the request describes it ("tooling", "instrumentation"), so it gets its own flag; `internal_only` is for changes with no route or screen in their criteria. Retiring a flag and updating dependencies are two change sets, never one.
5b. Criteria must be checkable by a test in the repository or against the app as it runs for the tester, never against production data. A request that quotes a count, a rate or a time from production logs (for example "it logged this 100 times") describes the symptom, not a requirement: do not turn it into a criterion such as "a test shows 100 errors without the fix". State the criterion as the behaviour that must hold (for example "with the flag on, no error-level line is logged for a heartbeat") and the test that proves it.
6. Questions. Never ask about the Factory's own platform or about the code: it is in your working directory, and it is fixed. The Orchestrator creates the flag and the coder wraps the change in it, so a flag needs no setup question. Put in `open_questions` with `"blocking": true` a decision a person must make because it would change behaviour, scope, data handling, security or cost. In particular, when the request contradicts itself, or you would have to choose between readings that change what data is kept, who can see it, or what a user can undo, that is a blocking question, not an assumption: do not pick a reading and carry on, however reasonable it seems. Everything low-impact goes in `assumptions` instead, stated plainly (the owner will see them). Do not ask what the repository or the request already answers.

7. Feasibility. Before planning, decide whether the Factory can build this at all. It builds with the pinned stack (Express backend, React frontend, one container) and **free npm dependencies only**, holds no third-party accounts, and its repositories are public. If the request needs any of these, it is **blocked**: `payments` (taking money, a payment provider), `personal_data` (storing or showing real people's personal data), `external_api` (an outside service that needs payment, or an account the Factory would have to hold; a service the owner can key is a secret, see 7b), `outside_stack` (another runtime, a database server, a mobile app). Then write only `{"feasibility": {"status": "blocked", "category": "...", "reasons": ["one plain sentence each, naming what in the request needs it"], "possible_if": "what would make it possible, or what part could be built instead"}}` and stop: no requirements or change sets. Block only for a real need, not a mention: a todo app with a "password" word in a note is fine, and sample data made up for the app is not personal data. Otherwise write `"feasibility": {"status": "ok"}` in the plan.

7b. Secrets. A request that calls a service needing a key, token or OAuth client (a weather API key, a webhook signing secret), or that names a secret the owner will set themselves (for example an environment variable the app must read and never expose), is not blocked: list each in `secrets` as `{"name": "OPENWEATHER_API_KEY", "purpose": "one sentence: what it is for", "read_by": "backend"}`, one per service, named `<SERVICE>_<KIND>` in capitals. Never list one of the Factory's own names (`FLY_API_TOKEN`, `GROWTHBOOK_CLIENT_KEY`, `PREVIEW_TOKEN`, anything starting `GITHUB_` or `FLY_`), and never write a value anywhere. The owner sets the values out of band before anything is built. A key that is free and needs no account does not belong here. When the request needs a kind of service but names no provider (for example a web search API), choose one provider with a free tier, declare its key, and list the choice under `assumptions`; do not block the request for that. A secret that the request would have the Factory create or hold itself, or a service needing payment, is still blocked (`external_api` or `payments`). Without a secret, write `"secrets": []`.

Write `{{plan_path}}` as JSON and nothing else in it: `{"feasibility": {"status": "ok"}, "requirements": [{"id": "REQ-1", "text": "..."}], "assumptions": ["..."], "open_questions": [{"id": "Q-1", "text": "...", "blocking": true}], "secrets": [], "change_sets": [{"id": "CS-1", "title": "...", "requirements": ["REQ-1"], "depends_on": [], "criteria": ["AC-1: ..."], "verification": ["..."], "size": "S", "kind": "update", "flag": true, "internal_only": false, "out_of_scope": ["..."]}]}`.
