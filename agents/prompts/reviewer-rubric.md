A finding is **blocking** when it is any of:
- a correctness bug: wrong logic, off-by-one, unhandled error, missing validation of input the code trusts (a missing or malformed body: Express leaves `req.body` undefined when there is no JSON body, so destructuring it throws and answers 500; wrong types; unknown ids), or parsing that accepts malformed input and acts on the wrong record (for example `parseInt("1abc")` deleting item 1)
- a route mounted before the global kill switch in `backend/src/app.ts` (only the health route may be), because the kill switch then does not cover it
- a security problem: injection, path traversal, secrets in code, unsafe handling of user input
- a requirement in the spec (`INTAKE.md` for a first build, the change request for an update) that the change does not meet, including any flag it names
- on an **update** to an existing app only: a user-facing change, or a change that alters behavior for every route (middleware, a global error handler), that is not wrapped by a flag checked with `isFeatureEnabled(res, slug)`. One flag around the whole change is enough, so do not ask for a flag per route or screen. A **first build** needs no flags: never report a missing flag on one
- a flag checked in code whose slug is missing from `flags.json`, on any build, because an unrecorded flag is never released
- a flag whose default is set to anything but `false` in the diff (flags fail closed). `isFeatureEnabled(res, slug)` takes no default and already fails closed, so a plain call to it is correct and is not a finding
- code that a test would obviously not catch and the change clearly needs one
- a test added for the change that cannot fail: it asserts nothing about an output or state (only that a function exists or a mock was called), or it repeats the code under test instead of checking a stated behaviour. A test file with no real assertion does not count as the test the change needs
- on an **update**: a way to reach the change that is not behind its flag. Beyond routes and UI, check background jobs, scheduled tasks, exports and notifications the change adds or alters
- a change to stored data that the code before it cannot live with: dropping, renaming or retyping a field or table the old code still reads, or requiring data the old code never writes. The deploy applies it to everyone while the feature is still dark, and a flag cannot undo it; it must be additive

A **flag checked in several unrelated places** is a **minor** finding: one change set has one flag, checked at the single entry point of the change, so that retiring it later means deleting one check. Name the extra call sites. A flag read from a computed or stored string instead of a plain literal is also minor: it cannot be found and removed mechanically. On a **retirement** (the task or spec lists `retire-flag: <slug>` lines), for each such slug, a test of the flag-off behaviour that remains, or any change beyond removing the flag, is **blocking** (the Orchestrator already rejects a commit that leaves code mentioning the slug).

The Orchestrator checks two things itself and reports them, so do not raise them: a flag in `flags.json` that no code outside the tests reads, and a flag whose `description` does not start with an issue reference (`owner/repo#number:`).

Every finding carries a `category` (`correctness`, `security`, `data_safety`, `requirement_not_met`, `flag_misuse`, `test_quality`, `style`, `duplication` or `other`) and an `evidence_kind`: `repro` (a command or check that shows the problem, written in `repro`), `cited` (the file and line, written in `file` and `line`) or `opinion`. The Orchestrator decides what blocks from these fields, not from the label alone: a finding blocks only when you mark it blocking, its category is not `style`, `duplication` or `other`, and it has a repro or a file and line. An opinion, or a blocking finding without a repro or a cited line, is treated as minor, so cite the line or give the repro. Pick the category that fits best; a finding that fits none is `other` and cannot block.

A test that covers only the happy path of new input handling, with no invalid or boundary case, is **minor**. Anything else is **minor**. Formatting and naming are the formatter's job, so leave them out.
