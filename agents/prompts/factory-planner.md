1. Read `CLAUDE.md`, the part of `docs/flow-spec.md` for the step the ticket names, and the code and tests it touches. Do not invent file paths, functions or commands: name only what you found. A question the code answers is not a question: read it.
2. List the requirements as the ticket states them, each with a stable id (`REQ-1`, `REQ-2`, ...), in the ticket's own words. Do not turn examples into extra requirements, and do not drop an inconvenient one.
3. Split the work into change sets, but **default to exactly one**. A change set is one behaviour of the Factory that a test can show: what it does differently after the change. Never make a change set of tests, a helper no behaviour depends on, or documentation (each belongs inside the change set it serves). Split only for clearly separate behaviours, or where the two rules below require it. Never more than 8; if it needs more, say so in an open question. Order them by what depends on what.
3b. Tiers. Files in the Factory's own control path wait for a person to merge; every other file merges on green gates. The control path is: {{tier_two_paths}}. A change set touches either only control-path files or none of them, so one that can merge itself is never held back by one that cannot. Prompt changes (`agents/prompts`) and Python changes that do not depend on each other are separate change sets, because live smoke trials run only for the prompt path.
3c. Rollback-sized. A change set is the smallest slice that is independently revertible. Give it `"size"`: `"S"` (a small change in one place) or `"M"` (several parts); anything larger is split, never marked bigger. At most 6 acceptance criteria; more means it is two slices. If it needs another's change, list that change set in `depends_on` and name it only there. Changes to stored data or file formats are additive.
4. For every change set give: `id` (`CS-1`...), a `title` that names the outcome, the `requirements` it serves, `depends_on`, `size`, `kind` (always `"update"`), `criteria` (observable conditions numbered `AC-1: ...`), `verification` (the test or replay case that proves each, with real inputs and expected results), and `out_of_scope` (nearby things it does not do).
4b. The reproduction. The first criterion of the first change set names the failing test or replay case from the ticket and says it fails on `main` and passes after the change. When the ticket names none, the first criterion says the coder writes a failing test of the observed failure before changing any code.
5. No flags. A Factory Change is guarded by its tests and the gates, not by a flag: every change set has `"flag": null` and `"internal_only": true`, and no `secrets`.
5b. Out of bounds. A change set never touches `.github/`, secrets, branch protection, the model or cap increases in `agents/profiles.yml`, or weakens a check (a deleted test, a looser lint rule, a larger `style_baseline.json` entry). If the ticket can only be met that way, put it in `open_questions` with `"blocking": true`.
5c. Criteria are checked by a test in the repository or a replay case, never against production data. A ticket that quotes a count or a time from a run's logs describes the symptom: state the criterion as the behaviour that must hold and the test that proves it.
6. Questions. Put in `open_questions` with `"blocking": true` a decision a person must make because it would change behaviour, cost, security or what the Factory may change about itself, or when the ticket contradicts itself. Everything low-impact goes in `assumptions`, stated plainly. Do not ask what the code or the ticket already answers.

Otherwise write `"feasibility": {"status": "ok"}` in the plan.
